# Requirements Specification — Jellyfin Plugin "SubDL Scribe" (Upload + Download)
**Project:** Native Jellyfin plugin: automatic upload of embedded subtitles to SubDL.com + download pipeline for missing external subtitles — both in ONE plugin
**Version:** 2.61
**Status:** Implementation — v12.1.12.157-dev. Single canonical requirements document. The revision history lives in the commit log; this document states what must hold and which test proves it.
**Document convention — read this before adding an entry.**
A requirement states **what must hold**: the rule, the constant, the reason it must hold, and the test that proves it. It does **not** record how the rule came about. Measurements, incident chronology, before/after numbers, log excerpts and defect forensics belong in the **commit message**. An entry that reads as a bug report has drifted out of scope and must be reduced to its rule.
---

## 1. Objective
Automatic upload of all embedded text subtitles from the Jellyfin library to SubDL.com.
**Core idea:** Jellyfin already knows every file and every stream. The plugin handles discovery, extraction, quality assurance and upload entirely within the media server — no external polling cron, no separate state management for file discovery.
## 2. Background / Current State
**Before the plugin: manual/scripted extraction and upload outside Jellyfin** — ffmpeg extraction (one call per file, all streams at once), upload to `https://api.subdl.com` with one account, a queue and uploaded-state JSON, lock files, a not-found retry, and a repeating two-hour job with a random delay.
**Architecture decision: one plugin, two pipelines.** Download and upload are integrated in ONE plugin; the downloader is NOT a standalone app or a second plugin.
- **Upload pipeline:** extracts embedded subs and uploads them.
- **Download pipeline:** searches for missing external subtitles and downloads them.
- Both share the same services and process, with separate switches, separate scheduled tasks and separate status counters.
- **Shared components:** one SubDL API client (login, rate limit, backoff, retry), one content-hash registry (every subtitle uploaded OR downloaded is registered under a normalized content hash, consulted before either direction acts), one language mapping / IMDB resolver, one config and status infrastructure.
**Known problems the plugin must solve:** container language tags are often wrong (ISO 639-2/B inconsistent), so language verification is needed; and files in subfolders can produce path resolution errors.
### 3.1 Triggers & Discovery
- **F-M1 [B1]:** Automatic upload of new media files via scheduled task, interval configurable (daily/weekly/monthly/3 months/manual per F-M21; "on new file" = ItemAdded, F-M1a)
- **F-M2 [B1]:** Manually triggerable scheduled task (dashboard "Scheduled Tasks") for a full library rebuild
- **F-M3 [B1]:** Only process files with embedded text subtitles (`IsTextSubtitleStream` from the Jellyfin item)
- **F-M4 [B1]:** Never upload an (item, language) pair twice — persistent state file in the plugin data dir
- **F-M4a [B1]:** Only process libraries selected in the config (F-M18)
- **F-M213:** **The library selection is a hard gate for every trigger and BOTH directions. Every report names only what was SELECTED.**
 - **Work:** with `SelectedLibraries` empty, no direction may start a run. The upload pipeline and the seeder stop up front; the download pipeline must do the same (`No libraries selected — nothing to do`) instead of filtering everything away later in `CollectItems`. A run that did nothing must not look like a run that scanned everything.
 - **Report:** `CheckDirectories` (the GUI's *Library directories* list) filters on `IsSelectedName`, not on `IsLibraryRelevant`. The walk scope includes the outer library of a nested selection (F-M189), but listing that library as a status row shows a directory the user never picked.
 - **Not in scope:** the database refresh's full-server id probe stays unscoped. It answers "does this item still exist", not "should this item be worked", so narrowing it would delete rows for merely deselected libraries. **Test: T32.**
- **F-M189 [B1]:** **Library selection resolves to PATHS, so a selection keeps working when libraries are NESTED.** An item is accepted when its `Path` lies under a selected root on a **directory boundary** (`/data/movies2Extra` must not match `/data/movies2`; comparison follows the filesystem's case semantics), or when the resolved collection-folder name is selected. `LibraryScope.cs` resolves the selected names once per scan via `GetVirtualFolders` → `VirtualFolderInfo.Locations`. `IsLibraryRelevant(name)` marks libraries that CONTAIN or are CONTAINED BY a selected path, because the folder walk must enumerate the OUTER library. Applied at all five scope sites: the seeder's hard gate and its event-path gate, `CollectItems` in both pipelines, the dispatcher's event-library resolution, and the status controller's directory check.
 - **A nested layout must not be "fixed" by restructuring the library:** creating the inner library over an already-covered path succeeds via the API but stays EMPTY, and deleting the outer one is destructive. The scope must handle subdirectories.
- **F-M1a [B3]:** ItemAdded real-time trigger — the `ItemAdded` subscription in `SubdlEventDispatcher` (`OnItemAdded`); there is no separate watcher class. Each arrival starts a non-resetting debounce timer (`ArrivalDebounceMinutes`, default 5 min). On fire the dispatcher runs one cycle: seed → download → upload (download first, F-M149). Events during an active cycle collect in `pendingDuringCycleIds`; one follow-up reseed runs at cycle end if the list is non-empty, gated by `FollowUpRoundsDownload` and `FollowUpRoundsUpload`.
### 3.2 Extraction
- **F-M5:** **One ffmpeg call per file, however many subtitle streams it carries.** All text subtitle streams are extracted in a SINGLE invocation into a temp folder: repeated `-map 0:s:N -c:s srt -f srt <out>` output pairs on one input.
 - **The index rule:** stream positions are SUBTITLE-relative (`0:s:N`), never container indices. Both numbering schemes agree only while the file has no non-subtitle streams before the subtitles; mixing them lands on video or audio and fails with exit 8 or a no-stream error.
 - **No optional mapping — `0:s:N` without `?`.** A trailing `?` is the opposite of safe: on an index that does not exist ffmpeg writes the FIRST subtitle stream into that slot, exits 0 and reports nothing — a wrong-language subtitle, silently duplicated in another slot. An unknown index must fail the call, which the caller reads as a whole-pass failure and answers by retrying the empty streams one at a time.
 - **Why one call:** the per-stream cost is the READ, not the extraction — each invocation opens and re-reads the whole container, so a file with N text streams is read N times. On CIFS/NAS media those reads dominate: one pass reads the file about once and produces byte-identical output.
 - **The fallback rule:** ffmpeg's exit code decides what an empty result means. Exit 0 → the stream carries no text; that is a verdict and must NOT be retried. Non-zero → the pass failed as a whole, and each empty stream is retried once with the per-stream call instead of being recorded as a permanent extraction failure.
 - **Test: T63.**
- **F-M6 [B1]:** Text formats only (SRT/ASS/SSA/VTT via SubRip conversion); bitmap subs (PGS/VobSub) explicitly excluded
- **F-M7 [B1]:** Safely delete temp files after processing (success AND failure)
- **F-M185:** **Canonical SRT form — one normalization for hash AND payload.** Every extracted or loose SRT is normalized once on arrival, before any QA gate, hashing or upload: strip a leading UTF-8 BOM, CRLF → LF, lone CR → LF, trim trailing whitespace. The same string feeds both `ComputeHash` and the upload body, so hash input and uploaded bytes are identical by construction. The normalization is **idempotent** and runs at extraction, at loose-file read, and again in the upload path (reachable via the retry path).
 - **Why:** ffmpeg writes CRLF for some container streams and LF for others, so identical subtitles produced two different hashes and two payloads. SubDL stores the MD5 of the raw file, so it saw two distinct entries and its own duplicate check could not fire. LF is canonical because it is the hash definition, the SRT standard, and readable by VLC/mpv/ffmpeg/Kodi/Jellyfin.
### 3.3 Upload
- **F-M8 [B1]:** SubDL API (`https://api.subdl.com`): login (user/pass → token), upload endpoint, rate limit 1–3 s between uploads
- **F-M9 [B1]:** Metadata per upload: series IMDB (**not** episode IMDB) + season + episode for TV; movie IMDB for movies — from Jellyfin provider IDs. Without IMDB → skip (F-M28). **F-M151:** the upload ID quality gate validates/corrects JF IDs via TMDb before upload, default ON. **F-M203:** the TMDb key is required — the gate is not optional.
- **F-M10 [B1]:** Language mapping to SubDL's two-letter codes (`nob→NO` etc.)
- **F-M11 [B1]:** Upload queue with retry: failed uploads (HTTP 5xx/timeout) retried with exponential backoff, max N attempts, then status "failed" + dashboard display
- **F-M12 [B1]:** Configurable account (SubDL user/pass) in plugin config, password never in plaintext in logs
- **F-M48 [D2]:** **Loose SRT files as an additional upload source:** external `.srt` files next to the media file are uploaded in addition to embedded streams. Language detection from the filename suffix; unlabeled treated as EN. The marker is **`sdh` only**, and such a file is uploaded with `hi=true` (F-M71). `hi` is NOT a marker — it is the ISO 639-1 code for **Hindi** (`MapToSubdl("hin") = HI`), so `Movie.hi.srt` is a Hindi subtitle. Nothing in this plugin writes `.hi.srt`; the downloader writes `.sdh.srt` (F-M239). The HI flag is part of the identity in both areas (F-M197, F-M199).
- **F-M88c [B3]:** **Upload-side short-circuit (`SubtitlesUploadedAt`):** a file whose embedded subtitle side is complete is skipped before any ffprobe, directory walk or API call. Complete means every stream position reached a terminal state (uploaded or rejected). The field is named after the SUBTITLES, not the file: the video file itself is never uploaded.
- **F-M151a [B3]:** **Download-side short-circuit (`SubtitlesDownloadedAt`):** analogous to F-M88c. The stored language set is part of the state: the mark covers the languages it was written for, and any configured language it does not cover makes the file un-done. **Subset, not equality:** a stored set that covers the configured one counts as complete (F-M234), so removing a language leaves existing marks intact. The mark is validated against the disk before it is trusted (F-M234).
### 3.4 Quality Assurance (QA — before every upload, automated)
- **F-M13 [B2]:** SRT parser validation: valid UTF-8, ≥1 cue, monotonically increasing timestamps, plausible cue duration (>0.1 s, <10 min — long music cues stay legal)
- **F-M14 [B2]:** Sync plausibility: cue span vs. media runtime (+5 min tolerance; all cues concentrated in <10 % of runtime = reject)
- **F-M15 [B2]:** Language verification: detected language of the content (script blocks for CJK/Cyrillic/etc., Latin via stopwords) vs. stream tag; mismatch → skip; undetectable content passes (fail-open)
- **F-M16 [B2]:** Minimum size (hard 2 KB floor, always on) and minimum cue count (30) — below that "too small", skip
### 3.5 Duplicate Handling
- **F-M17c [B2]:** **Own upload dedup:** (item, language) pair + content hash in persistent state — never upload an already-uploaded or in-session-processed content hash twice. Depends on the canonical SRT form (F-M185): the hash is only stable across extraction runs when the payload is normalized first.
- **F-M17c2:** **Remote duplicate detection requires a canonical payload AND a matching hash function.** The registry hash is comparable with SubDL's stored raw-file MD5 only when both describe the same bytes and use the same function (F-M186). F-M185 and F-M186 are therefore **preconditions** of this section, not improvements to it.
- **F-M17x [B2]:** **Remote duplicate learning:** when SubDL rejects an upload with "Duplicate upload: identical file already published", the normalized content hash is stored as `duplicate-remote`. Future runs skip that content before any API call.
- **F-M186:** **The registry content hash uses SubDL's own function** — `ContentHashRegistry.ComputeHash` returns the MD5 of the canonical payload from F-M185, lowercase hex, 32 characters, equal to the `md5` SubDL stores in `raw_files[].md5` for our uploads. Changing the function **invalidates the existing registry**; the database reset (F-M90) is the intended path, no migration. The media hash (F-M61) is unaffected — it is the OpenSubtitles OSHash over size + first/last 64 KiB.
- **F-M187:** **Downloaded bytes have exactly one decode path.** Every conversion of downloaded subtitle bytes to text goes through `DecodeSrt`, which honours a UTF-16 byte-order mark (LE/BE, stripped) and falls back to UTF-8. The download side hashes `DecodeSrt(bytes)`, and the upload side later reads the written file as UTF-8/UTF-16 text, so the two must agree. The file on disk stays **byte-identical** to SubDL's payload — normalization applies in memory for hashing and upload, never to the stored file.
 - **Why:** a bare `Encoding.UTF8.GetString` on a UTF-16 payload produces mojibake on one side only. The hashes then diverge, `IsContentKnown` misses, and the file is downloaded *and* uploaded again. The runtime check degrades silently as well: UTF-16 NUL bytes break the timecode regex, so it reports a match without comparing anything.
- **F-M17z [B2]:** **Upload dedup respects the stored outcome:** any recorded outcome — uploaded, or rejected with any reason — counts as "known". With the four-state model of 3.18 this is simply "a row exists", and a new rejection reason never needs a new state name.
- **F-M61:** **Path-independent dedup key (OSHash):** upload dedup keyed on the media content hash, persisted across restarts, moves and renames.
- **F-M184:** **Duplicate handling delegated to postprocessing:** the upload path does not search SubDL for duplicates before uploading. A duplicate upload is accepted by the API ("sent for review"), resolves to `rejected` on the SubDL dashboard, and the postprocessing job deletes that entry and marks the local row `remote-duplicate`. This removes one search call per item from the hourly bucket and the daily search quota; the cost is one upload per duplicate. A local self-echo guard (registry, per media/language pair) still prevents uploading the same pair twice.
### 3.6 Configuration / User Interface (IPluginConfigurationPage)
- **F-M18 [B1]:** Library selection: checkbox list of all JF libraries — only selected ones are scanned/uploaded (default: none, deliberate opt-in)
- **F-M19 [B1]:** Credentials: SubDL **username/password** *or* **API key** (both fields present; API key preferred if set, else user/pass → token)
- **F-M20 [B1]:** Configurable rate limit: uploads/hour (**default 400**) or a minimum pause between API calls (`MinCallPauseSec`, 0.1–10 s, default 0.5 s; the smaller of the two wins). `GlobalRateLimiter` clamps the rate to **1–2000**; `RunWatchdog` clamps its grace calculation to **1–500**. The default of 400 sits inside both.
- **F-M21 [B1]:** Update interval: **daily / weekly / monthly / 3 months** (scheduled fires at the per-installation diced random anchor, F-M51) or **manual** (no scheduled fires, dashboard/config-page triggers only); "on new file" = F-M1a. **Default: Weekly** — since F-M111 both directions share the unified `RefetchInterval`, whose constructor default is Weekly.
- **F-M22 [B1]:** **Dry-run switch: search runs, no transfer.** The pipeline walks its full decision path — search, threshold, ranking — and reports what it WOULD do (chosen candidate per language, the numbered slots of F-M242, the hearing-impaired pick of F-M241), but fetches no file and writes nothing.

 - **Why it is load-bearing:** with HI on, the second search is what makes the variant visible, so a dry run that skipped searching could not report it.

 - **Every refreshed endpoint carries a cache-buster** (`_t=Date.now`), so no layer can serve a stale body.
 - **Why this must be stated rather than assumed:** a loader called ONLY at page init is indistinguishable from server caching — a finished worker run changes nothing until an F5 — and the cause has to be visible in the code. The server's caching headers are not the explanation.

### 3.7 Status & Transparency
- **F-M23 [B2]:** Status view: two cumulative counters on the config page — subtitles uploaded and downloaded since the last reset. The line reads "N subtitles uploaded, M subtitles downloaded since <date> (last timer reset)". "Reset statistics" zeroes both and moves the date. Both are incremented at the end of every run from that run's summary, including runs cancelled from outside: the pipelines return their partial summary, so work that reached SubDL counts.
- **F-M209:** **A run's in-run watchdog is torn down on EVERY exit path.** Dispose, `ApiActivity` unsubscribe and null-out sit in the `finally` next to `PipelineRunLock.Release`.
 - **Why:** a watchdog released only inside the `try` outlives a run that left on an exception, then logs "no progress for N min" for a run that no longer exists. `UploadPipeline` already used `using var watchdog`; the asymmetry produced phantom aborts on the download side only. **Test: T28.**
- **F-M208:** **The reschedule budget is per UTC day and resets at the day roll-over** — the same 00:00 UTC boundary the SubDL quota reset uses, so the budget returns when the quota does. `ResetDailyRescheduleBudget` clears every slot at the roll-over, from the scheduler tick and from the top of `TryCountReschedule`. It is a no-op when the day has not changed.
 - A slot at the limit has no other path back: the refusal drops its pending fire, so it can never fire, so it can never clear its counter. With `RefetchInterval = Manual`/`OnArrival` no anchor exists that could.
 - Both refusal messages name the day roll-over as the recovery path, and do not promise a regular anchor — that anchor does not exist in those modes.
 - A manual run and a successful run do not clear the counter. Only a real fire or the day roll-over does. **Test: T27.**
- **F-M207:** **The cumulative counters live in the database; a database reset resets them with it.** Single-row area 5 (`status_stats`, key `"status"`, `long` counters — `int` would overflow far earlier). Write `Plugin.AddStatusCounters`, read `Plugin.GetStatusStats`, zero `Plugin.ResetStatusStats`.
 - `scope=all` calls `ResetStatusStats` in the same operation, so display and data cannot disagree.
 - GUI reads `GET /Plugins/SubdlSync/Stats`; reset posts `POST /Plugins/SubdlSync/StatsReset?confirm=true`. No live page path may read `config.StatusUploaded`.
 - The pre-migration XML totals are adopted once, guarded by `StatusCountersMigratedToDb`. Without the flag a restart after a database reset would re-import them. It is listed in `PluginOwnedFields` so an automatic save cannot drop it.
 - The XML fields `StatusUploaded`/`StatusDownloaded`/`StatusStatsSinceUtc` stay in place, unread, so a downgrade finds them. **Test: T26.**
- **F-M219:** **The type-neutral TMDb search is the FIRST rung wherever an id is resolved, and the year is checked on its RESULTS.**
 - The year must not be sent to `search/multi`: it ignores the parameter, so a query carrying one reads as a filter while filtering nothing. The typed endpoints honour it, which is why the typed search is the second rung.
 - The year is applied when the hits are read: a hit whose own date (`first_air_date`, `release_date`) equals the year wins over the first hit. With no year-equal hit the first film/series hit is used. `hits[0]` alone picks by POPULARITY, not identity — "Fargo" resolves to the 2014 series when the item is the 1996 film. The fallback is required, because a Jellyfin year is often the IMPORT year (F-M217).
 - Both id-less paths start type-neutral: `DownloadPipeline`'s title rung and `SubdlSeeder.ResolveIdsOfAsync`. A typed search inherits Jellyfin's guess, so a name-detected series typed as a `Movie` asks `search/movie` and can never match. **Test: T36.**
 - The seeder parses the file name before it asks TMDb (same `MediaNameParser`, F-M217), and returns the type TMDb reports.
- **F-M222:** **Every required field is marked ONCE on the configuration page, and states where to get the value.**
 - Four required inputs: **Libraries** (F-M213), **SubDL account** (login + API key), **TMDb API key** (F-M203), **Download target languages** (F-M42: empty = download off). Each carries a `Required` marker via `.subdl-required` / `.subdl-req-inline`, defined in both `configPage.html` and `configPage.js`. The colour is F-M228's accent blue.
 - The marker sits in parentheses after the field name: `Libraries (opt-in, Required)`, `SubDL Account (Required)`, `TMDb (Required)`, `Target languages (Required)`. Opt-in and required are separated by a comma in the same parenthesis, never stacked.
 - The description explains what the value is for. A requirement repeated per field (label suffix, `required` attribute, bold "Required") reads as emphasis and stops being read.
 - Each field names its source in the order the user needs it — register first, then the key. SubDL: `https://subdl.com`, then `https://subdl.com/api-doc`. TMDb: `https://www.themoviedb.org`, then `https://www.themoviedb.org/settings/api`.
 - Libraries is opt-in AND required: nothing is processed until a library is picked, and the description states that an empty list stops every run.
- **F-M220:** **The plugin description has TWO carriers and they must not drift — the card reads the DLL, not build.yaml.**
 - Dashboard → Plugins renders `Plugin.Description` from `Plugin.cs`, compiled into the DLL. The `description` in `build.yaml` only feeds the catalog manifest, so shortening one leaves the other visible.
 - Both must hold the same text, capped at **260 characters**, and must still name the required SubDL and TMDb keys.
 - `scripts/release.sh` enforces all three (identical, under the limit, keys named) as a precondition, so changing one carrier alone aborts the release. **Test: T37.**
 - Changing the card text requires a **DLL rebuild and a Jellyfin restart**; the string is not read at runtime.
- **F-M231:** **Jellyfin's ids are ALWAYS tested against TMDb by TITLE and YEAR; the year comes from the FILE NAME when it states one.**
 - The pair check is not enough: `ResolveAndValidateIdsAsync` answers "do these two ids describe the same entity", which a wrongly pinned pair passes. Title and year were never asked.
 - Year source: the file name's year first, Jellyfin's only as fallback (`Movie.ProductionYear`, else `Episode.Series.ProductionYear`) — Jellyfin's year comes from the metadata that may be pinned to the wrong title.
 - Correction only on an EXACT year match (`ResolveByTitleYearAsync`, the strict twin of the multi-search). No exact hit ⇒ Jellyfin's ids stand, so a missing year or a differently spelled title costs nothing (F-M190).
- **F-M232:** **A login that fails on a server error is CLASSIFIED, never propagated raw.**
 - An unclassified failure propagates as a raw parse exception: the cycle logs a generic failure, the recoverable overload is never recognised, and the F-M67 overload fire is never scheduled.
 - Every login attempt is classified: 404 `NOT_FOUND` and 403 are auth verdicts (fail closed, `AuthBroken`); 429 keeps its retry/backoff; a 5xx or a non-JSON body after the retries exhaust is a **transient overload** — sets `TransientOverload`, ends the run cleanly, schedules the F-M67 fire.
 - A JSON body behind a 5xx is still transient, never a credentials verdict: the status code decides.
 - The client's `Log` channel (login retries, raw 429 bodies, rate headers) is subscribed per run by both pipelines, so the retry line is reachable.
- **F-M238:** **A 429 is not a verdict — the COUNTERS decide whether the allowance is spent.**
 - Every 429 is classified into three variants: rate headers present → the daily allowance, exact reset from the header; body `service_busy` → transient overload, wait the server window; body `rate_limit` with `retryAfterSeconds` → a short-term trip, waited out like the overload. Only when the counters say the allowance is spent does the run stop for the day.
 - The status code alone cannot decide: SubDL answers 429 for both cases. "Spent" turns a short pause into a lost day; "harmless" turns a spent account into a retry storm.
 - The counters come from the same source the settings page shows (`GET /api/v2/me`, `usage.search`/`usage.downloads`), read only after a 429, so GUI and pipeline cannot disagree. Search and download are separate allowances, so every decision names its direction.
 - An unreadable quota is not a free quota: when the read fails or carries no limits, the 429 remains a stop.
 - A next-day fire anchors on the server's own `reset_at`, never a local midnight guess, with the jitter on top. `Continue after daily limit` still gates that path per direction.
 - The respacing offset is `JobSpacingMinutes` (clamped 5–120); no fixed interval is introduced for this case.
 - Every day-long stop schedules: a spent and an unreadable allowance both end in a fire after the reset plus the 30–300 min jitter. Only the direction's toggle off, or an arrival run holding the slot, stops without a fire.
 - A dry run reports the hearing-impaired choice — the HI variant is selected beyond the point a dry run stops, so the run repeats the selection and reports it (`DRY-RUN HI … (n/m candidates are HI)`). **See T52, T53, T55.**
- **F-M237:** **A `Rebuild` that cannot release the pages is replaced by a rebuild from the file's own rows.**
 - Rule: when LiteDB's own `Rebuild` fails, rows are read out, written into a fresh file, counted against the original, and only a matching count is swapped in. Rows are never traded for a smaller file.
 - `Rebuild` walks every index and past a few thousand rows exceeds its internal traversal limit and throws. The file then keeps every freed page forever, so the nightly refresh reports no shrink on every run.
 - The swap is a rename, not a copy: a running Jellyfin holds the file open, and a copy over it is refused with "being used by another process".
 - The previous file survives as exactly one timestamped backup, reachable through the database restore function. Nothing is deleted until the row count is proven equal.
 - The rebuild's side files are addressed by their STEM (`subdl-scribe-log.db`, `subdl-scribe-temp.db`), never by appending to the full name, which matches nothing on disk. **See T54.**
- **F-M236:** **A failed compaction must not leave the shared database dead.**
 - `LiteEngine.Rebuild` runs `Close` → `RebuildService.Rebuild` → `Open`, and the `Open` sits on the success path only. Any throw inside `RebuildService` leaves the engine closed, and with it every collection handle on the shared `SubdlDbContext` for the rest of the server's life: every database endpoint then fails with `ObjectDisposedException`, while readers that do not touch the database keep working.
 - The compaction is verified, not trusted: after a failed rebuild the database is probed with a real query (`Meta.FindById("db")`), and only a failing probe replaces the engine.
 - The repair is a fresh `LiteDatabase` over the same path — the engine cannot be reopened in place, because `Close` leaves `_state.Disposed` set. The collections are property getters over `_db`, so they resolve against the new engine on next access; `EnsureIndexes` runs again afterwards.
 - Three outcomes: `Compacted` (file shrunk), `Recovered` (rebuild failed, store back, **file NOT shrunk**), `Broken` (restart required). The refresh logs `compacted: X -> X bytes` for no outcome — a `Recovered` run states the file was not shrunk and the next refresh retries.
 - The repair preserves the data: the failed swap leaves the original file on disk, so rows survive. **See T51.**
- **F-M235:** **A transport timeout is retried three times; a user stop never is.**
 - A timeout is transient, like the 5xx login answer of F-M232. An expired request threw `TaskCanceledException`, which the API clients do not catch, so it reached the run loop's `catch (OperationCanceledException)` and was reported as "cancelled — keeping the partial result": a slow server looked like the stop button.
 - The two cancellations are told apart by one source of truth, the caller's token. Already cancelled → the user asked to stop, the request is not repeated. Otherwise the cancel came from the handler's own per-attempt timeout and the request is worth repeating.
 - Budget: 3 attempts per request (as in F-M232), 1 s base backoff, doubling. Transient means `TaskCanceledException`, `OperationCanceledException`, `HttpRequestException` or `IOException`; a `JsonException` is an answer and is never retried.
 - Per-request timeout, not one global value: 60 s per attempt for API calls, overridable via `HttpRequestOptionsKey`; a subtitle FILE download asks 5 minutes, because a season archive is orders of magnitude larger than a metadata answer. `HttpClient.Timeout` is disabled so it cannot cap the whole sequence including retries.
 - The request body is buffered once and the request rebuilt per attempt, otherwise the second attempt fails on consumed content.
 - The give-up line names the server as not answering in time, never as a caller cancel, and the retry lines are routed into the run's log channel. **See T50.**
- **F-M233:** **An on-arrival run works ONLY the arrivals; a full-coverage pass happens on the schedule or the manual button.**
 - The arrival path must be scoped to the items that arrived. Unscoped, one arrival window swept every gap in the library into the queue and the run died on the daily limit before reaching its own items.
 - The debounce window collects EVERY event in it, not merely the first, and arrivals during an active run form the follow-up window. An arrival cycle seeds and works exactly those ids.
 - Only `event` and `arrival-followup` are scoped. `scheduled-upload`, `scheduled-download`, recovery fires and the manual button carry no item scope and keep full coverage for the selected libraries.
 - "Kein treffer, kein lauf": an arrival-scoped round whose seed queued nothing for that direction ends instead of working leftover queue entries.
 - An arrival cycle with an empty collector ends without a scan. Falling back to a full scan on the arrival path is a defect, not a graceful default. **See T48.**
- **F-M234:** **The state prune is a database refresh: it verifies the FILE side of a stored verdict, not only whether the item still exists.**
 - A removed item is only the crudest case. A subtitle file deleted while its item stays keeps a verdict saying "uploaded"/"rejected"/"downloaded" and a download mark saying the language is settled — both permanently wrong, and the item is reported complete forever while the seeder keeps queueing it.
 - The mark cannot be replaced by a disk check, only falsified by one: it means "every target language settled", and settled includes "SubDL does not have it" (QA-exhausted, no file expected). A stored language is stale only when it is absent from disk AND not QA-exhausted (`FindStaleDownloadedLanguages`); the mark is then dropped and the search stamp cleared, so the item is reworked in the SAME run (`MarksInvalidated`).
 - Fail-safe, same two-tier rule as the oshash cache: every root the stored paths live under must exist and list cleanly, else the file side is skipped entirely. Rows without a stored path are never judged. "Unknown ≠ deleted" — a missed refresh costs nothing, a false one destroys valid verdicts.
 - Subset rule: a stored language set that COVERS the configured one counts as complete, so removing a language does not invalidate every mark; adding one still does.
 - Naming: task, dashboard name, log prefix (`[SubDL-Refresh]`), lock slot (`dbrefresh`) and the GUI heading say "database refresh". The config fields (`PruneMode`, `RandomPruneTime`) deliberately stay — they are serialized, and renaming would drop the user's settings. **See T49.**

### 3.8 Anti-Synchronization (thundering-herd protection)
- **F-M25 [NOT IMPLEMENTED]:** A per-run start offset (random wait before the first upload) is not implemented — no code path delays a run, no config property backs it. The anti-herd function is carried by the per-installation diced fire times (F-M51), the hourly-cap roll-over offset (`JobSpacingMinutes`, F-M26b) and the daily-limit recovery jitter (F-M182, 30–300 min). Manually triggered runs start immediately.
- **F-M26 [B2]:** **Random jitter in the rate limit — on the transfer rhythm, not on bare calls.**
 - The pause between two real transfers (upload→upload, download→download) is the base interval ±30 % (`GlobalRateLimiter.TransferPauseMs`).
 - The pause between two API calls carrying no transfer (empty search, skip, metadata lookup) is **deterministic** (`InterCallPauseMs`): exactly `MinCallPauseSec` when configured, otherwise `3600/cap`.
 - **Why:** transfers are the load a shared API actually sees, so that is where a randomised rhythm matters; spreading idle calls adds nothing. The two are also separated by name.
 - The band is base ±30 %, floor 1 s. With the default cap of 400/h that is 6.3–11.7 s.
 - A failed or skipped candidate gets **no** transfer pause — nothing was transferred — and stays on the bare-call pause (F-M26a).
 - The "derive from the hourly cap" sentinel `-1` must **survive** clamping; only a real value is clamped, otherwise `Math.Clamp(-1, 0.1, 10)` yields 0.1 and the derived branch is unreachable. **Test: T21.**
- **F-M26a:** **Which pause applies where (single source of truth).** `InterCallPauseMs` — bare API calls, deterministic. `TransferPauseMs` — real transfers, ±30 %.
- **F-M26b [D]:** **Hourly-cap roll-over fire is offset by `JobSpacingMinutes`.** When the shared hourly bucket is exhausted mid-run, the run stops and a one-shot recovery fire is scheduled at the bucket roll-over **+ `JobSpacingMinutes`** (both directions, `ScheduleHourlyFireIfExhausted`), clamped 5–120. Default 15.
 - One knob for all spacing — the user configures it through the existing **Job spacing (minutes)** field, with no separate control to discover.
 - Anti-herd spreading is not needed here: the offset is per installation and rides the account's own hourly roll-over, not a shared wall-clock event. The daily-limit reset keeps its randomised 30–300 min offset (F-M152, F-M182).
 - The coordinator must not add a second offset on top: this path uses `ScheduleRecoveryFireAt`, whose `alreadyJittered: true` leaves the caller's offset alone. The offset must not affect the daily-limit reset. **Test: T22.**
- **F-M27 [B2]:** **Auto-backoff:** on HTTP 429/rate-limit or 5xx the request is retried up to 3 attempts with exponential backoff (2 s, then 4 s; the server's `retryAfterSeconds` wins when sent, minimum 5 s). On exhaustion the request fails cleanly and the run-level reaction matrix (F-M54) applies.
### 3.9 Privacy / Anonymity
- **F-M28 [B1]:** **IMDB ID mandatory — correct per media type.** For series strictly the series IMDB (tvshow, not episode) plus season and episode; for movies the movie IMDB. Resolution order: (1) Jellyfin metadata as-is; (2) TMDB id → IMDB via the TMDB REST API (key required, F-M203); (3) TMDB title search; (4) skip "no-imdb". Episode IMDB is never used. The 15-min metadata wait was removed (F-M100).
- **F-M190 [B1]:** **ID resolution is type-free and TMDB-authoritative, and it is the standard path for every upload** — not an optional gate.
 - **Type detection comes from the FILE NAME and from TMDB, never from the Jellyfin library type.** `MediaNameParser` reads the name (`S01E05`, `Season 1 Episode 5`, TV stamps `Title_YYYYMMDD_HHMMSS`); when it reports a series while Jellyfin reports none, the item IS resolved as a series. A later `search/multi` answer overrides the assumed type: **TMDB decides** film or series. The library type is never the source — an episode in a library typed "movies" is imported as a `Movie`, so class-based detection would search TMDB for a FILM named after the episode.
 - **ID arbitration (JF vs TMDB) with a report:** both IDs present → cross-validate; on disagreement a **Normal-level** line is emitted (`ID conflict for "<title>": Jellyfin says <tt…>, TMDB says <tt…> — using the TMDB id`) and **TMDB wins**. Visible without raising the log level.
 - **Fallback chain:** TMDB returns no IMDb → the Jellyfin ids are kept; Jellyfin carries only a TMDB id → the IMDb id is fetched from TMDB; **no IMDb resolvable at all → NO upload** (fail-closed).
 - **Upload payload preference:** IMDb + TMDB when both are known, IMDb alone when TMDB is missing. Neither → no upload.
 - **Series IMDb needs `/external_ids`:** the detail endpoint reports `imdb_id: null` for series, while `<kind>/<id>/external_ids` returns the real `tt…`. `ResolveImdbAsync` falls back to it whenever the detail response leaves the id empty — without it every series was skipped as "no-imdb".
- **F-M28a:** Before every SubDL search/upload the plugin calls `ResolveAndValidateIdsAsync` to cross-check and correct Jellyfin's IDs via TMDB when a key is configured. Mismatches are corrected, missing IDs backfilled. Automatic whenever a TMDB key is present; no separate UI switch.
- **F-M249:** **The file-name parser reads two more real name shapes, and nothing else changes.** `MediaNameParser` recognises (a) a **bare episode marker without a season** and (b) a **broadcast date in the middle of the name with the title AFTER it**. Every other shape keeps its previous result.
 - **(a) Bare `Exx`.** `The Revolutionaries E05.mkv` carries no `S<d>E<d>`, so the series pattern never matched and the item was treated as a **MOVIE**, searched as `The Revolutionaries E05` (0 hits) while TMDb knows the series. The rule sets `IsSeries=true` and the episode number, then **falls through to the shared head/year/quality cleanup** — a separate return path would let the two branches drift.
 - **The bare marker is guarded.** `[Ee]\d{1,3}` alone is dangerous: `Movie.1080p.x265-E5.mkv` is a release-group suffix, not episode 5. A marker directly after `-` and preceded by a known codec token (`x264`, `x265`, `h264`, `h265`, `hevc`, `av1`, `aac`, `ac3`, `eac3`, `ddp`, `dts`, `10bit`, `8bit`) is **rejected**; dot, space, underscore and bracket separators keep it.
 - **(b) Mid-name broadcast date.** `BBC.Documentaries.2016.05.11.Cunk.on.Shakespeare.…` is `<strand>.<YYYY>.<MM>.<DD>.<title>.<tags>`, so the **title follows the date and the prefix is the strand**. Taking the first year and cutting there produced the strand (`BBC Documentaries`) as the title, which resolved to an unrelated film. The rule takes the text after the date, cuts at the first release/language token and drops trailing bare numbers.
 - **The date rule is narrow by construction:** it applies only when (1) no `SxxExx`/long-form marker is present, (2) the date is a **separated** `YYYY<sep>MM<sep>DD` (the compact `YYYYMMDD` stamp belongs to `TvStampPattern`), (3) month and day are in range, and (4) **text follows the date** — `Movie.2016.05.11.mkv` keeps `Movie` + year 2016.
 - **Scope:** only those two shapes change; every other file parses byte-identically in title, year, type, season and episode, and no file loses its title.
 - **Deliberately NOT changed:** the prefix of (b) is dropped, not combined (a strand is not part of a title); a bare `Exx` never invents a season; the compact TV-stamp path is untouched; and the `E` must be **uppercase** — a lowercase `e` is indistinguishable from a word fragment (`Z00topia.2.e5`).
 - **Not addressed here:** `Cunk on Britain` / `Cunk on Earth` parse **correctly** (S1E4 / S1E1). TMDb files both broadcasts as ONE entry (`Cunk on...`, tv 79063) whose `imdb_id` is empty, so F-M231's rule discards ids TMDb cannot confirm. That is a TMDb data gap, not a name parse, and needs its own decision. **Tests: T68, T69.**
- **F-M251:** **one name parser, not two.** The download side carried its own copy of the name logic — its own SxxExx regex, year regex and quality-tag list — so it kept every gap the main parser had already closed, and every future name shape would have had to be fixed twice. On the test instance the download path resolved the Cunk name as the strand while the upload path yielded `Cunk on Shakespeare` — same file, same run, two answers.
 - `ParseFileNameForIds` now calls `MediaNameParser.Parse` and returns `(Title, Year, IsSeries)` — same shape, one authority. The private regexes are gone.
 - **Deliberately NOT merged:** `SubtitleCandidate.EpisodeFromFileName` keeps its own patterns. It answers a different question — "which entry inside a SubDL ZIP is my episode?" — and must handle SubDL's `S0106` style, which is not a file name on disk. Two readers for two inputs is not duplication.
 - **Scope is arithmetic:** the files this change may touch fall into six named groups (`NxNN`, bare `Exx`, `SxxExx`-at-end, date names, long form, bracket titles), and the groups must add up to the diff total. If they do not, an unintended change hides in it. **Tests: T71.**
- **F-M252:** **a bracketed year is a year, and its opening bracket is not part of the title.** `TailYearPattern` must close its character class correctly and accept `(YYYY)` and `[YYYY]` at the tail. A pattern that cannot match lets every name fall through to the "year anywhere in the head" branch, which cuts at the YEAR rather than at the separator before it — so `The Pitt (2025) S02E01 …` parses to the title **`The Pitt (`**. Such a title is never real, and TMDb answers it with a different title than the clean one, so the id test compares against the wrong name.
 - **Three changes, each with its own reason:** (a) `TailYearPattern` closes the bracket properly; (b) the "year anywhere" branch cuts at the **start of the match** (the separator), never at the year, so no separator is left dangling; (c) `NormalizeTitle` drops an unclosed trailing `(`/`[`/`{` as a last line of defence.
 - **The diff is the bracket and nothing else** — every changed file must be a bracket name, and any other file in the diff is a regression. T71 asserts the bracket case, the `[YYYY]` variant and the "no other diff" claim.
- **F-M250:** **The parser reads two more series markers.**
 - **(a) `NxNN` (`2x01`).** Without the marker the item was typed as a **FILM** and searched as `Reacher 2x01 Sportello Automatico ITA ENG` (0 hits) while TMDb knows the series. Now read as a season/episode marker.
 - **The `NxNN` rule cannot misfire on a resolution.** `1920x1080` is the trap, so the season is capped at two digits, must not start with `0`, and may not be preceded by a digit (`(?<!\d)` + `[1-9]\d?`). Verified: `1920x1080`, `2160x1080` and `0x01` yield nothing; `1x01` → S1E1, `10x05` → S10E5.
 - **(b) `SxxExx` at the END of the name.** `SeasonEpisodePattern` required a separator AFTER the episode number, and a name ending in `E01` has none — so `For All Mankind S02E01.mp4` was typed as a film. The trailing separator is now optional-at-end (`(?:[\.\s_-]|$)`).
 - **The library diff is the acceptance criterion.** A filename parser that widens re-identifies a whole library quietly, so the four-group arithmetic proves the change is a fix rather than a drift. No file changes outside those groups, none loses its title, season or episode.
 - **`guessit` was NOT adopted.** It fails the Cunk date name and misreads `Movie.2024.1080p.x265-E5.mkv` as `season 2024, episode 5` — a release-group suffix taken for an episode, precisely what our codec guard rejects. The C# ports are anime parsers that do not cover these release shapes. It remains a useful oracle, not a dependency. **Tests: T70.**
- **F-M203 [B1]:** **The TMDb API key is required — a SERIES is refused without it, films still upload.**
 - Rationale: id resolution is TMDB-authoritative (F-M190) and the SHOW id a series upload must carry (F-M191) is only obtainable through the key. With Jellyfin's own ids a mis-typed episode would be uploaded with an **episode id in the series slot**.
 - **Scope: series only.** A film whose ids come from Jellyfin is not mis-slotted, so films keep uploading and the plugin stays usable for film-only libraries. Without a key no series resolves and such files stop at `no-imdb`.
 - Upload and download side alike: a series without a key is skipped with `no-tmdb-key +1`, counted in `SkippedNoTmdbKey`, requeued — never uploaded with episode ids.
 - GUI: the field label reads **"TMDb API key (v3) — required"**, the input carries `required`, and the save handler **refuses to save an empty key** instead of silently degrading the pipeline.
 - Status: a missing key reports **red** with "Not configured — REQUIRED: series are skipped without it (films still upload)".
- **F-M202 [B1]:** **An episode TMDB id is PROVEN against a candidate show — never guessed.**
 - Jellyfin reports an episode TMDB id with no IMDb id for some files, and `/find` **cannot** walk an episode id up to its show — `find?external_source=tmdb_id` returns every result array empty. Dropping such an id leaves the item with no ids at all.
 - Rule: title + season + episode from the **FILE NAME** → `search/multi` → candidate show → `tv/{show}/season/{s}/episode/{e}` → accept the show **only when the episode id returned there equals Jellyfin's id**. A confirmed match yields the SHOW ids (imdb via `/external_ids`, since the detail endpoint reports `imdb_id: null` for series).
 - **Fail-closed:** no confirmed equality ⇒ `(null, null)` ⇒ the item is skipped like any other unresolvable series. A title search alone is never sufficient — "Last Seen" also returns "Last Seen On Holiday" and "Last Seen Alive", and only the id equality makes the mapping provable.
 - Season/episode always come from the file name (Jellyfin reports none for a mis-typed episode).
 - **Known limit:** an item carrying an episode TMDB id and no usable S/E in the file name cannot be resolved by an id lookup, only by the title search. Records already written with episode ids are **not** repaired retroactively — `PatchMediaMetadata` runs only on upload/download.
- **F-M29 [B1]:** **No user-identifying metadata in uploads:** exclusively IMDB ID + season/episode + language + subtitle file. No username, no library/path information, no source media filenames, no server/installation identifiers, no version telemetry.
- **F-M30 [B1]:** Neutral upload filename: derived generically from the IMDB/language/release info — never internal JF paths or user names.
### 3.10 Skip Filters (configurable)
- **F-M34 [B1]:** **Skippable directories:** configurable list of folder/path patterns (e.g. `incomplete/`, `downloading/`, `.tmp/`) — matches are skipped entirely, reason "skip-dir" in status.
- **F-M35 [B1]:** **Skippable strings in filenames:** configurable list of substrings (e.g. `sample`, `trailer`, `incomplete`, `.partial`) — match → skip with reason "skip-pattern". Case-insensitive, simple substrings.
- **F-M36 [B2]:** Both lists maintainable on the config page (one pattern per line, textarea), defaults pre-filled (`incomplete`, `sample`, `trailer`, `partial`, `downloading`).
### 3.11 Architecture Specifications (download-ready, one plugin)
- **F-M37 [B1]:** **Modular layering:** strict separation into (a) SubDL API client, (b) content-hash registry, (c) language mapping/IMDB resolver, (d) upload pipeline, (e) config/status. Only (d) is upload-specific; (a)–(c) and (e) are reusable.
- **F-M38 [B1]:** **Persistent state split by the kind of thing described** (section 3.18). Embedded tracks live under their video file, keyed by media hash + stream position; sidecars are keyed by normalized content hash; the file's own record carries path, IDs, season/episode and the derived language aggregates. Both pipelines read and write the same store.
- **F-M39 [B2]:** **No double work across directions:** every subtitle the system uploads or downloads is registered under its normalized content hash. The upload side asks `IsContentKnown` before uploading and the download side before downloading, so a subtitle that already arrived from either direction is neither fetched nor sent again.
- **F-M40 [B1]:** **DI registration via IPluginServiceRegistrator:** the shared services are registered so the download pipeline obtains them via constructor injection.
- **F-M41 [D, parallel]:** **Download pipeline in the same plugin:** search for missing external subtitles per item (missing languages against a configurable target-language list), download via the same API client, registration in the registry, storage as an external stream next to the media file. Own scheduled task, own switch, own status block.
- **F-M63:** **Official API endpoint:** `https://api.subdl.com` for all API calls (login, search, upload, /me).
### 3.12 Download Pipeline — Matching & Priority Configuration
- **F-M42 [D]:** **Preferred languages:** target-language list (multi-select, no priority). Default `AR, EN, ES, FR, HI, ZH`; empty = download off. `DE` is deliberately absent (uploaded by hand), `RU`/`PT` have thin coverage.
- **F-M42b [D]:** **Hearing-impaired version additionally** (checkbox, default off): when on, the best hearing-impaired candidate per (item, language) is downloaded in addition to the regular version and stored as `<basename>.<lang>.sdh.srt`. It comes from the second search (F-M241), and the branch must sit before the `keepBest` break, or with the default `KeepBestPerLanguage=1` it is unreachable.
- **F-M244 [B1/D] [NOT IMPLEMENTED]:** **The queue item is a complete work order; the pipelines only carry it out.** The seeder decides WHAT is to be done and hands it over in the item; the downloader and the uploader execute that order rather than re-deriving it.
 - A `QueueItem` carries the work it was queued for — for downloads the target languages **and** whether the hearing-impaired variant is wanted (`HiWanted`); for uploads the needed stream positions. The seeder fills these at seed time, from the same evaluation that admitted the item.
 - The download pipeline reads its languages from the item and does not answer the HI question again — that decision is `HiWanted` plus the languages the order names. The upload pipeline likewise consumes the positions it was handed.
 - **Why one decision and not two:** every defect found in the queue seam has the same shape — the seeder and the pipeline evaluated the same question independently and disagreed. The HI branch was unreachable because the pipeline asked its question in only one of two branches; EN was fetched although the file already carried it, because the pipeline re-derived presence from files alone. A single decision removes the whole class: there is no second answer to be wrong.
 - The pipelines keep ONE non-derivation check — the media file's existence (F-M60, its consecutive-failure counter). A file that vanishes between seeding and the run is a fact about the filesystem at execution time, not a work-order decision, and it is reported as a failure rather than silently changing what was asked for.
 - `QueueItem` gains the work fields and they are persisted with it, so a queue that survives a restart still says what to do. A queued item whose order is empty is a contradiction and must not be written.
 - **Not yet implemented** — recorded because the rule is that the seeder owns the decision. The current code still re-derives in the pipelines (the "defense in depth" note in `SubdlSeeder`), which is the deviation this requirement removes.
- **F-M243 [D]:** **The HI variant counts as present whether it is a file or an embedded track.** Both evidence sources answer the same question, and Jellyfin's own `IsHearingImpaired` flag decides a stream — read through ONE detector (`SidecarNaming.IsHearingImpairedStream`) used by uploader and downloader alike.
 - A target language counts as having its HI variant when EITHER `<base>.<lang>.sdh.srt` exists on disk OR the item carries an embedded subtitle stream of that language whose `IsHearingImpaired` is true. Only when both are absent is the language queued for an HI download.
 - **Why it must hold:** the check is asked in three places (seeder queue gate, both pipeline branches) and all three looked at files only. A file whose English lives embedded in the container therefore read as "HI absent", so a download was spent on a variant that was already there. Files whose target language exists only embedded are the normal case, and with `KeepBestPerLanguage = 3` that is up to three wasted downloads per item.
 - The detector reads the flag first and falls back to the stream title (`sdh`, `hearing impaired`) — the same two sources F-M71 uses on the upload side, so both directions agree on what HI means. A title-only rule misses flagged-but-untitled streams; a flag-only rule misses libraries where MediaElch/TinyMediaManager set the title alone.
 - The verdict is stored once and read from there (F-M254). The detector still runs on the upload side, where the stream is in hand; the download side does not re-derive it.
- **F-M254 [D]:** **The HI switch is answered from the registry, not from the streams.** Whether a target language still needs its hearing-impaired variant is read from the stored verdict (`ContentHashRegistry.HearingImpairedLanguages`), which joins the embedded rows the uploader wrote (`MarkEmbed`) and the sidecar rows the downloader wrote (`MarkDownloaded`). Jellyfin's live stream list and the on-disk file names are not consulted.
 - A language counts as having its HI variant when the registry holds a hearing-impaired row for it — embedded or sidecar. Only when no such row exists is it queued. The seeder's queue gate and both download-pipeline branches read the same answer.
 - **Why it must hold:** answering live made the answer depend on what Jellyfin happens to surface. Jellyfin does not expose every stream title the container carries, so a track whose tag reads `CC` can arrive as `Title=null`; the detector then finds no marker, the language reads as "HI absent", and it is downloaded again although the variant is already in the container. The verdict is stored, so it cannot change between runs.
 - One reader: the question was asked in three places, each handing in its own stream snapshot; they now share `HearingImpairedLanguages` and differ only in whether they pass a path or an already-known media hash.
 - The marker list gains `cc`: closed captions serve the same audience as SDH and carry the same non-dialogue cues (`[ BEEPING ]`, `[ GRUNTING ]`, musical notes). Matched on a word boundary (`(?<![a-z])cc(?![a-z])`), never as a substring — `cc` sits inside real language names (`Occitan`), and reading that as hearing-impaired would repeat the `hi`/Hindi mistake.
 - **Known limit:** the marker is read from the title. A track with no title, or with one Jellyfin does not surface, stays `false` until its row is written from another source. Backfilling those rows is a separate decision.
 - **Superseded:** `SidecarNaming.EmbeddedHearingImpairedLanguages` and the `streams` parameter of `MissingHearingImpaired` are removed — with the verdict stored, nothing reads the streams for this question.
- **F-M255 [D]:** **No candidate and no stream is discarded without a line naming it and the reason.**
 - Every exit inside the candidate walk that does not end in a save, and every per-stream exit of the upload collector, writes one line at Verbose (`[SubDL-D] … reject …` / `[SubDL-V] …`) carrying the release or file, the language, and the measured reason. The gates are named individually: download failure (no bytes, too few bytes, with the byte count), language detection, structure (monotonic flag, cue span), cue count, runtime, content-already-known, keep-best stop (with the number of untried lower-ranked candidates), the QA memory filter (with the ids it removed), and the empty HI pool (with its size).
 - **Why it must hold:** the log is the only record of what a run did. Without a line for every exit, "the fetch failed", "a gate rejected it" and "the content was already known" are indistinguishable, and a fetched-and-discarded candidate leaves no trace — so a shrinking candidate list cannot be told apart from a thin SubDL result.
 - The reason carries the measured value, not a verdict: `structure: monotonic=False min=… max=…` and `only N bytes` are diagnosable; "rejected" is not.
 - The level is Verbose, not Normal: these lines are per candidate and per stream. The exits that already carried a counter but no line gained the line; the counters keep their meaning.
 - **Known limit:** the two exits in `CollectItems` that skip a NON-library root child (`child is not CollectionFolder`) stay silent on purpose — they discard a container node, not an item, and one line per run would be noise.
- **F-M256 [D]:** **A registry lookup takes the media PATH and resolves the hash itself.** `HearingImpairedLanguages` receives the media file path, resolves the media hash internally (`GetMediaHash`), then reads the embedded and sidecar rows; no caller passes a hash for this question.
 - **Why it must hold:** the hash and the path are both plain strings, so the compiler cannot tell them apart. Passing the path where a hash was expected compiles and ships, and then every lookup misses: the method returns an empty set for files whose rows exist, so every target language reads as "HI variant absent" and every item is searched again on every run.
 - The resolution lives inside the method, once. This is a signature change, not a caller-side fix: a rule that depends on every caller choosing the right one of two indistinguishable strings has already been broken — the same defect class as the two name parsers (F-M251) and the three HI readers (F-M254).
 - **The negative control is the test.** Assert `HearingImpairedLanguages(path)` finds a stored HI row AND that the same call with the HASH finds nothing; assert the pipeline consequence (with the path only `DE` is missing, with the hash `EN` and `DE` are). A positive-only test passes on the broken build, which is how this shipped — the earlier suite had asserted the broken behaviour as its expected value.
- **F-M257 [D]:** **The embedded area is written by whoever reads the streams, not only by the uploader.**
 - The seeder's scan and the download pipeline record each embedded, non-forced, mappable subtitle track as an observation row (position, language, hearing-impaired) carrying `Status = observed` and no verdict. The uploader keeps writing verdicts (`uploaded`/`rejected`) on the same key, and an observation never overwrites them.
 - **Why it must hold:** with `UploadEnabled` at its default `false` the embedded area stays empty, so every reader of it answers from nothing — and the one reader that depends on it is the HI question (F-M254), which then reports the variant as absent for a track that is right there. The language is queued and an external HI sidecar is fetched for a variant the container already carried, on every run, and no later run can correct it because nothing writes the row while the upload is off.
 - An observation is not a verdict: `observed` is deliberately NOT terminal. `CountKnownPairs` counts only `uploaded`/`rejected`, so the seeder's queue gate cannot mistake "we looked at the stream" for "this pair is settled" — a gate that counted it would silently cancel the uploader's work in the name of recording it.
 - The position is the index into the UNFILTERED subtitle list: ffmpeg's `0:s:N` counts bitmap and forced tracks as well (F-M246), so a position taken from the filtered list names a different stream.
 - Only TEXT subtitle streams are recorded. A bitmap track (`dvdsub`, `pgssub`) carries painted pixels: it cannot be extracted, so it can never be uploaded, and it is not readable for a viewer either — it is not coverage for its language. A file whose target language exists ONLY as a bitmap track reads as having no readable subtitle, so the language stays due and one is fetched. The same rule applies to `EmbeddedPresentLanguages`, the reader that decides what is queued and downloaded at all.
 - One enumeration (`SidecarNaming.EmbeddedTracks`) serves the observers, so the rules cannot drift — the same reason the name parse (F-M239/F-M251) and the HI reader (F-M254) each have one copy.
 - A failure to observe is swallowed and logged at Debug. An observation is an improvement, never a precondition: a scan whose streams cannot be read still queues its items normally.
 - **Known limit:** existing rows are left alone. A track an older build mis-marked as `hi=false` keeps that verdict, because the item is already settled and nothing reopens it. This change records new facts; it does not backfill history. **Test: T74.**
- **F-M258 [D]:** **The database refresh checks the embedded side too, not only the sidecar side.**
 - For every media row whose Jellyfin item still exists and which has stored embedded rows, the refresh reads the item's current streams and forgets every stored row that disagrees — on the key (position) and on the recorded facts (language, hearing-impaired). A row whose position is gone, or whose language/HI no longer matches the stream at that position, is dropped.
 - **Why it must hold:** the refresh has verified the file side of a stored verdict since F-M234. SIDECARS have a file on disk, so `File.Exists` is the evidence; an embedded track has no file, and its evidence is the stream list, which nothing read for this purpose. Without that check a file replaced in place, or streams removed by a re-encode or a language re-tag, leaves rows pointing at positions that no longer exist — and the readers of that area, including the HI question (F-M254) and the observation path (F-M257), answer from tracks that are gone.
 - The check is structural, not judicial: it compares position, language and HI without judging the verdict, so an `uploaded`/`rejected` row is dropped on the same terms as an observation. A row survives while its track survives.
 - Fail-safe, exactly as the rest of the refresh ("unknown ≠ deleted"). An item Jellyfin no longer resolves, an unreadable stream list, and an EMPTY stream list are all skipped rather than judged. The empty case is the dangerous one: treating "Jellyfin cannot probe this item" as "the file has no tracks" would delete every row of a library that is merely offline. Only a NON-empty list that disagrees with a stored row is evidence.
 - The check runs only for files that HAVE stored rows, so it costs one stream lookup per file with state.
 - A check that removes rows also refreshes the media aggregates (`LanguagesAvailable`, `HearingImpairedAvailable`), so the summary cannot keep claiming a language whose only row was just dropped. **Test: T75.**
- **F-M261 [D]:** **An untagged or `und` subtitle track is resolved, and the found language is written back into the container.**
 - A text subtitle track whose tag is absent, empty, `und` or `undefined` is not a fact about its language. The gate extracts those tracks, detects the language offline, records it as an observation and — when enabled — writes it into the container as a real tag.
 - **Why:** neither shape can be mapped. `und` has no entry in `LanguageMapper.Map` (its two-letter fallback invents `UN`) and a NULL tag produces no row, so `EmbeddedPresentLanguages` reports the language as absent for a track that is in the file, and the item is queued and searched for a language it already carries.
 - **It belongs to the SEEDER, before the queue decision.** `IsDownloadTodo` asks `MissingLanguagesOf`, which answers "not present" for an untagged track, so a resolution that has not happened yet cannot change that answer. A pipeline-only gate is too late.
 - **The sequence is forced:** find the untagged text tracks from the stream list (no ffmpeg call when there are none) → one ffmpeg pass for all of them (F-M5) → detect offline with the 2 KB floor (F-M74) → write the codes into the container → move the file's registry state to the new hash → record the tracks. The queue decision then reads the corrected language.
 - **The registry move exists because the rewrite changes the file's IDENTITY** (the OSHash covers size plus the first and last 64 KB, and a Matroska segment header carries its own size). `ReplaceMediaIdentity(oldHash, newHash)` is a rename, not a re-decision: marks, ids, language aggregates, embed rows (rebuilt under `"<hash>|<pos>"`) and the parents of the sidecars travel. Where both sides hold a row the OLD one wins; an equal pair is a no-op and an empty hash is refused.
 - **The gate reads and returns the hash pair** (`LanguageTagGate` holds the registry); the caller moves only a COMPLETE pair. The gate stays a file-level component.
 - **The tracks are recorded from the gate's own verdict**, not through `ObserveEmbeddedFacts`: Jellyfin caches its stream list, so the tags just written still read as "none" for the rest of the scan.
 - **The position rule:** a track's position is `0:s:N` over TEXT-eligible subtitle streams only (subtitle streams, not external, not forced, not bitmap), in container order. Video and audio never enter the count; bitmap and forced tracks DO occupy a position and stay in it, or every track after one would shift; the tag goes back to the position it came from. The gate filters to subtitle streams itself, so no caller can pass the wrong shape. External streams are skipped, not counted — ffmpeg only sees container streams.
 - **What the detector cannot decide stays without a row on purpose** (below the 2 KB floor, no text, no confident verdict). A wrong language is worse than none.
 - **The resolution counts as PRESENT for the coverage check in the same run**, because Jellyfin's cached list still reports the old tag for a container that was just corrected.
 - **The write is a stream copy (`-c copy`), never a re-encode**, and the original is replaced only after the result was read back and found to carry the wanted tag. `mkvpropedit` was rejected (native, architecture-bound, on neither target); ffmpeg is already required.
 - The result is read back out of the file across the stream shapes that exist (audio in front, interleaved, bitmap tracks between, forced tracks between): every corrected track carries the wanted language and none is misassigned. Only files carrying an untagged track are touched, and each once. **Test: T79.**
- **F-M262:** **A rewritten container is reported at NORMAL — one line per file naming which languages were written; the per-track detail stays at Verbose.**
 - The gate logged through `LogUtil.PerItem` (Verbose and up) and `WriteLanguageTagsAsync` logged nothing on success, so at the default `Normal` a rewrite of a media file left no trace at all. A pass that EDITS the user's media must be visible at the level every install runs at.
 - One Normal line names the file, how many codes were written, which languages (distinct ISO codes, position order) and — when the identity moved — the old and new hash. Per-track positions and byte counts stay at Verbose. The seeder's identity line carries only what only the seeder knows, so the two do not repeat each other. **Test: T80.**
- **F-M263:** **A dry run suppresses the container rewrite — for BOTH directions — and the seeder is the only caller of the language gate.**
 - With `DryRun` (upload) OR `DownloadDryRun` (download) armed, the gate still resolves untagged tracks and reports them but writes nothing into the media file. Detection is not suppressed: a dry run's value is answering what it WOULD do (F-M22).
 - **Why ONE rule for BOTH switches:** the write runs from the SEEDER, which belongs to no direction — tying it to one switch would leave the other dry run rewriting the user's library.
 - The seeder's scan is the only entry point: every path — scheduled task, arrival, follow-up, manual — goes through `SeedAndMaybeRunAsync`, which seeds first and then calls `RunDirectionAsync`; the pipeline holds no gate call of its own. It would need the registry (without one, a write leaves two identities and the download mark lands on the dead one) and it would run ahead of the first `DownloadDryRun` check.
 - `MissingLanguages` reads `ContentHashRegistry.EmbeddedLanguages(mediaPath)` — the rows the seeder wrote — instead of the pipeline's in-memory field. That source is more accurate: Jellyfin caches its stream list, so a corrected container still reports its OLD tag through `EmbeddedPresentLanguages`, while the registry row is current. The hash is resolved from the path inside the method (F-M256). **Test: T81.**
- **F-M264:** **A media file is rewritten at most once — a track that already carries a tag in the container is never written again.**
 - Within ONE cycle the DOWNLOAD-seed pass writes the codes and the UPLOAD-seed pass that follows finds the same tracks untagged again, because it reads a stale stream list. Both passes write.
 - The second pass cannot see the first one's work: it asks Jellyfin, and Jellyfin caches its stream list, so a corrected container keeps reporting its old tag. No registry read and no self-observation of a freshly written tag can fix a source that is stale by construction.
 - Before the extraction pass, read the container's ACTUAL per-subtitle tags (`FfmpegTools.ReadSubtitleTagsAsync`, one ffprobe call, no remux) and drop every pending position that already carries a mappable tag. Those positions are recorded as ordinary tracks instead, so the registry and the queue decision still see the real language. When nothing remains pending, the run returns with `Written == 0` and logs `N track(s) already carry a language tag in the container; nothing to write` at Normal.
 - The container is the right authority: the tag it reports is the one `WriteLanguageTagsAsync` verified before moving the temp file over the original, so a track seen as tagged here is tagged on disk. An untagged track stays pending in any later run, so this cannot mask a failed write.
 - **Cost of not holding:** ffmpeg cannot edit a Matroska container in place, so every tag write is a full remux — a second copy of the media file, a second identity change with its own `ReplaceMediaIdentity` bookkeeping, and a second ownership flip. `mkvpropedit` would edit in place, but it is a native, architecture-bound binary and is not available.
 - The switch `AllocateMissingLanguageCodes` sits on the **General** tab under `Media files`, directly above `Statistics`. **Test: T82.**
- **F-M265:** **The LAST run of each worker is stored in the database and shown in a "Workers" section at the bottom of the configuration page — one line per worker with the time of its last run and how it ended.** Deliberately the last run only, NOT a history: a history would need a prune path and a cap.
 - **What it replaces:** the postprocessing status lived in `UploadPipeline` static fields, so every Jellyfin restart reset it to `"never run"` — the endpoint reported a task as never-executed minutes after it had run.
 - **Storage:** area 6, collection `worker_runs`, keyed by the worker's own task key (`WorkerRunEntity.Id`), one row per worker. A new run OVERWRITES its row, so the area can never grow and needs no retention policy. Written through `Registry/WorkerRunRegistry` (`Start`/`Finish`/`List`), reached via `Plugin.WorkerRuns`.
 - **The six workers:** seeder, download, upload, postprocessing, database refresh, OSHash refresh. `KnownWorkers` is the canonical list and `List` MERGES it with the stored rows, so a worker that has never run still appears; a stored row whose key is no longer a worker this build runs is dropped rather than shown as a ghost. **The seeder is NOT a Jellyfin scheduled task** — it is the dispatcher's own scan step, so the task manager cannot enumerate it. It carries the key `SubDLSeeder` and gets a row anyway, because it is the longest and most substantive part of a cycle: a full scan runs for the better part of an hour while the GUI shows the wait-only upload task as finished. Because it is not a task, the waiting download/upload rows report the CYCLE's fate, not their own wait: a direction that sat in an idle wait while the seeder was still scanning, or that was stopped by the quota, must not read `ok` (F-M267).
 - **Six outcomes**, each mapped to a colour and a word in the GUI: `ok`, `failed`, `cancelled`, `skipped` (a scan that found nothing to do), `deferred` (nothing broken, the work was pushed forward: run lock busy, quota, user stop) and `never`, plus `running` while a cycle is still working at the wait cap. Colour rule: F-M268. A `skipped` run still writes its row — "the task was not allowed to run" is information, and without it a disabled direction looks identical to a broken one.
 - **A worker that has never run shows NO date.** The first build defaulted `Started` to `DateTime.UtcNow`, so the section printed a fresh timestamp next to `never run`, which reads as if the worker had just executed. The field is `DateTime?` and stays null; the GUI renders `never`.
 - **The dry-run note is CONDITIONAL**: appended to the line only while the direction's dry-run flag is on, e.g. `cycle finished — dry run, nothing written` (download) / `— dry run, nothing uploaded` (upload). With the flag off the line stays clean. A dry run's log numbers are hypothetical, and a reader who cannot see the flag would take the run for a real one.
 - **Endpoint:** `GET /Plugins/SubdlSync/WorkerRuns` → `{ Workers: [{Id, Name, Started, Ended, Outcome, Detail}], Timestamp }`, read by `#WorkerRunList` / `#WorkersLine` in `configPage.html` AND `configPage.js` (both copies carry the script). **Test: T83.**
- **F-M260 [D]:** **The downloader reads the hearing-impaired flag of the file it actually fetched.** When a candidate resolves to one file inside a season or range pack (`FindUnpackFile`), that file's own `hi` flag is the truth for naming and registration; for a plain single-file release the candidate's flag is, because the candidate *is* the file.
 - **Why it must hold:** a pack's header flag says nothing about its contents — a pack may declare `hi=false` while every file inside is hearing impaired. Reading the header alone saves an HI file as `<base>.<lang>.srt` and records it with `hi=false`, so it never counts as hearing impaired again: not for `HearingImpairedLanguages` (F-M254), not for the refresh (F-M258), not for `SidecarNaming.List`. The item stays due for an HI download on every run while the variant sits on disk.
 - The name is composed by `SidecarNaming.Build`, in the same class as `Parse` and `List` — a writer that composes where the reader parses cannot drift from it. No caller composes a name inline; the dry-run preview and the HI concatenation go through the same builder.
 - The slot and the marker combine: `<base>.<lang>.sdh.2.srt` is slot 2 of the HI variant. Because `Build` writes that shape, `Parse` MUST accept it, and `List` therefore sees it as a hearing-impaired sidecar of that language.
 - The HI block of the download loop is guarded by the *effective* flag, not the candidate's: when the file just saved already was the HI variant, no second download follows.
 - The dry run reports the name and marker it WOULD write, HI marker included.
 - **Known limit:** only new writes change. Sidecars already written as `.srt` keep that name. A pack's file list deliberately does NOT feed the HI *search* — the HI pool carries usable entries for nearly every episode on its own. **Test: T77.**
- **F-M259 [D]:** **The loose .srt files get the same writer the embedded tracks got — the scan.**
 - The seeder's scan records every loose subtitle file beside the media as an observation row, keyed by the normalized content hash (the sidecar's identity) with its language and HI flag. `Status = observed`, no verdict; an existing verdict is never overwritten.
 - **Why it must hold:** `MarkSidecar` had exactly two writers — the upload and download pipelines — and each sits behind its own switch, with upload off by default. A `.srt` that no plugin run ever moved therefore had no row: written by another tool (MediaElch, TinyMediaManager), kept from before the registry existed, or never touched because the uploader is off. F-M257 fixed this for embedded tracks and left the sidecar half open.
 - **The two readers disagree, which is what makes it visible:** `DownloadPipeline.MissingLanguages` reads the DISK (`SidecarNaming.List`) and sees the language as present, while the HI question reads the REGISTRY (F-M254) and sees the variant as absent. The item is queued for an HI download on every run and the run can never settle it.
 - Content is the key, not the path, and the hash uses the uploader's own function (`ContentHashRegistry.ComputeHash`), so a row observed here is the row the uploader would find. Two sidecars with the same language but different text stay two rows.
 - The reader is `SidecarNaming.List` via `UploadPipeline.FindLooseSrts`, NOT the seeder's own private copy — that one returns bare paths and knows no language or HI marker. A fifth name parse would repeat the drift F-M239 removed.
 - An observation is NOT knowledge: `IsContentKnown` answers only from verdict rows. Counting observations would make the downloader skip a write it never performed. A failure to observe is swallowed and logged at Debug. **Test: T76.**
- **F-M246:** **A forced subtitle track does not make its language present — a hearing-impaired track does.**
 - When the download side asks which target languages are covered (`DownloadOnlyMissing`), an embedded subtitle stream counts as evidence only when `MediaStream.IsForced` is NOT true. A forced track carries only the lines of foreign-language scenes, so counting it as coverage leaves the language without a real subtitle and the item marked complete.
 - A hearing-impaired track DOES count: SDH is the same dialogue with annotations. A bitmap track does NOT (F-M257) — painted pixels, nothing to read. The rule is therefore "any non-forced TEXT subtitle stream", and the HI switch is answered separately from the registry (F-M254).
 - **Why it must hold:** the check is asked twice — the seeder's queue gate and the pipeline's missing-language check — and both walked the streams with their own copy of the loop, neither asking `IsForced`. An item whose target language exists ONLY as a forced track was logged as `FILE COMPLETE … all target languages settled`, so the language was never downloaded.
 - One reader, for the same reason the name parse has one: the rule lives in `SidecarNaming.EmbeddedPresentLanguages`. The seeder's answer decides whether the pipeline ever sees the item, so the two callers must not disagree.
 - The upload side follows the same rule: a forced track is removed from the upload set, read through ONE predicate `SidecarNaming.IsForcedStream` used by the pipeline's collector AND the seeder's `IsUploadTodo` prefilter — otherwise the prefilter keeps queueing items whose every track the run then discards.
 - **The position invariant that survives the filter:** `subPos` is the ffmpeg map index (`0:s:N`) and MUST be computed against the UNFILTERED stream list, because ffmpeg counts every subtitle stream, forced and bitmap included. Filtering must never shift an index; T64 asserts the mapping explicitly (`0:s:0`, `0:s:2`, `0:s:6` for a file whose forced tracks sit at 1, 3 and 5). **Test: T64.**
- **F-M242 [D]:** **"Best subtitles to keep per language" saves exactly that many numbered files.** With `KeepBestPerLanguage = X` the pipeline saves the top X QA-passed candidates per (item, language): slot 1 is `<basename>.<lang>.srt`, slots 2..X are `<basename>.<lang>.2.srt`, `.<lang>.3.srt`, … Fewer usable candidates than X saves fewer files, never an error.
 - The ONLY exit from the candidate loop is `savedCount >= keepBest`. An unconditional `break` after the first save made the setting inert — the numbering code was dead and every value of X produced one file. `KeepBestPerLanguage = 1` (the default) is unchanged.
 - Every saved slot costs download quota, which is why the GUI caps X at 10.
 - The dry run names the files it would write (`DRY-RUN slot 2/3 … → <name>.en.2.srt`), so the setting is verifiable without spending quota.
- **F-M239 [B1/D2]:** **One reader for sidecar file names.** The name→(language, hearing-impaired) rule exists ONCE (`Registry/SidecarNaming`); the uploader, the pipeline's missing-language check and the database refresh all call it. Marker is `sdh` only — never `hi` (F-M48). Recognized shapes: `<base>.srt` (unlabeled = EN), `<base>.<lang>.srt`, `<base>.<lang>.sdh.srt`, and the numbered slots `<base>.<lang>.<n>.srt` the downloader writes. `.part` is never a subtitle.
 - **Why:** three copies of the rule had drifted, and two did not know the marker. `MapToSubdl` maps an unknown three-letter tag to its first two letters, so the refresh read `Movie.de.sdh.srt` as the language **"SD"** — a language that does not exist — while `DE` looked absent. `FindStaleDownloadedLanguages` then declared the download mark stale and the item was refetched on every run.
 - A marker is consumed as a marker and the language token is read from the position BEFORE it; a marker must never reach `MapToSubdl`. A name whose marker has no resolvable language token yields nothing.
- **F-M240 [B1]:** **The hearing-impaired switch is answered against the disk, not against the mark.** The download mark is keyed by language, so a file that already carries its subtitles is "complete" the moment the switch is turned on — and the HI variant is never fetched. While the switch is on, a target language whose `<base>.<lang>.sdh.srt` is absent counts as stale, which invalidates the mark and lets the same run deliver the variant.
 - A language already settled-as-unavailable (QA-exhausted) does not count as stale, so an item with no HI release on SubDL is not reworked forever.
 - Disk evidence and not a stored flag, because it is self-correcting: deleting the `.sdh.srt` makes the item due again, and turning the switch off needs no bookkeeping.
- **F-M241 [D]:** **Two searches, one per side of the hearing-impaired split.** The regular slot is filled from a `&hi=0` search and the HI slot from a `&hi=1` search; the HI search runs only while the switch is on, so a user who does not want HI pays one search exactly as before.
 - SubDL filters HI server-side and the two pools do not overlap — a release appears in one or the other, never both. An unfiltered response is a MIXTURE, and the regular ranking would silently depend on how many HI releases it happened to contain.
 - A failed HI search keeps the regular candidates and logs it — the HI variant is a bonus (F-M42b), the regular subtitle is the target.
 - The HI branch sits BEFORE the `keepBest` break. Behind it, with the default `KeepBestPerLanguage=1`, it was unreachable and no HI variant was ever fetched.
 - A dry run reports the HI pick from the HI pool, because the real selection happens after the file download, which a dry run never reaches.
- **F-M43 [D]:** **Runtime/FPS match with tolerance:**
 - **Stage 1 — pre-download (FPS):** SubDL provides `framerate`/`fps` per candidate. If set: difference > ±1 % vs. item FPS → candidate rejected. Missing → criterion skipped, no hard fail.
 - **Stage 2 — post-download (structure + runtime):** corruption check on the downloaded bytes (cue timings present, monotonically increasing, plausible durations), then runtime check of SRT cue span vs. item `RunTimeTicks`, default tolerance ±600 s. Outside → discard. Missing runtime metadata → criterion deactivated.
- **F-M44 [D]:** **Release match:** candidate release name scored against the local filename: release-group match > token overlap > download-count tie-breaker. Weights configurable (expert mode).
- **F-M45 [D]:** **IMDB/TMDB match** (default on, switchable off): candidates matched against item IDs. Default is a hard criterion (no ID → no download); switchable off for title-based fallback. **F-M151b:** the download ID quality gate validates/corrects JF IDs via TMDb before search, default ON.
- **F-M46 [D]:** **Overall selection:** exactly one best candidate per (item, language) by combined score from F-M43–F-M45. No candidate passing → the language counts as "not available".
- **F-M47 [D]:** **Configurable refetch interval:** Manual / Weekly / Monthly / Quarterly. **Default: Weekly.** The per-file last-search stamp (`MediaEntity.LastSearchUtc` + `LastSearchLanguages`) protects already-downloaded languages and controls re-search. `DownloadRefetchInterval` is **obsolete since F-M111** — the unified `RefetchInterval` governs both directions; the old property is kept only for XML compatibility.
- **F-M49 [D]:** **Daily-limit resume per direction:** two independent checkboxes, "Continue after daily limit" (Download) and "Continue after daily API limit" (Upload). **Both default ON.** ON → wait once until reset (max 24 h) and retry; OFF → clean stop.
- **F-M50 [D]:** **Download budget per (item, language):** max N candidate downloads before the language counts as "not available" (default 3, 0 = unlimited).
- **F-M215 [D]:** **A season or range pack is resolved to the episode it belongs to — never saved whole.** A pack must yield exactly one subtitle file per episode, chosen from the pack's own listing:
 - The search requests the unpacked file list (`unpack=1`); `SubtitleCandidate` parses the resulting `unpack_files` array (`name`, `season`, `episode`, `md5`, ready single-file url). The parameter is a **GET `/subtitles/search` parameter only** — sending it on `files/search` answers `Invalid request parameters`.
 - `DownloadCandidateAsync` picks the entry matching the **current season/episode** and downloads that single file.
 - **The ZIP fallback matches the entry NAME** (`S01E06`, `s01.e06`, `1x06`, SubDL's `S0106`). A multi-file archive whose entry cannot be resolved returns **null** instead of guessing — writing "the first `.srt` in the archive" next to every episode of the season is the defect this rule forbids.
 - A pack with no entry for this episode is **skipped**, not saved wrong. Non-pack paths keep their existing behaviour.
- **F-M217 [D]:** **For a download the FILE NAME decides type, title and episode — not the Jellyfin library.** Jellyfin types an episode living in a library declared as *movies* as a `Movie`, and its item NAME is the raw file name (`Reacher.S03E01`), which resolves against nothing. Three consequences:
 - **The seeder prefilter must not drop such an item:** the id gate may not depend on a lookup that resolves the item's name. An item that cannot be resolved by name still has to reach the queue.
 - **The search query is the PARSED title** (`MediaNameParser`) — `Reacher.S03E01` returns 0 hits against the type-neutral `search/multi`, `Reacher` returns the show.
 - **Season and episode come from the file name too.** For a `Movie`-typed item Jellyfin reports 0/0, so the F-M215 pack guard (`episode > 0 || season > 0`) could never fire.
 - **A year-filtered search retries once without the year.** Jellyfin's `ProductionYear` is frequently the IMPORT year (a 2022 show carrying 2025): the filtered query returns 0 hits where the unfiltered one finds the title.
- **F-M266:** **The registry sweep removes OBSERVATIONS only — a VERDICT and a detection-attempt record are out of its reach.**
 - In `ContentHashRegistry.ForgetStaleEmbeds` the comparison between a stored row and the caller's stream list is skipped for every row whose status is `uploaded` or `rejected`, and for every row carrying a `DetectionAttemptedAt` stamp. Only the remaining rows are compared, by position, language and HI flag.
 - **Why it must hold:** an untagged or `und` track is invisible to a stream list BY CONSTRUCTION — the shared reader `SidecarNaming.EmbeddedTracks` drops every position whose tag does not map — so a row for such a track looked stale on EVERY run and was deleted each time. That destroyed the uploader's own verdict (`rejected / und-too-small`, stored with `Language="UN"`) and the record that detection had already been attempted for that position.
 - **The consequence of getting it wrong:** a never-resolving track is re-opened and re-run through detection on every scan, and a rejected subtitle loses its verdict and is offered for upload again. **Test: T84.**
- **F-M267:** **The waiting download/upload rows report the CYCLE's fate, not their own wait.**
 - `WorkerRunRegistry.DescribeCycle(cycleFinished, seederOutcome, seederDetail, directionOutcome, directionDetail)` decides the row of a wait-only task, with a strict ranking: (1) cycle not finished at the wait cap → `running` ("cycle still running at the wait cap"); (2) a `failed` direction or seeder → `failed`; (3) a `deferred`/`cancelled` direction, then a `deferred`/`cancelled` seeder → yellow; (4) a `skipped` direction, then a `skipped` seeder → grey; (5) otherwise → `ok`, carrying the seeder's numbers when it reported any, else "cycle finished".
 - **Why red ranks first:** a cycle that threw did not do its work either, so a green or yellow light would bury it.
 - **Why the direction's fate outranks the seeder's:** the seeder can have scanned fine while the direction it fed was stopped by the quota — ranking it below would repaint exactly that case green.
 - Reporting the task's own "ok" is wrong twice over: it claims success when the wait cap expires while the seeder is still scanning, and it hides a quota stop behind a green light. `Fallback` substitutes "not recorded" so a row cannot show a bare outcome word. **Test: T85.**
- **F-M268:** **One colour rule for every worker: green = the work ran and ended without an exception, yellow = the work did not happen but nothing is broken, red = something is broken, grey = deliberately not run.**
 - `ok` → green; `deferred` and `cancelled` → yellow (quota, run-lock deferral, user stop); `failed` → red (exception, failed cycle, unreachable core); `skipped` and `never` → grey (disabled, never run, or a scan that found nothing to do).
 - **Why grey is not green:** "the task was not allowed to run" and "the scan found nothing" are both information, and without a distinct colour a disabled direction is indistinguishable from a working one. **Test: T85.**
- **F-M269:** **The database refresh's detail line names the compaction fallback.**
 - `SubdlDatabaseRefreshTask.BuildRefreshDetail` (static and pure, so the wording is testable without a Jellyfin host) appends a compaction note to the body with ` | `, e.g. `removed 33 dead state, forgot 0 stale row(s), dropped 450 mark(s) | compaction failed — rebuilt from own rows (12419072 -> 8249344 bytes)`.
 - **This is a NOTE, not a red light:** the refresh did its work and the store came back usable, so the outcome stays `ok`. The line carries the note precisely so the fallback is visible; with no compaction the line stays clean, so a note cannot be mistaken for the normal case. The LiteDB compaction failure itself is deliberately NOT to be solved; the rebuild is the accepted answer. **Test: T86.**
### 3.13 Scheduler, Firing & Catch-up
- **F-M51:** **Per-installation random schedule anchors:** all scheduled fires come from a background coordinator (30-s tick). Daily/weekly/monthly/quarterly anchors are diced once per installation and persisted in config. No default fixed-time triggers. `OnArrival` / `Manual` modes disable scheduled fires.
- **F-M55:** **Download-on-arrival as its own switch** + UI restructure: "Download subtitles on arrival" checkbox (Download tab), independent of the upload arrival setting. Both directions share the same diced anchors/jitter.
- **F-M57:** **Symmetric per-direction schedule config:** Upload: "Upload subtitles on arrival" checkbox + "Upload schedule" dropdown. Download: "Download subtitles on arrival" checkbox + "Refetch interval" dropdown. Both share the same anchors/jitter; Manual disables scheduled fires for that direction.
- **F-M156:** **One-shot global catch-up for missed refetch windows:** if any scheduled anchor window passes unhandled (server down, restart, lock busy), the scheduler queues **exactly one** catch-up run. Multiple missed slots do **not** stack. The catch-up state resets when the next regular anchor fire runs.
- **F-M65:** **One-shot night recovery fire per direction:** a run stopped on the daily limit schedules one re-fire after the quota reset plus a random 30–300 min jitter (away from the 00:00 UTC herd), diced freshly per fire by cryptographic RNG — see F-M182.
- **F-M182:** **Jittered recovery fire after the daily limit:** when a pipeline stops on the daily quota, the direction is re-fired once after the server-reported reset plus a random 30–300 minutes. The offset is diced freshly per fire (cryptographic RNG) and rolled independently per direction, so the retry does not land on the 00:00 UTC reset moment every API consumer hits. The jitter applies to the **quota-anchor path only**; fires carrying their own offset (run-lock retry, hourly-cap roll-over) keep their exact time. Log lines name the reset anchor, the resulting fire time in the local zone, and the jitter window applied.
- **F-M116:** **Recovery fires persisted:** the next scheduled download/upload fire times are persisted to disk and restored on restart, so missed windows are eventually caught.
- **F-M210:** **Every scheduled job is driven by its OWN setting.** Database refresh, OSHash refresh and upload postprocessing each carry their own cadence field and their own diced anchor, and must fire on them regardless of any other job's setting. `RefetchInterval` governs **only** the automatic pipeline cycles; `Manual` and `OnArrival` there suppress those cycles and nothing else. A job must never sit behind an early return belonging to a different job's configuration.
- **F-M210a:** **A service with no manual start button offers "Never"/"off", never "Manual".** `Manual` means "triggered by the dashboard button"; where no such control exists, the disabling option is `Never` (prune, OSHash, postprocessing).
- **F-M211:** **The shared database context is created under a lock.** Concurrent first access by two jobs firing in the same tick must yield exactly one context; constructing two over the same data file races LiteDB's non-thread-safe `BsonMapper` and kills one task.
- **F-M212:** **No fire may be consumed before its task is registered.** `ITaskManager.QueueScheduledTask` silently drops the fire (logging `Unable to find scheduled task of type "X"`) when the target task is not yet registered, which is the normal state during early startup. Every fire path must therefore test `IsTaskRegistered<T>` **before** it consumes its slot (no marker set, no reschedule counter reset), so the next 30-s tick retries and the work is not lost for the day. This applies to **all six** paths: database refresh, OSHash refresh, postprocessing, the refetch cycle, the F-M156 catch-up and the F-M65 recovery fires. A guard placed after the marker is consumed is a silent data-loss bug. **Test: T31.**
- **F-M248:** **The scheduler's whole due-state is persisted, and a missed anchor slot is caught up instead of waiting for the next window.**
 - Every dedup marker, the catch-up flag and the lock-busy deferrals survive a restart. A slot that already fired stays consumed; a slot whose window was missed fires on the first tick where it is past-due and unconsumed. No fire carries a time window.
 - **Why the state must be on disk:** every due-test in the coordinator is answered against a RAM field (`_lastXMarker != marker`, `!_catchUpFired`). After a restart those are null, so `null != today` re-claims a slot that has already run. The database refresh carries the same shape on its own anchor day, and so do the refetch slot (`_catchUpFired`, `_lastFiredMarker` — F-M156's catch-up replayed after every restart) and postprocessing (minute-granular marker, so it re-claims far more often).
 - **What is persisted:** one file `scheduler-state.json` in the configuration directory, holding the four markers (`refresh`, `oshash`, `postprocess`, `fired`), the `catchup` flag and the three deferral instants (`refreshDefer`, `oshashDefer`, `postprocessDefer`, round-trip `O` format, `DateTime.MinValue` when none is pending). Written at most once per tick and only when a field changed.
 - The marker counts the CLAIM, not the outcome: a run that fails after being queued stays consumed for the day, so persistence cannot turn a failure into an infinite retry.
 - **No fire window.** The refetch slot carried `if (now > fire.Effective.AddSeconds(2 * TickSeconds)) continue;` — a 60-s window that made a missed anchor wait for the NEXT regular window, contradicting F-M156. It is removed: a past-due, unconsumed slot fires on the next tick, and stacking is prevented by the persisted marker.
 - **Deliberately unchanged:** the deferrals keep their semantics (lock-busy → back off `JobSpacingMinutes`, slot stays claimable), the reschedule budget stays per-day in RAM (a safety valve, not a due-state), and recovery fires keep their own file (F-M116) because they are consumed on fire rather than keyed by day. **Tests: T66, T67.**
### 3.14 Run Behaviour, Limits & Lifecycle
- **F-M54:** **Reaction matrix per server response:** 403 auth → immediate stop; 429 → classified by variant (F-M238) and decided against the live counters — a spent allowance follows F-M49/F-M182 (wait-until-reset or clean stop per the direction's setting), a short-term `service_busy`/`rate_limit` trip is respaced by `JobSpacingMinutes`; 5xx → retry with backoff; 200 + `status:false` → warn, fail-open for searches.
- **F-M58:** **Transient-overload 429 classification:** `service_busy` 429 with `retryAfterSeconds` → retry loop (max 3×), run continues; login hardening for non-JSON 429 responses.
- **F-M62:** **429 classification fix:** a 429 carrying no rate headers and naming neither `service_busy` nor `rate_limit` is treated as the conservative fallback (server-level 429, next-midnight anchor), not as the daily allowance — a 429 whose kind cannot be named must never be guessed in the direction that discards a day of work. The real daily allowance carries a reset signal.
- **F-M59:** **LIFO queue order:** both pipelines process items by `DateCreated` descending — newest first. The id-order partition keeps id-resolvable items before the id-less backlog.
- **F-M60:** **File-missing retries before permanent skip:** persistent counter per item (shared by both pipelines). Each failed file access bumps it, success resets it. At the configurable threshold (default 3, 0 = never) the item is skipped as "file-missing (retries exhausted)".
- **F-M64:** **Target-language change needs no reset pass:** each file stores the language list it was last searched under plus the timestamp (`MediaEntity.LastSearchLanguages`). `IsDue` compares that stored list against the current configuration, so a changed list simply makes affected files due again — no global reset run and no second bookkeeping row. Items already holding all new languages still skip without API calls.
- **F-M111:** **Queue-driven operation:** both pipelines run only over items the seeder placed in the in-memory queue. Runs are atomic per direction and serialized by a global run lock.
- **F-M131:** **Manual stop via marker files:** the Stop button creates `.stop-upload` and/or `.stop-download` in the plugin data directory. Each pipeline checks its marker before processing the next item (and, for uploads, between streams of the same item), cancels the direction, deletes the marker and reports `StopRequested`. The dispatcher ends the cycle without starting further directions. Stop markers do **not** affect the delayed postprocessing task. The canonical endpoint for programmatic stops is `POST /Plugins/SubdlSync/Stop?direction=upload|download|all`; `DELETE /ScheduledTasks/Running/{id}` cancels the Jellyfin task wrapper, but a running pipeline item may finish first.
- **F-M177:** **Conditional follow-up reseed:** after the first seed/download/upload round of a cycle, a follow-up reseed runs exactly once — and only if new library arrivals were collected while a seed, download or upload was already running. Gated by `FollowUpRoundsDownload` and `FollowUpRoundsUpload`; if both are off no reseed runs, otherwise the forced scan seeds the pending arrivals and, if it adds new work, download runs before upload.
### 3.15 Upload Postprocessing
- **F-M17y:** **Delayed upload postprocessing:** after an upload run (normal finish or stop), on the postprocessing schedule (F-M176; not tied to the run and not to a fixed delay — SubDL review latency varies), the plugin queries `/user/mySubtitles` and resolves every locally pending-review entry into its final verdict: `accepted` → approved; `rejected` with "Duplicate upload" → deleted on SubDL + marked duplicate-remote; other rejects → marked upload-rejected. All steps logged at Debug. The task is scheduled by the dispatcher so it also runs after a stopped upload.
- **F-M176:** **Postprocessing reschedule spacing:** if postprocessing cannot start because the global run lock is busy (F-M94h: immediate `false`, no waiting) or it hits the hourly rate limit, it schedules a one-shot re-fire in `JobSpacingMinutes` (5–120 min). The re-fire still respects the diced anchor and does not move the next regular run. A busy lock is first checked for staleness; only a genuinely living previous run causes a deferral.
- **F-M193 [B1]:** **`/user/mySubtitles` is NOT paginated — the counters must count DISTINCT upload ids.** The endpoint ignores `page`, `per_page`, `offset`, `limit` and `start`: every value returns the byte-identical complete list. `ListMySubtitlesAsync` must therefore deduplicate by `UploadId` and break on the first page that adds no new id, while rows with `UploadId <= 0` are kept unconditionally so a parser regression cannot silently drop data. `CountMySubtitles` counts distinct ids and additionally reports `distinctUploadIds` and `paginationUnsupported`; the status line must not claim "in N pages".
### 3.16 Shared State, Locks & Maintenance
- **F-M94h:** **ONE global run lock for all six state-mutating components** (seeder, downloader, uploader, postprocessing, database refresh, OSHash refresh) — they all touch the same LiteDB state, so a single mutual exclusion is what the design needs. The lock is a block file holding `PID|UTC`; **overlap is never waited out.** A caller that cannot acquire gets `false` immediately (only a 20-s in-process hand-off grace) and **reschedules itself by `JobSpacingMinutes`** via the coordinator's `Schedule*Fire`/`ScheduleRecoveryFireAt`. No poll loop.
 - **Stale detection:** dead holder PID → take over immediately; holder alive but stamp older than the 6-h run ceiling → wedged run, take over; file older than 24 h → take over. `ClearOnStartup` deletes a leftover block file at plugin start. Fail-open: a malformed block file never wedges the plugin.
 - **Why one lock:** the redundant in-process semaphores (`_uploadWorkLock`, `_postprocessingLock` with its own duplicate stale logic) and the dispatcher's `_seedLock` guarded nothing the global lock did not cover, and `_uploadWorkLock.WaitAsync` sat outside its `try`, so a cancellation between the two acquires leaked the run lock.
- **F-M204:** **A running cycle is never widened and a trigger is never merged into it.** Any overlap between scheduled upload and download is answered by a **reschedule**: `ScheduleRecoveryFireAt(direction, now + JobSpacingMinutes)` for the direction not covered by the running cycle; the dispatcher logs `rescheduled +N min — cycle already running` and returns `false`. When the fire comes due, the coordinator's tick re-checks `PipelineRunLock.IsFree` and defers again if still busy. The per-direction latch exists for the fresh-cycle case only.
 - **Why:** the old merge returned "merged into running cycle", so the other direction's run never happened, and because the merge sat above the global run lock the lock's busy path was never reached. **Test: T23.**
- **F-M205:** **Every reschedule is counted; after 16 the rescheduling stops.** `TryCountReschedule(slot, reason)` keeps one counter per slot (`upload`, `download`, `postprocess`, `dbrefresh`, `oshash`, `refetch`) and returns `false` once the slot has been rescheduled `MaxRescheduleAttempts` times. **The limit is 16** — a single constant; every log line renders `{Limit}`, so raising it touches no message text.
 - The count happens in the **public entry points** — `ScheduleRecoveryFireAt` (lock-busy, hourly-cap roll-over, rate-limit respacing), `ScheduleOverloadFire`, `SchedulePostprocessFire`, `ScheduleRefreshFire`, `ScheduleOshashFire`, plus the coordinator's own anchor defers — **before** the F-M65 duplicate check, so repeated triggers consume budget rather than being silently swallowed.
 - On refusal the slot's pending fire is dropped (recovery fires) or the defer is skipped (anchor fires) and the slot falls back to its next **regular** anchor; `DeferFire` additionally clears the pending recovery fire.
 - Giving up logs a **warning** exactly once (`attempt == MaxRescheduleAttempts + 1`); further refusals log at debug, so a repeatedly-triggered slot cannot flood the log.
 - The counter is cleared by `ResetReschedule(slot)` on a real fire and by the per-day budget reset (F-M208). It lives in RAM only — a restart resets it, which is the intended fail-open.
 - **Not counted:** daily-limit quota-reset fires (`ScheduleRecoveryFire`) — they are driven by the reset, and dropping them would skip the direction outright. **Test: T24.**
- **F-M206:** **A respacing log line must not claim a quota reset.** A fire carrying an exact, caller-computed time (lock-busy, hourly-cap, rate-limit respacing) applies **no jitter** and must log `respaced by JobSpacingMinutes after lock-busy or rate-limit (no jitter)`. The quota-reset wording (reset anchor + 30–300 min jitter) is confined to the branch that actually dices it. **Test: T25.**
- **F-M94:** **Database refresh as scheduler task:** a dedicated task reconciles the stored state with reality — it removes tracker state for Jellyfin items that no longer exist and verifies the file side of stored verdicts (F-M234). The task, its dashboard name and its log prefix all read "database refresh" (`SubdlDatabaseRefreshTask`, `[SubDL-Refresh]`); the config field `PruneMode` keeps its name because it is serialized. It uses the global run lock and operates on the shared **LiteDB** database (`SharedDbContext`).
- **F-M214:** **A database refresh compacts the database in the same run.** Deleting rows in LiteDB releases pages inside the file but never returns them to the filesystem, and every delete also sits in the rollback journal (`subdl-sync-log.db`) until a checkpoint — so a prune on its own leaves the store physically as large as before. The prune is therefore followed, in the same run and while it holds the global run lock, by `SubdlDbContext.Compact`: fold the journal in (`Checkpoint`), then rebuild the file (`Rebuild`) to release the free pages.
 - **Compaction is measured as the whole footprint** — data file plus journal, before and after. Reporting the main file alone understates the starting size (the freed bytes are in the journal at that moment) and can render a real reduction as growth.
 - **It must never fail the task:** an exception is logged as a warning and swallowed. It is housekeeping, and the refresh's own work has already succeeded.
 - **No separate setting:** the compaction follows the refresh cadence (`PruneMode`), including a manual trigger. `PruneMode.Never` therefore means neither prune nor compaction. On an already dense file `Rebuild` reports 0 collections rewritten, so the cost per run is negligible.
 - **Why not a file-level copy-and-rebuild:** the database is open and other components hold references to it, so swapping the file under them would race with their writers. The rebuild runs in-process on the open store. **Test: T33.**
- **F-M119:** **OSHash refresh as scheduler task:** a dedicated task recomputes expired or fingerprint-changed OSHash cache entries on **its own diced WEEKLY anchor** (`RandomOshashTime`, "D HH:mm", drawn once at install and never re-rolled). It fires **every week** — unlike the database refresh there is no `IsoWeek` gating. It holds the global run lock while mutating the shared cache. `OshashRefresh` is **not** a cadence: it bounds how long a cached fingerprint is trusted (`Never` = fingerprint mismatch only, zero media reads in the steady state), while the fire date comes from the anchor alone. Setting it to `Never` therefore does **not** disable the job.
- **F-M193a:** **No construct LiteDB cannot translate may cross into a query.** A `StringComparison` overload, a helper-method call or any predicate without a `BsonExpression` must be applied **outside** the query lambda: keep the indexed equality inside and move the rest to LINQ-to-objects afterwards.
 ```
 // wrong — the ItemId index stays unused and the query fails at execution
 Find(x => x.ItemId == itemId && string.Equals(x.Language, language, StringComparison.OrdinalIgnoreCase))
 // right
 Find(x => x.ItemId == itemId).Where(x => string.Equals(x.Language, language, StringComparison.OrdinalIgnoreCase))
 ```
 - **Why this is a rule and not a style note:** such a predicate does not fail at build time and does not fail helpfully at runtime. LiteDB emits a syntactically valid-looking expression with a **missing operand**, and the exception leaves `RunAsync` — so the failure presents as a **dead pipeline**, not as a compile error, a startup error or a network problem. A pipeline that dies *after* its API calls succeeded points at this class of defect. **Test: T29.**
- **F-M192 [B1]:** **The partial reset scopes (`scope=upload`, `scope=download`) must WRITE BACK the rows they mutate.** Clearing a file-complete marker mutates the entities returned by `FindAll`, so the persist step must receive **those same objects** — passing a second, freshly deserialized `Update(db.Media.FindAll)` makes both scopes silent no-ops that answer `200 {ok:true}` while the database is untouched. Collect the touched entities and call `Update(list)`. The scope logs the number of cleared markers so a no-op is visible instead of looking like success. **The `all` scope was never affected** — it deletes the whole file, which is why a full reset appeared to work while the partial scopes did not.
- **F-M191 [B1]:** **A SERIES item must carry SHOW-level ids** — TMDB and SubDL expect the tvshow id together with season and episode, **never an episode id**. Jellyfin's provider ids for a mis-typed episode are EPISODE ids in **both** fields.
 - **Episode → show resolution:** `GET /find/{imdbId}?external_source=imdb_id` → `tv_episode_results[0].show_id` IS the series TMDB id; `tv_results[0].id` is the series itself when the id was already show-level. The series IMDb then comes from `/tv/{showId}/external_ids`.
 - **An episode TMDB id cannot be walked up directly:** `/find/{episodeId}?external_source=tmdb_id` returns EMPTY and `/tv/{episodeId}` is 404. Without a usable IMDb id such a value is **dropped** (one `IsShowIdAsync` probe instead of two guaranteed 404s); the caller's type-free title search resolves the show by name.
 - **Placement:** `NormalizeSeriesLevelIdsAsync` runs for series items **after** the file-name type detection (so name-detected series are covered) and **before** the quality gate. Every correction is reported at Normal level.
- **F-M191b — Unresolvable IMDb id ⇒ DROP it, never keep it.** When `/find` returns every result array empty, TMDB does not index that IMDb id at all — for a series item it is an episode id TMDB has no record of. Keeping it "as the best available" uploads an episode IMDb id in the SERIES slot, exactly what this rule forbids. Both ids are dropped so the caller's type-free title search resolves the show by name.
- **F-M90:** **Database maintenance UI:** the config page exposes only **Reset** and **Restore** for `subdl-sync.db`. **Reset** creates a timestamped backup, then removes the database so the plugin starts with a fresh registry. **Restore** restores the most recent backup after a single confirmation. No separate "Initialize database" button: the plugin creates an empty database on first start and always opens an existing one.
- **F-M181:** **Single backup retention:** after a database reset all older `subdl-sync.db.bak-*` files are deleted; only the backup created by that reset remains.

### 3.18 Persistent State — Data Model and Compatibility
The plugin keeps its state in **one LiteDB file** (`subdl-sync.db`, next to the DLL, in the plugin data directory), grouped into **five clearly separated areas**, each keyed by the thing it actually describes. "One file, five areas" is deliberate: the areas share a lifetime and are written by the same lock, but they must not be mixed, because a verdict about a video file, a stream position and a piece of subtitle text has three different identities.
#### 3.18.0 Area 0 — Compatibility record (`meta`)
- **F-M195:** exactly **one** row (`_id = "db"`) describing the file itself: `SchemaVersion` (integer, raised by hand whenever the stored shape changes), the plugin version that wrote it last, the Jellyfin version, and a timestamp.
 - Read at startup to answer "may I safely write here?". A `SchemaVersion` **higher** than the running build understands → writing is disabled for the session and an Error names both versions: a newer build may store fields this one would silently drop when it rewrites a row, so without the check an older DLL opening newer data destroys it quietly.
 - A **lower** version logs a warning and raises the marker; no migration (F-M195b).
 - The row is written **once per context creation**, never per run: an audit record that rewrites itself every cycle is a write amplifier and tells nobody anything.
 - The Jellyfin version is read from the loaded server assembly and stays **null when unavailable** rather than being invented. The assembly is named `jellyfin` (from `jellyfin.dll`); `Jellyfin.Server` is only a namespace inside it. The probe must try `jellyfin`, `Jellyfin.Server` and `Jellyfin.Server.Implementations` **case-insensitively** and fall back to the entry assembly.
#### 3.18.1 Area 1 — Media hash cache (`oshashes`)
- **F-M61b:** keyed by **file path** → `Hash`, `Size`, `MtimeUnix`, `Updated`. Pure cache: losing it costs one recomputation, which is why it is the one area keyed by a path while every other area is keyed by a hash. A lookup validates size **and** mtime and treats a mismatch as a miss, so a replaced file is re-hashed automatically.
#### 3.18.2 Area 2 — Video files and their embedded tracks (`media`, `embeds`)
- **F-M196:** one record per **video file**, `_id` = the stable OSHash (16 hex characters, F-M61). Carries `Path`, `JellyfinItemId`, `ImdbId`, `TmdbId`, `SdId`, `IsSeries`, `Season`, `Episode`, `LastSeen`. For a series episode the ids are the **SHOW** ids, never episode or season ids (F-M191).
 - Derived, written automatically whenever an embedded track is stored so they cannot drift: `LanguagesAvailable` (sorted, comma separated) and `HearingImpairedAvailable`.
 - Completion marks: `SubtitlesUploadedAt` / `SubtitlesDownloadedAt` + `SubtitlesDownloadedLanguages` (F-M88c, F-M151a).
 - Search bookkeeping: `LastSearchUtc` + `LastSearchLanguages` (F-M64).
- **F-M197:** one record per **embedded subtitle stream** in `embeds`, `_id` = `"<media hash>|<stream position>"`.
 - The key is media hash **plus position** because that is the identity of an embedded track: it has no name and no existence of its own. Two streams of one file can share a language (a normal and an SDH variant), so the language alone must never identify the row.
 - Fields: `Language`, `HearingImpaired`, `ContentHash`, `Status`, `Reason`, `StatusAt`, `SubdlId` (F-M198).
 - **Why position-grain matters:** recording a rejection per (file, language, HI) while recording terminality per position allows the two to contradict each other — one rejected stream blocks the whole language, so a pair with a rejected *and* an uploaded stream is skipped entirely. With the key on the position they cannot contradict each other. **Test: T17.**
#### 3.18.3 Area 3 — Sidecar files (`sidecars`)
- **F-M199:** one record per loose `.srt` file, `_id` = the **normalized content hash** (F-M186).
 - Content is the identity because that is what makes a sidecar an independent thing: the same subtitle stays known after the file is renamed or moved, and two sidecars sharing a language but differing in text stay two rows. The file name is stored for diagnosis only and plays **no part** in the key.
 - Fields: the shared subtitle state (F-M198), plus `FileName`, `Path`, `MediaHash` and a copy of the parent metadata (`ImdbId`, `TmdbId`, `IsSeries`, `Season`, `Episode`) so a sidecar can be judged without loading the file record.
 - Downloaded subtitles are stored here too: once fetched, the file on disk **is** a sidecar.
 - Sidecars deliberately carry **no stream position**: they have none. Terminality is therefore the outcome itself — there is no second "settled" marker to write. **Test: T19.**
#### 3.18.4 Area 4 — Burned download candidates (`rejected_candidates`)
- **F-M200:** one record per fetched-and-discarded download candidate, `_id` = `"<item id>|<language>|<SubDL id>"`.
 - Its grain is neither a stream nor a piece of content but "this remote release was burned for this file and language", and SubDL's own id is the only identifier such a verdict has.
 - Fields: `Reason`, `Updated`. Capped at the newest 50 per file and language so a pathological candidate sequence cannot grow the store without bound. Cleared for a file and language when a download finally succeeds.
#### 3.18.5 The four subtitle states (F-M198)
A subtitle in area 2 or 3 is in exactly one of four states:
- **uploaded** — sent to SubDL and accepted.
- **rejected** — not accepted. The **reason** lives in its own field (`Reason`), never in the state name: `duplicate-remote`, `duplicate-content`, `too-small`, `too-few-cues`, `lang-mismatch`, `bad-structure`, `runtime-mismatch`, `und-off`, `und-too-small`, `und-detection-failed`, `unmapped-language`, `duplicate-self-echo`, `candidate-rejected`.
- **downloaded** — fetched from SubDL.
- **pending** — nothing recorded yet. This is **never stored**: it is the absence of a row.
There is deliberately **no "settled"/"done" state.** The previous model kept a separate settled row beside the outcome row, which duplicated every verdict and forced every reader to know both layers. "Is this position finished?" is answered by asking whether any of the three stored outcomes is present.
#### 3.18.6 Key discipline (all areas)
- **F-M194b:** every area is keyed by a **computed business key stored in the record's own `_id`**, never by a database-assigned auto id. This is the structural correction of **F-M194**: with an auto id an upsert of a "new" row can never find the row it means to update, and the write silently inserts instead — so one logical fact came to exist many times over. With a computed key the failure is impossible by construction. **Test: T16.**
- Composite keys are built in exactly one place per area (`SubdlDbContext.EmbedKey`, `SubdlDbContext.CandidateKey`) so writers and readers cannot drift apart on the key shape.
- Every area has an index on its key; the query paths used by the pipelines are indexed as well (media hash, content hash, status, language).
#### 3.18.7 Consequences for readers and writers
- `IsUploaded(mediaHash, language, hearingImpaired)` stays pair-level by design: it answers "do I still need to upload this language for this file", which is what the self-echo guard and the collector ask.
- Per-position questions use `GetEmbed` / `EmbedRejectedReason` / `ArePositionsTerminal` — never a pair-level query.
- A stream skipped **because its language is already uploaded** is recorded as **rejected with `duplicate-self-echo`**, not as "uploaded". It was not uploaded; claiming so would inflate the upload statistics.
- Derived file aggregates (`LanguagesAvailable`, `HearingImpairedAvailable`) are recomputed whenever a track is written, in one place, so no caller can leave them stale.
- **F-M201:** **The plugin persists its OWN configuration fields by patching them into the file on disk**, not by writing its in-memory object over it. The file is read, only those fields are replaced, the rest of the document is preserved byte for byte, and the result is written as a temp file that then replaces the original.
 - **Fields:** the seven scheduler anchors plus the statistics counters and their start stamp (the counters moved to the database in F-M207; the flag `StatusCountersMigratedToDb` remains a config field).
 - **Why:** Jellyfin has no partial write — `SaveConfiguration(config)` always serialises the **whole** object, so any consumer that saves must be able to reproduce every field. Two code paths here save automatically (the constructor and the event dispatcher), and neither is a user action.
 - **Consequence:** with the fields taken from the file, an empty or damaged in-memory state can no longer erase user settings — the failure is impossible by construction rather than merely guarded against. The temp-file-and-rename write additionally ensures an interrupted save cannot replace a valid file with a truncated one.
 - A `null` field value is **skipped**, never written as empty: "unknown" must not become "delete".
 - When no file exists yet, only the plugin's own fields are written; the document is deliberately **not** seeded from the in-memory object, since that would be the very overwrite this rule prevents.
 - User-facing saves are unaffected: the config page writes through Jellyfin's own `updatePluginConfiguration`, which legitimately sends the complete object. **Test: T20.**
#### 3.18.8 Migration policy
- **F-M195b:** structural changes are **not migrated**. The schema marker in area 0 makes the change visible and the database reset (F-M90) is the intended path; records from an unrecognised schema version are ignored rather than rewritten. The stored state is reconstructible from the media files, and a half-migrated store is worse than an empty one.

- **Retired requirements:** F-M17, F-M17a, F-M17b, F-M17d, F-M17e, F-M17f, F-M24, F-M24c, F-M52, F-M56, F-M175c. Their scope was folded into the entries named above or dropped outright. ## 5. Non-Functional Requirements
- **NF-1:** Platform independence: pure IL DLL (net10.0), no native binding, no P/Invoke, no platform-specific dependencies.
- **NF-2:** GPLv3
- **NF-3:** Performance: no blocking of library scans; uploads asynchronous (background queue, IHostedService), extraction sequential per file
- **NF-4:** Robustness: queue survives Jellyfin restart (persistent state files); no infinite retries
- **NF-5:** No telemetry/external calls except api.subdl.com (+ dl.subdl.com for downloads, + api.themoviedb.org when a TMDB key is configured)
- **NF-6:** Testability: test JF instance with a small test library
- **NF-7:** Cross-platform discipline in code: no hardcoded path separators, no P/Invoke, no case-sensitive file operations without normalization
- **NF-8:** **Manual stop button** ("■ Stop all uploads & downloads", General tab): one click sends `DELETE /ScheduledTasks/Running/{taskId}` for BOTH directions.
## 6. Acceptance Criteria
- **A-1:** New episode with embedded subs appears in JF → all text subs automatically extracted, QA-checked, uploaded, without manual intervention
- **A-2:** Dry run on test library produces a complete status report without API calls
- **A-3:** Corrupted/garbled subtitle stream is detected by QA and skipped
- **A-4:** Wrong-language test case → detected per config
- **A-5:** Upload error (simulated 5xx) → retry + "failed" status, no crash
- **A-6:** State survives JF restart: already uploaded files are not processed again
- **A-7:** Library scan is not blocked by running uploads (<1s in-scan overhead)
