# Requirements Specification — Jellyfin Plugin "SubDL Scribe" (Upload + Download)

**Project:** Native Jellyfin plugin: automatic upload of embedded subtitles to SubDL.com + download pipeline for missing external subtitles — both in ONE plugin
**Version:** 2.61
**Date:** 2026-09-30
**Author:** SubDL Scribe Team
**Status:** Implementation — v12.1.12.157-dev. Single canonical requirements document. The revision history lives in the commit log; this document states what must hold and which test proves it.

**Document convention — read this before adding an entry.**
A requirement states **what must hold**: the rule, the constant, the reason it must hold, and the test that proves it. It does **not** record how the rule came about. Measurements, incident chronology, "verified live" narratives, before/after numbers, log excerpts, IL offsets and defect forensics belong in the **commit message**, not here. An entry that reads as a bug report has drifted out of scope and must be reduced to its rule. Historical `F-Mxx` markers without a requirement line are removed from the source rather than kept.

---

## 1. Objective

Automatic upload of all embedded text subtitles from the Jellyfin library to SubDL.com.

**Core idea:** Jellyfin already knows every file and every stream. The plugin handles discovery, extraction, quality assurance and upload entirely within the media server — no external polling cron, no separate state management for file discovery.

## 2. Background / Current State

**Manual / scripted extraction and upload, outside Jellyfin:**
- Extraction of embedded subs via ffmpeg — one call per file, all streams at once
- Upload to SubDL API (`https://api.subdl.com`), 1 account, MAX_UPLOADS=2000/run
- Queue JSON + uploaded-state JSON + lock files + not-found retry (96 attempts)
- A repeating two-hour job with a random delay (anti-determinism)

**Architecture decision: one plugin, two pipelines — "SubDL Scribe"**

Download and upload are integrated in ONE plugin. The downloader is NOT a standalone app or a second plugin.

- **Upload pipeline:** extracts embedded subs and uploads them (sections 3.1–3.10).
- **Download pipeline:** searches for missing external subtitles and downloads them (F-M37–F-M41 guarantee it integrates without refactoring).
- Both share the same services and process, with separate switches, separate scheduled tasks and separate status counters.

Shared components (identical for both pipelines):
- **SubDL API client** (login, rate limit, backoff, retry) — one implementation, two consumers
- **Content-hash registry** (central state): every sub the system uploads OR downloads is registered under a normalized content hash. The upload side consults it before uploading, the download side before downloading.
- **Language mapping + IMDB resolver** (tvshow-IMDB/season/episode chain)
- **Config/status infrastructure** (one config page, shared logging, shared skip filters)

**Known problems the plugin must solve:**
- Container language tags are often wrong (ISO 639-2/B inconsistent) → language verification needed
- Files in subfolders: path resolution errors possible

## 3. Functional Requirements

Requirements carry a **release stage** tag:
- **[B1]** Base (MVP, v1.0) — core upload path. No publish without B1.
- **[B2]** Extension (v1.1+) — QA, duplicate protection, anti-synchronization, filters.
- **[B3]** Comfort/expansion (v2.0, optional).
- **[D]** Download pipeline, parallel to B1/B2.

### 3.1 Triggers & Discovery
- **F-M1 [B1]:** Automatic upload of new media files via scheduled task with configurable interval (daily/weekly/monthly/3 months/manual per F-M21; "on new file" = ItemAdded, F-M1a)
- **F-M2 [B1]:** Manually triggerable scheduled task (dashboard "Scheduled Tasks") for a full library rebuild
- **F-M3 [B1]:** Only process files with embedded text subtitles (`IsTextSubtitleStream` from the Jellyfin item)
- **F-M4 [B1]:** Never upload an (item, language) pair twice — persistent state file in the plugin data dir
- **F-M4a [B1]:** Only process libraries selected in the config (F-M18)
- **F-M213:** **The library selection is a hard gate for every trigger and BOTH directions, and every user-facing report names only what was SELECTED — never the wider walk scope.** Two consequences, both mandatory:
 - **Work:** with `SelectedLibraries` empty, no direction may start a run. The upload pipeline and the seeder have always stopped up front; the download pipeline must do the same (`No libraries selected — nothing to do`) instead of running its setup and filtering everything away later in `CollectItems` — a run that did nothing must not look like a run that scanned everything.
 - **Report:** `CheckDirectories` (the GUI's *Library directories* list) must filter on `IsSelectedName`, **not** on `IsLibraryRelevant`. The walk scope must include the outer library of a nested selection (F-M189: the items live there), but listing that outer library as a status row shows a directory the user never picked and reads as "all of this is scanned".
 - **Not in scope:** the database refresh's full-server id probe stays unscoped on purpose — it answers "does this item still exist", not "should this item be worked", so narrowing it would delete registry rows for libraries that are merely deselected. **Test: T32.**
- **F-M189 [B1]:** **Library selection resolves to PATHS, so a selection keeps working when libraries are NESTED.** An item is accepted when its `Path` lies under a selected root **on a directory boundary** (`/data/movies2Extra` must not match `/data/movies2`; comparison follows the filesystem's case semantics), or when the resolved collection-folder name is selected. `LibraryScope.cs` resolves the selected names once per scan via `GetVirtualFolders` → `VirtualFolderInfo.Locations`. A second predicate `IsLibraryRelevant(name)` marks the libraries that CONTAIN or are CONTAINED BY a selected path, because the folder walk must enumerate the OUTER library — otherwise it filters an empty set. Applied at all five scope sites: the seeder's hard gate and its event-path gate, `CollectItems` in BOTH pipelines, the dispatcher's event-library resolution, and the status controller's directory check.
 - **A nested layout must not be "fixed" by restructuring the library:** creating the inner library over an already-covered path succeeds via the API but stays EMPTY, and deleting the outer one is a destructive layout change. The scope must handle subdirectories.
- **F-M1a [B3]:** ItemAdded real-time trigger — implemented as the `ItemAdded` subscription in `SubdlEventDispatcher` (`OnItemAdded`); there is no separate watcher class. Each arrival starts a non-resetting debounce timer (`ArrivalDebounceMinutes`, default 5 min). On fire the dispatcher runs one cycle: seed → download → upload (download first, F-M149). Events arriving during an active cycle collect in `pendingDuringCycleIds`; at cycle end one follow-up reseed runs if the list is non-empty, gated by `FollowUpRoundsDownload` and `FollowUpRoundsUpload` (both off → no reseed).

### 3.2 Extraction
- **F-M5:** **One ffmpeg call per file, however many subtitle streams it carries.** Every text subtitle stream of a file is extracted in a SINGLE ffmpeg invocation into a temp folder: repeated `-map 0:s:N -c:s srt -f srt <out>` output pairs on one input. The per-stream cost is not the extraction but the READ — ffmpeg opens and re-reads the container for every invocation, so a file with N text streams is read N times.
 - **The index rule:** stream positions are SUBTITLE-relative (`0:s:N`), never container indices. Both numbering schemes agree only while the file has no non-subtitle streams before the subtitles; mixing them lands on video or audio and fails with exit 8 or a no-stream error.
 - **No optional mapping — `0:s:N` without `?`.** A trailing `?` looks like the safe choice ("skip the index if it does not exist") and is the opposite: on an index that does not exist ffmpeg writes the FIRST subtitle stream into that slot, exits 0 and reports nothing — a subtitle of the wrong language, silently duplicated in another slot. An unknown index must therefore fail the call, which the caller reads as a whole-pass failure and answers by retrying the empty streams one at a time. A slow honest path beats a fast mislabelled upload.
 - **Why one call:** the cost of the per-stream shape is not the extraction but the READ — each invocation opens and re-reads the whole container. A file with N text streams is therefore read N times, and on CIFS/NAS media those reads dominate: the single pass reads the file about once regardless of how many streams it carries, and produces byte-identical output.
 - **The fallback rule:** ffmpeg's exit code decides what an empty result means. Exit 0 → the stream was read and carries no text; that is a verdict, and it must NOT be retried. Non-zero → the pass failed as a whole, the empty results are suspicions, and each empty stream is retried once with the per-stream call rather than being recorded as a permanent extraction failure.
 - **Test: T63.**
- **F-M6 [B1]:** Text formats only (SRT/ASS/SSA/VTT via SubRip conversion); bitmap subs (PGS/VobSub) explicitly excluded
- **F-M7 [B1]:** Safely delete temp files after processing (success AND failure)
- **F-M185:** **Canonical SRT form — one normalization for hash AND payload.** Every extracted or loose SRT is normalized once on arrival, before any QA gate, hashing or upload: strip a leading UTF-8 BOM, CRLF → LF, lone CR → LF, trim trailing whitespace. The same string then feeds both `ComputeHash` and the upload body, so hash input and uploaded bytes are identical by construction. The normalization is **idempotent**. Applied at extraction, at loose-file read, and again as a safety net in the upload path (reachable directly via the retry path).
 - **Why:** ffmpeg writes CRLF for some container streams and LF for others, so without a canonical form identical subtitles produced two different hashes and two different payloads. SubDL stores the MD5 of the raw file, so it saw two distinct entries and its own duplicate check could not fire. LF is canonical because it is the hash definition, the SRT standard, and readable by VLC/mpv/ffmpeg/Kodi/Jellyfin.

### 3.3 Upload
- **F-M8 [B1]:** SubDL API (`https://api.subdl.com`): login (user/pass → token), upload endpoint, rate limit 1–3 s between uploads
- **F-M9 [B1]:** Metadata per upload: series IMDB (**not** episode IMDB) + season + episode for TV; movie IMDB for movies — from Jellyfin provider IDs. Without IMDB → skip (F-M28). **F-M151:** upload ID quality gate validates/corrects JF IDs via TMDb before upload, default ON. **F-M203:** the TMDb key is required — the gate is not optional.
- **F-M10 [B1]:** Language mapping to SubDL's two-letter codes (`nob→NO` etc.)
- **F-M11 [B1]:** Upload queue with retry: failed uploads (HTTP 5xx/timeout) retried with exponential backoff, max N attempts, then status "failed" + dashboard display
- **F-M12 [B1]:** Configurable account (SubDL user/pass) in plugin config, password never in plaintext in logs
- **F-M48 [D2]:** **Loose SRT files as an additional upload source:** external `.srt` files next to the media file are uploaded in addition to embedded streams. Language detection from the filename suffix; unlabeled treated as EN; an `sdh` suffix marks the file hearing-impaired and it is uploaded with `hi=true` (F-M71). The HI flag is part of the identity in both areas (F-M197, F-M199). **Correction:** the rule also accepted `hi` as a marker. That is wrong — `hi` is the ISO 639-1 code for **Hindi** (`MapToSubdl("hin") = HI`), so `Movie.hi.srt` is a Hindi subtitle; since no language token preceded it, such a file was dropped outright. Nothing in this plugin writes `.hi.srt` (the downloader writes `.sdh.srt`). The marker is `sdh` only (F-M239).
- **F-M88c [B3]:** **Upload-side short-circuit (`SubtitlesUploadedAt`):** a file whose embedded subtitle side is complete is skipped before any ffprobe/directory walk/API call. Complete means every stream position reached a terminal state (uploaded or rejected). The field is deliberately named after the SUBTITLES, not the file: the video file itself is never uploaded — only subtitle data travels to SubDL.
- **F-M151a [B3]:** **Download-side short-circuit (`SubtitlesDownloadedAt`):** analogous to F-M88c. The stored language set is part of the state, not a note — the mark covers the languages it was written for, and any configured language it does not cover makes the file un-done and revisits it. **Subset, not equality:** a stored set that covers the configured one counts as complete (F-M234), so removing a language from the configuration leaves existing marks intact. The mark is validated against the disk before it is trusted (F-M234).

### 3.4 Quality Assurance (QA — before every upload, automated)
- **F-M13 [B2]:** SRT parser validation: valid UTF-8, ≥1 cue, monotonically increasing timestamps, plausible cue duration (>0.1 s, <10 min — long music cues stay legal)
- **F-M14 [B2]:** Sync plausibility: cue span vs. media runtime (+5 min tolerance; all cues concentrated in <10 % of runtime = reject)
- **F-M15 [B2]:** Language verification: detected language of the content (script blocks for CJK/Cyrillic/etc., Latin via stopwords) vs. stream tag; mismatch → skip; undetectable content passes (fail-open)
- **F-M16 [B2]:** Minimum size (hard 2 KB floor, always on) and minimum cue count (30) — below that "too small", skip

### 3.5 Duplicate Handling
- **F-M17c [B2]:** **Own upload dedup:** (item, language) pair + content hash in persistent state — never upload an already-uploaded or in-session-processed content hash twice. Depends on the canonical SRT form (F-M185): the hash is only stable across extraction runs when the payload is normalized first.
- **F-M17c2:** **Remote duplicate detection requires a canonical payload AND a matching hash function.** The registry hash is comparable with SubDL's stored raw-file MD5 only when both describe the same bytes and use the same function (F-M186). F-M185 and F-M186 are therefore **preconditions** of this section, not improvements to it.
- **F-M17x [B2]:** **Remote duplicate learning:** when SubDL rejects an upload with "Duplicate upload: identical file already published", the normalized content hash is stored in the registry as `duplicate-remote`. Future runs skip that exact content before any API call.
- **F-M186:** **The registry content hash uses SubDL's own function** — `ContentHashRegistry.ComputeHash` returns the MD5 of the canonical payload from F-M185, lowercase hex, 32 characters, so the registry value equals the `md5` SubDL stores in `raw_files[].md5` for our uploads. Changing the function **invalidates the existing registry**; the database reset (F-M90) is the intended path, no migration. The media hash (F-M61) is unaffected — it is the OpenSubtitles OSHash over size + first/last 64 KiB, not a content hash.
- **F-M187:** **Downloaded bytes have exactly one decode path.** Every conversion of downloaded subtitle bytes to text goes through `DecodeSrt`, which honours a UTF-16 byte-order mark (UTF-16LE/BE, BOM stripped) and falls back to UTF-8. The download side computes its content hash over `DecodeSrt(bytes)` and the upload side later reads the written file as UTF-8/UTF-16 text, so the two must agree. The file written to disk stays **byte-identical** to SubDL's payload — normalization is applied in memory for hashing and upload, never to the stored file.
 - **Why:** a bare `Encoding.UTF8.GetString` on a UTF-16 payload produces mojibake on one side only, the hashes diverge, `IsContentKnown` misses and the file is downloaded *and* uploaded again. The runtime check degrades silently as well: UTF-16 NUL bytes break the timecode regex, so it reports a match without comparing anything.
- **F-M17z [B2]:** **Upload dedup respects the stored outcome:** any recorded outcome — uploaded or rejected with any reason — counts as "known" for the subtitle. With the four-state model of section 3.18 this is simply "a row exists", and because the rejection reason lives in its own field a new reason never needs a new state name.
- **F-M61:** **Path-independent dedup key (OSHash):** upload dedup keyed on the media content hash, persisted across restarts, moves and renames.
- **F-M184:** **Duplicate handling delegated to postprocessing:** the upload path does not search SubDL for duplicates before uploading. A duplicate upload is accepted by the API ("sent for review"), resolves to `rejected` on the SubDL dashboard, and the postprocessing job deletes that entry and marks the local registry entry `remote-duplicate`. This removes one search call per item against the hourly bucket and the daily search quota; the cost is one upload per duplicate, removed again by the next postprocessing run. A local self-echo guard (registry, per media/language pair) still prevents uploading the same pair twice.

### 3.6 Configuration / User Interface (IPluginConfigurationPage)
- **F-M18 [B1]:** Library selection: checkbox list of all JF libraries — only selected ones are scanned/uploaded (default: none, deliberate opt-in)
- **F-M19 [B1]:** Credentials: SubDL **username/password** *or* **API key** (both fields present, login method automatic: API key preferred if set, else user/pass → token)
- **F-M20 [B1]:** Configurable rate limit: uploads/hour (**default 400**) or a minimum pause between API calls (`MinCallPauseSec`, 0.1–10 s, default 0.5 s; the smaller of the two wins). `GlobalRateLimiter` clamps the rate to **1–2000**; `RunWatchdog` clamps its grace calculation to **1–500**. The default of 400 sits inside both.
- **F-M21 [B1]:** Update interval: **daily / weekly / monthly / 3 months** (scheduled fires at the per-installation diced random anchor, F-M51) or **manual** (no scheduled fires, dashboard/config-page triggers only); "on new file" = F-M1a. **Default: Weekly** — since F-M111 both directions share the unified `RefetchInterval`, whose constructor default is Weekly.
- **F-M22 [B1]:** **Dry-run switch: search runs, no transfer.** The pipeline walks its full decision path — search, threshold, ranking — and reports what it WOULD do (chosen candidate per language, the numbered slots of F-M242, the hearing-impaired pick of F-M241), but fetches no file and writes nothing. Search quota is spent; download quota is not.
 - **What the dry run does and does not do:** it stops before the download call, so no file is ever transferred — but searches DO cost API quota, one per language set (two while the HI switch is on, F-M241). The GUI text must name both, because "without saving files" and "without API calls" are not the same claim.
 - **Why it is load-bearing:** with HI on, the second search is what makes the variant visible; a dry run that skipped searching could not report it, and the run costs one search per item — the reason a dry run over a large library is not free.
- **F-M53:** Manual run buttons and statistics reset on the General tab
- **F-M216:** **A GUI call to a plugin endpoint that answers `application/json` must request `dataType: "json"`.** Without it the Jellyfin apiclient bundle returns the **raw `Response` object** — `application/json` is not `text/*`, so the bundle falls through to its last branch. The object is truthy, so a `!s` guard never fires, while every field reads `undefined`: the statistics line rendered "undefined subtitles uploaded, undefined subtitles downloaded since —" although the endpoint answered correctly. Set `dataType: "json"` on the `Stats` GET **and** the `StatsReset` POST, in **both** the inline script of `configPage.html` and `configPage.js` (F-M216 is the second instance of this file-pair trap, cf. F-M218). Other loaders in these files call `.json` themselves, which is why only the statistics line was affected.

- **F-M270:** **ONE page-wide "Refresh status" button at the END of the General tab reloads every live readout at once.**
 - **Rule:** the button sits INSIDE the general tab container, directly below the Workers list, and writes one timestamp line directly above itself. It refreshes five readouts in one click: the API/search quota AND the download quota (both live in `#SubdlQuotaBox`), the SubDL/TMDb lights AND the library read/write rows, the statistics counters, and the Workers list. Implementation: `subdlReloadEverything` exposed as `window.subdlReloadEverything`.
 - **It is not a form action:** it must NOT sit next to Save, and no tab may carry a second refresh button. Nothing live exists on the Expert/Upload/Download tabs, so the General tab is the only correct home — that placement is also what keeps it off the other three tabs.
 - **Width and depth are set INLINE** (`display:block;width:100%;box-sizing:border-box;background-color:#424242;border-color:#5a5a5a;color:rgba(255,255,255,0.85)`) with `class="raised button-submit block emby-button"` as a fallback, inside a bare wrapper `<div>` (any wrapper margin breaks the flush fit with Save). The `block` class alone is NOT authoritative: a client/theme whose own `.emby-button` rule is ordered after `.block` overrides it silently.
 - **Test: T87.**
- **F-M271:** **The refresh timestamp has exactly ONE writer — the button's own click handler — and it names the manual act.**
 - **Rule:** the stamp sits directly above the button and reads `Manually refreshed <time>` with `<time>` rendered from the CLICK moment in the viewer's timezone, seconds included. `Not refreshed yet.` before the first click.
 - **Why exactly one writer:** only a user's click may write the line. The quota's `fetchedAt` comes from a server answer cached for 5 minutes — a time the click did not cause — so a second writer moves the stamp with nobody pressing the button. A stamp the user cannot attribute to an action is worse than no stamp.
 - **Why the label names the manual act:** the page refreshes itself on two other cadences (F-M272), so a bare "Refreshed" would claim the whole page was refreshed when only that one button was pressed. The automatic cadences stay silent about themselves by design — no second writer and no "auto-refreshed" line.
 - **The rule holds in BOTH page scripts.** `configPage.js` is inert for the served page (nothing requests the `Plugins/SubdlSync/ConfigJs` route), but it carried its own copy of the status loader that wrote the stamp with a SERVER timestamp labelled "Last checked" — a contradicting second writer, invisible in the browser. It was removed; the regression check reads both files.
 - **Resolution IS the feedback:** `subdlFmtTime` must show seconds. It rendered hour/minute only, so a refresh inside the same minute produced a byte-identical string and the user concluded the button was broken although the click had fired all four requests.
 - **Test: T87.**
- **F-M272:** **The page has THREE refresh cadences, and none of them is "10 s for everything".**
 - **The 10 s tick** (`window.subdlStatsRefresh`) reloads the statistics counters and the Workers list ONLY — both read live instance state, no external call.
 - **The quota box** (holding BOTH the API/search bar and the download bar) has its OWN **60 s** timer (`subdlQuotaTimer`), stopped and restarted around Save, and is additionally cached 5 minutes server-side, so that call is free.
 - **The SubDL/TMDb lights, the login light and the library read/write rows** have **NO interval at all** — they run at page init, after Save, and on the Refresh button only.
 - **Every refreshed endpoint carries a cache-buster** (`_t=Date.now`), so no layer can serve a stale body.
 - **Why this must be stated rather than assumed:** a loader called ONLY at page init is indistinguishable from server caching — a finished worker run changes nothing until an F5 — and the cause has to be visible in the code, not inferred from the server's behaviour. The server's caching headers are not the explanation and must not be mistaken for one.
 - **Test: T87.**
- **F-M273:** **The configuration page has a host-free structural regression check.**
 - **Rule:** `scripts/tests/gui-structure/check.py` (run: `python3 scripts/tests/gui-structure/check.py`, exit code 0 = all pass) asserts the page's structure and wiring without a Jellyfin host: the Workers section and the Refresh button sit INSIDE the general tab container and nowhere else; the timestamp exists exactly once, sits above the button, and neither automatic loader writes it; all four loaders carry a cache-buster; the one refresh covers all five readouts; no `window.<loader>` reference names a plain function declaration; the 10 s poll really reloads statistics AND workers; the default target languages read from `PluginConfiguration.cs` are exactly `AR, EN, ES, FR, HI, ZH` and every one of them exists in the picker; `configPage.js` does not write the stamp; the embedded script parses (via `node --check`).
 - **Why it exists:** three defects in this page are invisible in the browser and read only as "it feels sluggish" or "why is this on every tab". A section placed outside the tab containers stays visible under EVERY tab; a loader called only at init never updates again; and a `window.x` reference to something that is not on `window` resolves to `undefined`, so the refresh skips that readout silently.
 - **The checks are structural, not wording-dependent:** a comment rewrite must not be able to raise a false failure.
 - **Test: T87.**
### 3.7 Status & Transparency
- **F-M23 [B2]:** Status view: two cumulative counters on the config page — total subtitles **uploaded** and **downloaded** since the last reset. The line reads "N subtitles uploaded, M subtitles downloaded since \<date\> (last timer reset)". "Reset statistics" zeroes both and moves the "since" date. The counters are incremented at the end of every run from that run's summary, **including runs cancelled from outside** (user stop marker, task cancel, Jellyfin restart): the pipelines return their partial summary, so work that already reached SubDL is counted. Only these two counters exist — the earlier per-outcome counters were removed as dead state no UI rendered.
- **F-M209:** **A pipeline run's in-run watchdog is torn down on EVERY exit path, not only on success.** The dispose, the `ApiActivity` unsubscribe and the null-out sit in the `finally` alongside `PipelineRunLock.Release`.
 - **Why:** a watchdog released only inside the `try` outlives a run that left it on an exception and then logs "no progress for N min — aborting run" for a run that has already ceased to exist. `UploadPipeline` already used `using var watchdog`; the asymmetry is what produced phantom aborts on the download side only. **Test: T28.**
- **F-M208:** **The reschedule budget is per UTC day and resets at the day roll-over** — deliberately the same 00:00 UTC boundary the SubDL quota reset uses, so the budget comes back when the quota comes back. `SubdlSchedulerCoordinator.ResetDailyRescheduleBudget` clears every slot once the day rolls over; it runs from the scheduler tick (so it also happens while nothing else runs) and at the top of `TryCountReschedule` (so a trigger just after midnight is never charged to yesterday's budget). It is a **no-op** when the day has not changed and logs only when it actually clears slots.
 - A slot that reached the limit otherwise has no path back: the refusal drops its pending fire, so it can never fire, so it can never clear its own counter — and with `RefetchInterval = Manual`/`OnArrival` no anchor exists that could clear it.
 - Both refusal messages must name the **day roll-over** as the recovery path and must **not** promise that a regular anchor takes over (that anchor does not exist in those modes).
 - The counter is NOT cleared by a manual run and NOT cleared by a successful run — it is indifferent to where the action came from. Only a real fire or the day roll-over clears it. **Test: T27.**
- **F-M207:** **The cumulative counters live in the database, and a database reset resets them with it.** They occupy a single-row area 5 (`status_stats`, key `"status"`, `long` counters — `int` would overflow far earlier than the totals warrant). Writes via `Plugin.AddStatusCounters(uploaded, downloaded)`, reads via `Plugin.GetStatusStats`, zeroing via `Plugin.ResetStatusStats`.
 - `scope=all` calls `ResetStatusStats` as part of the same operation, so display and data can no longer disagree.
 - The GUI reads `GET /Plugins/SubdlSync/Stats`; "Reset statistics" posts `POST /Plugins/SubdlSync/StatsReset?confirm=true`. No live page path may read `config.StatusUploaded`.
 - The pre-migration XML totals are adopted **once**, guarded by the config flag `StatusCountersMigratedToDb`. The flag is required, not cosmetic: without it a restart after a database reset would re-import the old totals into the freshly emptied data file. It is listed in `PluginOwnedFields` so an automatic save cannot drop it.
 - The XML fields `StatusUploaded`/`StatusDownloaded`/`StatusStatsSinceUtc` remain in place, unread, so a downgrade still finds them. **Test: T26.**
- **F-M219:** **The type-neutral TMDb search is the FIRST rung everywhere an id is resolved, and the year is checked on its RESULTS — never sent to it.**
 - **The year must not be sent to `search/multi`.** It ignores the parameter entirely; a query that carries one reads as a filter while filtering nothing. The typed endpoints do honour it, which is why the typed search remains the second rung. **The year is applied when the hits are read:** a hit whose own date (`first_air_date` for tv, `release_date` for films) equals the year wins over the first hit; with no year-equal hit the first film/series hit is used, unchanged. Taking `hits[0]` alone picks by POPULARITY, not identity — "Fargo" resolves to the 2014 series when the item is the 1996 film, "The Office" to the US show when the item is the UK one. The fallback is required, not lenient: a Jellyfin year is often the IMPORT year (F-M217), so a list with no year match must still resolve.
 - **Both id-less resolution paths start type-neutral:** `DownloadPipeline`'s title rung and `SubdlSeeder.ResolveIdsOfAsync`. A typed search inherits whatever type Jellyfin guessed — the assumption F-M190 and F-M217 stopped trusting — so a name-detected series that Jellyfin typed as a `Movie` asks `search/movie` and can never match. The typed search stays the SECOND rung, where a known type plus the year is the sharper query. **Test: T36.**
 - **The seeder parses the file name before it asks TMDb** (same `MediaNameParser`, F-M217), so its title, type and season/episode do not depend on the library's typing. The type TMDB reports is what the seeder returns.
- **F-M222:** **Every required field is marked ONCE, in red, on the configuration page — and states where to get the value.**
 - The four required inputs: **Libraries** (F-M213: nothing runs without a selection), **SubDL account** (login + API key), **TMDb API key** (F-M203) and **Download target languages** (F-M42: empty = download off). - **F-M220:** **The plugin description has TWO carriers and they must not drift — the card reads the DLL, not build.yaml.**

- **F-M231:** **Jellyfin's ids are ALWAYS tested against TMDb by TITLE and YEAR, and the year comes from the FILE NAME when it states one.**
 - **Both id sources are always tested against TMDb.**
 - **Why the pair check is not enough:** `ResolveAndValidateIdsAsync` answers "do these two ids describe the same entity", which a wrongly pinned pair passes. Title and year were never asked. That is how a 110-minute 2026 film sitting in `Mayday/S01/` kept the 2003 documentary's identity (uploaded as S20E26, 37 languages).
 - **Year source:** the file name's year first, Jellyfin's only as fallback (`Movie.ProductionYear`, else `Episode.Series.ProductionYear`). Jellyfin's year comes from the same metadata that may be pinned to the wrong title, so asking with it can only confirm the mistake.
 - **Correction rule:** only on an EXACT year match (`ResolveByTitleYearAsync`, the strict twin of the multi-search that refuses the popularity fallback). No exact hit ⇒ Jellyfin's ids stand, so a missing year or a differently spelled title costs nothing (F-M190's rule that the name is authoritative is unchanged).
- **F-M232:** **A login that fails on a server error is CLASSIFIED, never propagated raw.**
 - **Why classification is mandatory:** an unclassified failure propagates as a raw parse exception, the cycle logs a generic failure, and a recoverable server overload is never recognised as one — so the F-M67 overload fire is never scheduled and the run is simply lost.
 - **Rule:** every login attempt is classified — 404 `NOT_FOUND` and 403 are auth verdicts (fail closed, immediately, `AuthBroken`), 429 keeps its existing retry/backoff, and a 5xx or a non-JSON body after the retries exhaust is a **transient overload**: it sets `TransientOverload`, ends the run cleanly and schedules the F-M67 overload fire (`ScheduleOverloadFire`). A raw parse exception must never escape `LoginAsync`.
 - **A JSON body behind a 5xx is still transient**, never a credentials verdict — the status code decides, not the body shape.
 - **Diagnostics must be reachable:** the client's `Log` channel (login retries, raw 429 bodies, rate headers) is subscribed per run by both pipelines. A channel wired in one path only leaves the retry line that names the failure written nowhere reachable.
- **F-M238:** **A 429 is not a verdict — the COUNTERS decide whether the allowance is spent.**
 - **Rule:** every 429 is classified into three variants before anything stops. Rate headers present → the daily allowance (exact reset from the header). Body `service_busy` → transient overload, wait the server-reported window. Body `rate_limit` with `retryAfterSeconds` → a short-term trip, waited out like the overload. Only when the counters say the direction's allowance is spent does the run stop for the day.
 - **Why the status code alone cannot decide:** SubDL answers 429 for both the spent allowance and a short-term trip. Reading it as "spent" turns a short pause into a lost day of work; reading it as "harmless" turns a spent account into a retry storm. The two are indistinguishable without the numbers, which is why the decision moves to the counters.
 - **The counters are read from the same source the settings page shows** (`GET /api/v2/me`, `usage.search` / `usage.downloads`), so GUI and pipeline can never disagree, and only after a 429 — a healthy run makes no extra call. Search and download are separate allowances, so every decision names its direction.
 - **An unreadable quota is not a free quota.** When the read fails or the response carries no limits, the conservative path stands (the 429 remains a stop) — answering "not exhausted" on an unknown counter would spend requests against a limit that may already be reached.
 - **The anchor for a next-day fire is the server's own `reset_at`**, never a local midnight guess, with the jitter added ON TOP so the retry cannot land before the allowance is back. `Continue after daily limit` still gates that path per direction; with it off, that direction stops clean with no fire.
 - **The respacing offset is `JobSpacingMinutes`** — the setting the GUI exposes (clamped 5–120 like every other reader of it). No fixed interval is introduced for the rate-limit case.
 - **Every day-long stop schedules.** A spent allowance and an unreadable one both end in a fire after the reset plus the 30–300 min jitter; stopping without scheduling means the work waits for the next regular anchor instead of the reset. Only the direction's toggle off, or an arrival run holding the slot, stops without a fire. **Correction:** the search path stopped with a log line only and scheduled nothing, so an unreadable allowance lost the day it was meant to recover.
 - **A dry run reports the hearing-impaired choice.** The HI variant is selected after the main download, beyond the point a dry run stops, so the run repeats the selection and reports it (`DRY-RUN HI … (n/m candidates are HI)`) and marks each planned candidate with its `hi` flag. Checking the HI setting therefore costs no download — it is a question about the search result, not about the file.
 - **See T52, T53, T55.**
- **F-M237:** **A `Rebuild` that cannot release the pages is replaced by a rebuild from the file's own rows.**
 - **Rule:** when LiteDB's own `Rebuild` fails, the store is rewritten from its rows: rows are read out, written into a fresh file, counted against the original, and only a matching count is swapped in. Rows are therefore never traded for a smaller file.
 - **Why the engine's rebuild is not enough:** `Rebuild` walks every index, and past a few thousand rows it exceeds its internal traversal limit and throws. The file then keeps every freed page forever, so the nightly refresh reports no shrink on every run.
 - **The swap is a rename, not a copy.** The rebuilt file takes the old one's place by rename, because a running Jellyfin holds the file open and a copy over it is refused with "being used by another process" — the very refusal that stopped the first attempt.
 - **The previous file survives as exactly one timestamped backup**, reachable through the database restore function. The rebuild deletes nothing until the row count is proven equal.
 - **The rebuild's side files are addressed by their STEM** (`subdl-scribe-log.db`, `subdl-scribe-temp.db`), never by appending to the full name — the latter matches nothing on disk and left stale rebuild temporaries behind.
 - **See T54.**
- **F-M236:** **A failed compaction must not leave the shared database dead.**
 - **Rule:** LiteDB's `Rebuild` is not an in-place operation. `LiteEngine.Rebuild` runs `Close` → `RebuildService.Rebuild` (move the file aside, rename a temp copy in) → `Open`, and the `Open` sits on the success path only. Any throw inside `RebuildService` therefore leaves the engine closed — and with it every collection handle on the shared `SubdlDbContext`, for the rest of the server's life. Every endpoint that touches the database then fails with `ObjectDisposedException` on LiteDB's `ReaderWriterLockSlim`, while a reader that does not touch the database keeps working.
 - **The compaction is verified, not trusted.** After a failed rebuild the database is probed with a real query (`Meta.FindById("db")`); only when the probe fails is the engine replaced. A flag would merely restate the exception.
 - **The repair is a fresh `LiteDatabase` over the same path.** The engine cannot be reopened in place — `Close` leaves `_state.Disposed` set — so `_db` is deliberately not readonly and the instance is swapped. The collections are property getters over `_db`, so they resolve against the new engine on their next access; no handle is re-created by hand. `EnsureIndexes` runs again afterwards.
 - **Three outcomes, because two of them mean different things:** `Compacted` (the file was shrunk), `Recovered` (the rebuild failed, the store was brought back, **the file was NOT shrunk**), `Broken` (restart required). The refresh logs `compacted: X -> X bytes` for no outcome — a `Recovered` run states that the file was not shrunk and that the next refresh retries.
 - **The repair preserves the data.** The failed swap leaves the original file on disk, so rows survive; the harness asserts the row count is unchanged across the failure and that the repaired engine accepts a write.
 - **See T51.**
- **F-M235:** **A transport timeout is retried three times, and a user stop never is.**
 - **Rule:** a timeout is transient, like the 5xx login answer of F-M232. Before this, an expired request threw `TaskCanceledException`, which the API clients do not catch (they catch `JsonException`), so it reached the run loop's `catch (OperationCanceledException)` and was reported as "cancelled — keeping the partial result": a slow server looked like the stop button, and the item was dropped without a retry.
 - **The two cancellations are told apart by ONE source of truth — the caller's token.** Already cancelled → the user (or the run) asked to stop and the request is NOT repeated; otherwise the cancel came from the handler's own per-attempt timeout and the request is worth repeating. Retrying a user stop would make the stop button ineffective.
 - **Budget:** 3 attempts per request (the same number the login path has used since F-M232), 1 s base backoff, doubling. Transient means `TaskCanceledException`, `OperationCanceledException`, `HttpRequestException` or `IOException` — a `JsonException` is an answer, not a transport problem, and is never retried.
 - **Per-request timeout, not one global value:** 60 s per attempt for API calls, overridable per request via `HttpRequestOptionsKey`; a subtitle FILE download asks for 5 minutes, because a whole-season archive is orders of magnitude larger than a metadata answer. `HttpClient.Timeout` is disabled (`InfiniteTimeSpan`) so it cannot cap the whole sequence including the retries.
 - **A request body survives a retry:** the body is buffered once and the request rebuilt per attempt, otherwise the second attempt would fail on consumed content.
 - **Exhaustion is classified, not silent:** the give-up line names the server as not answering in time, and never as a caller cancel. The retry lines are routed into the run's log channel, so a hidden retry is visible.
 - **See T50.**
- **F-M233:** **An on-arrival run works ONLY the arrivals; a full-coverage pass happens on the schedule or the manual button.**
 - **Rule:** the arrival path must be scoped to the items that actually arrived. Unscoped, a single arrival window swept every gap in the library into the queue and the run died on the daily limit before reaching its own items.
 - **Collector, not one-shot:** the debounce window collects EVERY event in it, not merely the first, and arrivals during an active run form the follow-up window. An arrival cycle seeds and works exactly those ids.
 - **Trigger rule:** only `event` and `arrival-followup` are scoped. `scheduled-upload`, `scheduled-download`, recovery fires and the manual button carry NO item scope and keep full coverage for the selected libraries.
 - **"Kein treffer, kein lauf":** an arrival-scoped round whose seed queued nothing for that direction starts no run — it ends instead of working leftover queue entries. A full-coverage round is unaffected.
 - **Never widen:** an arrival cycle with an empty collector (the follow-up re-read after the first direction drained it) ends without a scan. Falling back to a full scan on the arrival path is a defect, not a graceful default.
 - **See T48.**
- **F-M234:** **The state prune is a database refresh: it verifies the FILE side of a stored verdict, not only whether the item still exists.**
 - **Rule:** a removed item is only the crudest case. A subtitle file deleted while its item stays keeps a verdict that says "uploaded"/"rejected"/"downloaded" and a download mark that says the language is settled — both are then permanently wrong, and the item is reported complete forever while the seeder keeps queueing it.
 - **The mark cannot be replaced by a disk check, only falsified by one.** It means "every target language settled", and settled includes "SubDL does not have it" (QA-exhausted, no file expected). So a stored language is declared stale only when it is absent from disk AND not QA-exhausted (`FindStaleDownloadedLanguages`); then the mark is dropped and the search stamp cleared so the item is reworked in the SAME run instead of waiting out the refetch gap (`MarksInvalidated`, reported in the run-end line).
 - **Refresh phases:** dropped/missing sidecars lose their verdict, stale download marks of still-existing items are dropped, and the previous work (dead rows, guid-keyed trackers, oshash paths, compaction) is unchanged.
 - **Fail-safe (same two-tier rule as the oshash cache):** every root the stored paths live under must exist AND list cleanly, else the file side is skipped entirely and nothing is forgotten. Rows without a stored path are never judged. "Unknown ≠ deleted": a missed refresh costs nothing, a false one destroys valid verdicts.
 - **Subset rule:** a stored language set that COVERS the configured one counts as complete, so removing a language from the configuration no longer invalidates every mark and forces a full-library refetch; adding one still does.
 - **Naming:** task, dashboard name, log prefix (`[SubDL-Refresh]`), lock slot (`dbrefresh`) and the GUI heading say "database refresh". **The config field names (`PruneMode`, `RandomPruneTime`) deliberately stay** — they are serialized property names and renaming them would drop the user's saved settings.

- **F-M247:** **A dry run contributes NOTHING to the statistics — all six counters, not only the volume ones.**

### 3.8 Anti-Synchronization (thundering-herd protection)
- **F-M25 [NOT IMPLEMENTED]:** A per-run start offset (random wait before the first upload) is not implemented — no code path delays a run before its first item and no config property backs it. The anti-herd function is carried instead by the per-installation diced fire times (F-M51), the hourly-cap roll-over offset (`JobSpacingMinutes`, F-M26b) and the daily-limit recovery jitter (F-M182, 30–300 min). Manually triggered runs start immediately.
- **F-M26 [B2]:** **Random jitter in the rate limit — on the transfer rhythm, not on bare calls.**
 - The pause between two real transfers (upload→upload, download→download) is the base interval ±30 % (`GlobalRateLimiter.TransferPauseMs`).
 - The pause between two API calls carrying no transfer (empty search, skip, metadata lookup) is **deterministic** (`InterCallPauseMs`): exactly `MinCallPauseSec` when configured, otherwise `3600/cap`.
 - **Why:** transfers are the load a shared API actually sees, so that is where a randomised rhythm matters; spreading idle calls adds nothing. The two are separated by name as well, so a reader cannot mistake one for the other.
 - The band is base ±30 %, floor 1 s. With the default cap of 400/h that is 6.3–11.7 s.
 - A failed or skipped candidate gets **no** transfer pause (transaction semantics: nothing was transferred) and stays on the bare-call pause (F-M26a).
 - The "derive from the hourly cap" sentinel `-1` must **survive** clamping; only a real value is clamped, otherwise `Math.Clamp(-1, 0.1, 10)` yields 0.1 and the derived branch is unreachable. **Test: T21.**
- **F-M26a:** **Which pause applies where (single source of truth).** `InterCallPauseMs` — bare API calls, deterministic. `TransferPauseMs` — real transfers, ±30 %.
- **F-M26b [D]:** **Hourly-cap roll-over fire is offset by `JobSpacingMinutes`.** When the shared hourly bucket is exhausted mid-run, the run stops and a one-shot recovery fire is scheduled at the bucket roll-over **+ `JobSpacingMinutes`** (upload and download alike, `ScheduleHourlyFireIfExhausted`), clamped 5–120 like every other reader of that setting. Default 15.
 - The user configures this through the existing **Job spacing (minutes)** field — one knob for all spacing, no separate control to discover.
 - Anti-herd spreading is not needed here: this offset is per installation and rides the account's own hourly roll-over, not a shared wall-clock event. The daily-limit reset keeps its randomised 30–300 min offset (F-M152, F-M182) instead.
 - The coordinator must not add a second offset on top: this path uses `ScheduleRecoveryFireAt`, whose `alreadyJittered: true` leaves the caller's offset alone by design. The offset must not affect the daily-limit reset. **Test: T22.**
- **F-M27 [B2]:** **Auto-backoff:** on HTTP 429/rate-limit or 5xx the request is retried up to 3 attempts with exponential backoff (2 s, then 4 s; the server's `retryAfterSeconds` wins when sent, minimum 5 s). On exhaustion the request fails cleanly and the run-level reaction matrix (F-M54) applies.

### 3.9 Privacy / Anonymity
- **F-M28 [B1]:** **IMDB ID mandatory — correct per media type.** For series strictly the series IMDB (tvshow, not episode) plus season and episode; for movies the movie IMDB. Resolution order: (1) Jellyfin metadata as-is; (2) TMDB id → IMDB via the TMDB REST API (required key, F-M203); (3) TMDB title search; (4) skip "no-imdb". Episode IMDB is never used. (The 15-min metadata wait was removed — F-M100: arrival runs go straight to the ladder.)
- **F-M190 [B1]:** **ID resolution is type-free and TMDB-authoritative, and it is the standard path for every upload** — not an optional gate.
 - **Type detection comes from the FILE NAME and from TMDB, never from the Jellyfin library type.** `MediaNameParser` reads the name (`S01E05`, `Season 1 Episode 5`, TV-recording stamps `Title_YYYYMMDD_HHMMSS`); when it reports a series while Jellyfin reports none, the item IS resolved as a series. A later `search/multi` answer overrides the assumed type: **TMDB decides** whether the title is a film or a series. The Jellyfin library type is never the source: an episode in a library typed "movies" is imported as a `Movie`, so class-based detection would search TMDB for a FILM named after the episode.
 - **ID arbitration (JF vs TMDB) with a report:** both IDs present → cross-validate via TMDB; on disagreement a **Normal-level** log line is emitted (`ID conflict for "<title>": Jellyfin says <tt…>, TMDB says <tt…> — using the TMDB id`) and **TMDB wins**. This must be visible without raising the log level.
 - **Fallback chain:** TMDB returns no IMDb → the Jellyfin ids are kept; Jellyfin carries only a TMDB id → the IMDb id is fetched from TMDB; **no IMDb resolvable at all → NO upload** (fail-closed).
 - **Upload payload preference:** IMDb + TMDB when both are known, IMDb alone when TMDB is missing. Neither id → no upload.
 - **Series IMDb lookup needs `/external_ids`:** the TMDB detail endpoint reports `imdb_id: null` for series, while `<kind>/<id>/external_ids` returns the real `tt…`. `ResolveImdbAsync` therefore falls back to `/external_ids` whenever the detail response leaves the IMDb id empty — without it every series was skipped as "no-imdb".
- **F-M28a:** Before every SubDL search/upload the plugin calls `ResolveAndValidateIdsAsync` to cross-check and correct Jellyfin's IDs via TMDB when a key is configured. Mismatches are corrected, missing IDs backfilled. This runs automatically whenever a TMDB key is present; there is no separate UI switch.
- **F-M249:** **The file-name parser reads two more real name shapes, and nothing else changes.**
 - **Rule:** `MediaNameParser` recognises (a) a **bare episode marker without a season** and (b) a **broadcast date in the middle of the name with the title AFTER it**. Both are read as the name states them; every other shape keeps its previous result.
 - **(a) Bare `Exx`.** A name like `The Revolutionaries E05.mkv` carries no `S<d>E<d>`, so the series pattern never matched: the item was treated as a **MOVIE** and searched as `The Revolutionaries E05` — **0 hits** — while TMDb knows the series (tv 249863, 8 episodes, 2026). The new rule sets `IsSeries=true` and the episode number from a bare marker, and **falls through to the shared head/year/quality cleanup** rather than returning early — a separate return path would let the two branches drift apart.
 - **The bare marker is guarded.** `[Ee]\d{1,3}` on its own is dangerous: `Movie.1080p.x265-E5.mkv` is a release-group suffix, not episode 5. A marker written directly after `-` and preceded by a known codec token (`x264`, `x265`, `h264`, `h265`, `hevc`, `av1`, `aac`, `ac3`, `eac3`, `ddp`, `dts`, `10bit`, `8bit`) is **rejected**. Other separators (dot, space, underscore, bracket) keep it. Verified: `x265-E5` → no episode, `1080p-E5` → episode 5.
 - **(b) Mid-name broadcast date.** `BBC.Documentaries.2016.05.11.Cunk.on.Shakespeare.EN.SUB.MPEG4.x264.WEBRIP.[MPup].mp4` is `<strand>.<YYYY>.<MM>.<DD>.<title>.<tags>`: the **prefix is the strand and the title follows the date**. The old code took the first year anywhere and cut there, producing the strand (`BBC Documentaries`) as the title — the TMDb search for it returned an unrelated film (`Transgender Kids: Who Knows Best?`). TMDb knows the real title (`Cunk on Shakespeare`, movie 397385, `tt5715186`). The new rule takes the text after the date, cuts it at the first release/language token and drops trailing bare numbers, yielding `Cunk on Shakespeare` with no year.
 - **The date rule is narrow by construction:** it applies only when (1) no `SxxExx`/long-form marker is present, (2) the date is a **separated** `YYYY<sep>MM<sep>DD` (the compact `YYYYMMDD` stamp is `TvStampPattern`'s job and stays there), (3) month and day are in range, and (4) **text follows the date** — `Movie.2016.05.11.mkv` keeps `Movie` + year 2016.
 - **Scope of the change:** only the two intended name shapes are affected — bare `Exx` names and the Cunk date name. Every other file parses byte-identically in title, year, type, season and episode, and no file loses its title. The change is a fix, not a broadening.
 - **Deliberately NOT changed:** the prefix of (b) is dropped rather than combined (a strand is not part of a title); a bare `Exx` never invents a season (`Season` stays null, so the pipeline's `season >= 0` gate still decides); the compact TV-stamp path (F-M190) is untouched; and the `E` must be **uppercase** — a lowercase `e` is left alone, because `Z00topia.2.e5`-style names are indistinguishable from a word fragment.
 - **Not addressed here:** `Cunk on Britain` / `Cunk on Earth` parse **correctly** (series, S1E4 / S1E1). TMDb files both broadcasts as ONE entry (`Cunk on...`, tv 79063), S1 = Britain, S2 = Earth) whose **`imdb_id` is empty**, so `/find/tt16867040` and `/find/tt8232636` both return nothing and F-M231's "test Jellyfin's ids against TMDb" rule discards ids TMDb cannot confirm. That is a TMDb data gap, not a name parse. It is **not** covered by this requirement and needs its own decision before any code changes — deliberately left open here rather than folded into a parser fix.

- **F-M251:** **one name parser, not two.** The download side carried its own copy of the name logic — `ParseFileNameForIds` with its own SxxExx regex, its own year regex and its own quality-tag list — so it silently kept every gap the main parser had already closed, and every future name shape would have had to be fixed twice.

- **F-M250:** **The parser reads two more series markers.**
 - **Method:** an independent release-name parser (`guessit` 4.4.0) was run over every media file and compared against ours per file. It located an episode where ours found none in **84** cases; the reverse never happened. Two causes account for **83** of them — both real defects, fixed here.
 - **(a) `NxNN` (`2x01`, `1x04`).** 43 files, chiefly Italian scene releases (`Reacher.2x01.Sportello.Automatico.ITA.ENG.…`, `Stranger.Things.1x04.…`). Without the marker the item was typed as a **FILM** and searched as `Reacher 2x01 Sportello Automatico ITA ENG` — 0 hits — while TMDb knows the series. Now read as a series marker with season and episode.
 - **The `NxNN` rule cannot misfire on a resolution.** `1920x1080` is the obvious trap, so the season is capped at two digits, must not start with `0`, and may not be preceded by a digit (`(?<!\d)` + `[1-9]\d?`). Verified: `1920x1080`, `2160x1080` and `0x01` yield nothing; `1x01` → S1E1, `10x05` → S10E5.

 - **Scope of the change:** every affected file belongs to one of the four intended shapes (bare `Exx`, the Cunk date name, `NxNN`, `SxxExx` at the end). No file changes outside those groups, none loses its title, none loses its season or episode.
 - **The library diff is the acceptance criterion, not a nicety.** A filename parser that widens is a parser that re-identifies a whole library quietly; the four-group arithmetic above is what proves the change is a fix rather than a drift, and T70 asserts it.
 - **`guessit` itself was NOT adopted.** It solves (a) exactly as we do, but it **fails the Cunk date name** (reports the strand `BBC Documentaries`, i.e. our old bug) and it **misreads** `Movie.2024.1080p.x265-E5.mkv` as `season 2024, episode 5` — a release-group suffix taken for an episode, which is precisely the case our codec guard rejects. - **F-M202 [B1]:** **An episode TMDB id is PROVEN against a candidate show — never guessed.**
 - Gap it closes: Jellyfin reports an episode TMDB id with no IMDb id for some files, and `/find` **cannot** walk an episode id up to its show — `find?external_source=tmdb_id` returns every result array empty for such an id. Dropping the id leaves the item with no ids at all and no path to a show id.

A confirmed match yields the SHOW ids (imdb via `/external_ids`, since the detail endpoint reports `imdb_id: null` for series).

 - Season/episode always come from the file name (Jellyfin reports none for a mis-typed episode), which is why `NormalizeSeriesLevelIdsAsync` now takes them.

- **F-M244 [B1/D] [NOT IMPLEMENTED]:** **The queue item is a complete work order, and the pipelines only carry it out.** The seeder decides WHAT is to be done and hands it over in the item itself; the downloader and the uploader execute that order and do not re-derive it.
 - **Rule:** a `QueueItem` carries the work it was queued for — for downloads the target languages **and** whether the hearing-impaired variant is wanted (`HiWanted`); for uploads the needed stream positions. The seeder fills these fields at seed time, from the same evaluation that admitted the item to the queue.
 - **Rule:** the download pipeline reads its list of languages from the item. The upload pipeline likewise consumes the positions it was handed.

- **F-M255 [D]:** **No candidate and no stream is discarded without a line naming it and the reason.**
 - **Rule:** every exit inside the candidate walk that does not end in a save, and every per-stream exit of the upload collector, writes one line at Verbose (`[SubDL-D] … reject …` / `[SubDL-V] …`) carrying the release or file, the language, and the measured reason. Without a line for every exit, different outcomes look identical: "the fetch failed", "a gate rejected it" and "the content was already known" are indistinguishable, the same way a fetched-and-discarded candidate leaves no trace — so a shrinking candidate list cannot be told apart from a thin SubDL result.

- **F-M256 [D]:** **A registry lookup takes the media PATH and resolves the hash itself.**
 - **Rule:** `ContentHashRegistry.HearingImpairedLanguages` receives the media file path, resolves the media hash internally (`GetMediaHash`), and only then reads the embedded and sidecar rows. No caller passes a hash for this question.
 - **Why it must hold:** the hash and the path are both plain strings, so the compiler cannot tell them apart. This is not a caller-side fix but a signature change, because a rule that depends on every caller choosing the right one of two indistinguishable strings is a rule that has already been broken — the same defect class as the two name parsers (F-M251) and the three HI readers (F-M254).

Assert `HearingImpairedLanguages(path)` finds a stored HI row AND that the same call with the HASH finds nothing; assert the pipeline consequence (with the path only `DE` is missing, with the hash `EN` and `DE` are). - **F-M257 [D]:** **The embedded area is written by whoever reads the streams, not only by the uploader.**
 - **Rule:** the seeder's scan and the download pipeline record each embedded, non-forced, mappable subtitle track as an observation row (position, language, hearing-impaired). The row carries `Status = observed` and no verdict. The uploader keeps writing verdicts (`uploaded`/`rejected`) on the same key, and an observation never overwrites them.
 - **Why it must hold:** with `UploadEnabled` at its default `false` the embedded area stays empty, so every reader of it answers from nothing — and the one reader that depends on it is the HI question (F-M254), which then reports the variant as absent for a track that is right there. The consequence is not cosmetic: the language is queued and an external HI sidecar is fetched for a variant the container already carried, on every run, and no later run can correct it because nothing writes the row while the upload is off.

 - **Rule:** only TEXT subtitle streams are recorded. A bitmap track (`dvdsub`, `pgssub`) carries painted pixels: it cannot be extracted, so it can never be uploaded, and it is not readable for a viewer either — it is not coverage for its language. A file whose target language exists ONLY as a bitmap track reads as having no readable subtitle for it, so the language stays due and a subtitle is fetched. The same rule applies to `EmbeddedPresentLanguages`, which is the reader that decides what is queued and downloaded at all.
 - **Rule:** one enumeration (`SidecarNaming.EmbeddedTracks`) serves the observers, so the rules cannot drift — the same reason the name parse (F-M239/F-M251) and the HI reader (F-M254) each have one copy.

 - **Known limit :** existing rows are left alone. A track an older build mis-marked as `hi=false` keeps that verdict, because the item is already settled and nothing reopens it. This change guarantees that new facts are recorded; it does not backfill history.

- **F-M258 [D]:** **The database refresh checks the embedded side too, not only the sidecar side.**
 - **Rule:** for every media row whose Jellyfin item still exists and which has stored embedded rows, the refresh reads the item's current streams and forgets every stored row that disagrees with them — on the key (position) and on the recorded facts (language, hearing-impaired). The empty case is the dangerous one: an item Jellyfin cannot probe returns no streams, and treating that as "the file has no tracks" would delete every row of a library that is merely offline. Only a NON-empty list that disagrees with a stored row is evidence.

- **F-M261 [D]:** **An untagged or `und` subtitle track is resolved, and the found language is written back into the container.**
 - **Rule:** a text subtitle track whose tag is absent, empty, `und` or `undefined` is not a fact about its language. The gate extracts those tracks, detects the language offline, records it as an observation and — when enabled — writes it into the container as a real track tag.
 - **Why:** neither shape can be mapped. `und` has no entry in `LanguageMapper.Map` (its two-letter fallback invents `UN`) and a NULL tag produces no row, so `EmbeddedPresentLanguages` reports the language as absent for a track that is in the file — and the item is queued and searched for a language it already carries.
 - **Rule — it belongs to the SEEDER, before the queue decision.** `IsDownloadTodo` asks `MissingLanguagesOf`, which answers "not present" for an untagged track, so a resolution that has not happened yet cannot change that answer. A pipeline-only gate is too late.
 - **Rule — the sequence is forced:** find the untagged text tracks from the stream list (no ffmpeg call when there are none) → one ffmpeg pass for all of them (F-M5) → detect offline with the 2 KB floor (F-M74) → write the codes into the container → move the file's registry state to the new hash → record the tracks. The queue decision then reads the corrected language.
 - **Rule — the registry move exists because the rewrite changes the file's IDENTITY** (the OSHash covers size plus the first and last 64 KB, and a Matroska segment header carries its own size). `ReplaceMediaIdentity(oldHash, newHash)` is a rename, not a re-decision: marks, ids, language aggregates, embed rows (rebuilt under `"<hash>|<pos>"`) and the parents of the sidecars travel. Where both sides hold a row the OLD one wins; an equal pair is a no-op and an empty hash is refused. After the move `FindOne(ItemId)` is unambiguous again.
 - **Rule — the gate reads and returns the hash pair** (`LanguageTagGate` holds the registry); the caller moves only a COMPLETE pair. The gate stays a file-level component.
 - **Rule — the tracks are recorded from the gate's own verdict, not through `ObserveEmbeddedFacts`:** Jellyfin caches its stream list, so the tags just written still read as "none" for the rest of the scan.
 - **Rule — the position rule.** A track's position is `0:s:N` over TEXT-eligible subtitle streams only (subtitle streams, not external, not forced, not bitmap), in container order: video and audio never enter the count; bitmap and forced tracks DO occupy a position and stay in the count, or every track after one would shift; the tag goes back to the position it came from. The gate filters to subtitle streams itself, so no caller can pass the wrong shape. External streams are skipped, not counted — ffmpeg only sees container streams.
 - **Rule — what the detector cannot decide stays without a row on purpose** (below the 2 KB floor, no text, no confident verdict). A wrong language is worse than none.
 - **Rule — the resolution counts as PRESENT for the coverage check in the same run**, because Jellyfin's cached list still reports the old tag for a container that was just corrected.
 - **Rule — the write is a stream copy (`-c copy`), never a re-encode**, and the original is replaced only after the result was read back and found to carry the wanted tag. `mkvpropedit` was rejected (native, architecture-bound, on neither target); ffmpeg is already required.
 - **The result is read back out of the file**, across the stream shapes that exist (audio in front, audio interleaved, bitmap tracks between, forced tracks between): every corrected track carries the wanted language and none is misassigned.  - **Why:** SubDL filters HI server-side and the two pools do not overlap — a release appears in one or the other, never both. An unfiltered response is therefore a MIXTURE, and the regular ranking would silently depend on how many HI releases it happened to contain.
 - **Rule:** a failed HI search keeps the regular candidates and logs it — the HI variant is a bonus (F-M42b), the regular subtitle is the target.
 - **Rule:** the HI branch sits BEFORE the `keepBest` break. Behind it, with the default `KeepBestPerLanguage=1`, it was unreachable and no HI variant was ever fetched or logged.
 - **Rule:** a dry run reports the HI pick from the HI pool, because the real selection happens after the file download, which a dry run never reaches.
- **F-M43 [D]:** **Runtime/FPS match with tolerance:**
 - **Stage 1 — pre-download (FPS):** SubDL provides `framerate`/`fps` per candidate. If set: difference > ±1 % vs. item FPS → candidate rejected. Missing → criterion skipped, no hard fail.
 - **Stage 2 — post-download (structure + runtime):** corruption check on the downloaded bytes (cue timings present, monotonically increasing, plausible durations), then runtime check of SRT cue span vs. item `RunTimeTicks`, default tolerance ±600 s. Outside → discard. Missing runtime metadata → criterion deactivated.
- **F-M44 [D]:** **Release match:** candidate release name scored against the local filename: release-group match > token overlap > download-count tie-breaker. Weights configurable (expert mode).
- **F-M45 [D]:** **IMDB/TMDB match** (default on, switchable off): candidates matched against item IDs. Default is a hard criterion (no ID → no download); switchable off for title-based fallback. **F-M151b:** download ID quality gate validates/corrects JF IDs via TMDb before search, default ON.
- **F-M46 [D]:** **Overall selection:** exactly one best candidate per (item, language) by combined score from F-M43–F-M45. No candidate passing → the language counts as "not available".
- **F-M47 [D]:** **Configurable refetch interval:** Manual / Weekly / Monthly / Quarterly. **Default: Weekly.** The per-file last-search stamp (`MediaEntity.LastSearchUtc` + `LastSearchLanguages`) protects already-downloaded languages and controls re-search. `DownloadRefetchInterval` is **obsolete since F-M111** — the unified `RefetchInterval` governs both directions and is what the GUI writes; the old property is kept only for XML compatibility.
- **F-M49 [D]:** **Daily-limit resume per direction:** two independent checkboxes, "Continue after daily limit" (Download) and "Continue after daily API limit" (Upload). **Both default ON** (`DownloadContinueAfterLimit` / `UploadContinueAfterLimit` = true). ON → wait once until reset (max 24 h) and retry; OFF → clean stop.
- **F-M50 [D]:** **Download budget per (item, language):** max N candidate downloads before the language counts as "not available" (default 3, 0 = unlimited).
- **F-M215 [D]:** **A season or range pack is resolved to the episode it belongs to — never saved whole.** A SubDL pack (a candidate whose payload covers a season or an episode range) must yield exactly one subtitle file per episode, chosen from the pack's own listing:
 - The search requests the unpacked file list (`unpack=1`); `SubtitleCandidate` parses the resulting `unpack_files` array (`name`, `season`, `episode`, `md5`, ready single-file url). The parameter is a **GET `/subtitles/search` parameter only** — sending it on `files/search` answers `Invalid request parameters`.
 - `DownloadCandidateAsync` picks the entry matching the **current season/episode** and downloads that single file.
 - **The ZIP fallback matches the entry NAME** (`S01E06`, `s01.e06`, `1x06`, SubDL's `S0106`). A multi-file archive whose entry cannot be resolved returns **null** instead of guessing — writing "the first `.srt` in the archive" next to every episode of the season is the defect this rule forbids.
 - A pack with no entry for this episode is **skipped**, not saved wrong. Non-pack paths (candidates without `unpack_files`, single-file releases, films) keep their existing behaviour.
- **F-M217 [D]:** **For a download the FILE NAME decides type, title and episode — not the Jellyfin library.** Jellyfin types an episode living in a library declared as *movies* as a `Movie`, and its item NAME is the raw file name (`Reacher.S03E01`), which resolves against nothing. Three consequences, all mandatory:
 - **The seeder prefilter must not drop such an item:** the id gate may not depend on a lookup that resolves the item's name. An item that cannot be resolved by name still has to reach the queue.
 - **The search query is the PARSED title** (`MediaNameParser`, the parser the upload side already uses) — `Reacher.S03E01` returns 0 hits against the type-neutral TMDb `search/multi`, `Reacher` returns the show.
 - **Season and episode come from the file name too.** For a `Movie`-typed item Jellyfin reports 0/0, so the F-M215 pack guard (`episode > 0 || season > 0`) could never fire.
 - **A year-filtered search retries once without the year.** Jellyfin's `ProductionYear` is frequently the IMPORT year (a 2022 show carrying 2025): the filtered query returns 0 hits where the unfiltered one finds the title.

- **F-M266:** **The registry sweep removes OBSERVATIONS only — a VERDICT and a detection-attempt record are out of its reach.**
 - **Rule:** in `ContentHashRegistry.ForgetStaleEmbeds` the comparison between a stored row and the caller's stream list is skipped for every row whose status is `uploaded` or `rejected`, and for every row carrying a `DetectionAttemptedAt` stamp. Only the remaining rows are compared, by position, language and hearing-impaired flag.
 - **Why it must hold:** an untagged or `und` track is invisible to a stream list BY CONSTRUCTION — the shared reader `SidecarNaming.EmbeddedTracks` drops every position whose tag does not map — so a row for such a track looked stale on EVERY run and was deleted each time. That destroyed two kinds of work: the uploader's own verdict (`rejected / und-too-small`, stored with `Language="UN"`) and the record that detection had already been attempted for that position.
 - **The consequence of getting it wrong:** a never-resolving track is re-opened and re-run through detection on every scan, and a rejected subtitle loses its verdict and is offered for upload again.
 - **Test: T84.**
- **F-M267:** **The waiting download/upload rows report the CYCLE's fate, not their own wait.**
 - **Rule:** `WorkerRunRegistry.DescribeCycle(cycleFinished, seederOutcome, seederDetail, directionOutcome, directionDetail)` decides the row of a wait-only task, with a strict ranking: (1) cycle not finished at the wait cap → `running` ("cycle still running at the wait cap"); (2) a `failed` direction or seeder → `failed`; (3) a `deferred`/`cancelled` direction, then a `deferred`/`cancelled` seeder → yellow; (4) a `skipped` direction, then a `skipped` seeder → grey; (5) otherwise → `ok`, carrying the seeder's numbers when it reported any, else "cycle finished".
 - **Why red ranks first:** a cycle that threw did not do its work either, so a green or yellow light would bury it.
 - **Why the direction's fate outranks the seeder's:** the seeder can have done its job perfectly (scanned fine) while the direction it fed was stopped by the quota — ranking it below would repaint exactly that case green.
 - **Why it must hold:** reporting the task's own "ok" is wrong twice over: it claims success when the wait cap expires while the seeder is still scanning, and it hides a quota stop behind a green light.
 - **Detail text is never empty:** `Fallback` substitutes "not recorded", so a row cannot show a bare outcome word.
 - **Test: T85.**
- **F-M268:** **One colour rule for every worker: green = the work ran and ended without an exception, yellow = the work did not happen but nothing is broken, red = something is broken, grey = deliberately not run.**
 - **Rule:** `ok` → green; `deferred` and `cancelled` → yellow (quota, run-lock deferral, user stop); `failed` → red (exception, failed cycle, unreachable core); `skipped` and `never` → grey (disabled, never run, or a scan that found nothing to do).
 - **Why grey is not green:** "the task was not allowed to run" and "the scan found nothing" are both information, and without a distinct colour a disabled direction is indistinguishable from a working one.
 - **Test: T85.**
- **F-M269:** **The database refresh's detail line names the compaction fallback.**
 - **Rule:** `SubdlDatabaseRefreshTask.BuildRefreshDetail` (static and pure, so the wording is testable without a Jellyfin host) appends a compaction note to the body with ` | `, e.g. `removed 33 dead state, forgot 0 stale row(s), dropped 450 mark(s) | compaction failed — rebuilt from own rows (12419072 -> 8249344 bytes)`.
 - **This is a NOTE, not a red light:** the refresh did its work and the store came back usable, so the outcome stays `ok`. The line carries the note precisely so the fallback is visible; with no compaction the line stays clean, so a note cannot be mistaken for the normal case.
 - **Context:** the LiteDB compaction failure itself is deliberately NOT to be solved; the rebuild is the accepted answer.
 - **Test: T86.**

### 3.13 Scheduler, Firing & Catch-up
- **F-M51:** **Per-installation random schedule anchors:** all scheduled fires come from a background coordinator (30-s tick). Daily/weekly/monthly/quarterly anchors are diced once per installation and persisted in config. No default fixed-time triggers. `OnArrival` / `Manual` modes disable scheduled fires.
- **F-M55:** **Download-on-arrival as its own switch** + UI restructure: "Download subtitles on arrival" checkbox (Download tab), independent of the upload arrival setting. Both directions share the same diced anchors/jitter.
- **F-M57:** **Symmetric per-direction schedule config:** Upload: "Upload subtitles on arrival" checkbox + "Upload schedule" dropdown. Download: "Download subtitles on arrival" checkbox + "Refetch interval" dropdown. Both share the same anchors/jitter; Manual disables scheduled fires for that direction.
- **F-M156:** **One-shot global catch-up for missed refetch windows:** if any scheduled anchor window passes unhandled (server down, restart, lock busy), the scheduler queues **exactly one** catch-up run. Multiple missed slots do **not** stack. The catch-up state resets when the next regular anchor fire runs.
- **F-M65:** **One-shot night recovery fire per direction:** a run stopped on the daily limit schedules one re-fire after the quota reset plus a random 30–300 min jitter (away from the 00:00 UTC herd), diced freshly per fire by cryptographic RNG — see F-M182.
- **F-M182:** **Jittered recovery fire after the daily limit:** when a pipeline stops on SubDL's daily quota, the direction is re-fired once after the server-reported reset plus a random 30–300 minutes. The offset is diced freshly per fire (cryptographic RNG) and rolled independently per direction, so the retry does not land on the 00:00 UTC reset moment every API consumer hits. The jitter applies to the **quota-anchor path only**; fires that already carry their own offset (run-lock retry, hourly-cap roll-over) keep their exact time. Log lines name the reset anchor, the resulting fire time in the local zone, and the jitter window actually applied.
- **F-M116:** **Recovery fires persisted:** the next scheduled download/upload fire times are persisted to disk and restored on plugin/Jellyfin restart so missed windows are eventually caught.
- **F-M210:** **Every scheduled job is driven by its OWN setting.** Database refresh, OSHash refresh and upload postprocessing each carry their own cadence field and their own diced anchor and must fire on them regardless of any other job's setting. The refetch rhythm (`RefetchInterval`) governs **only** the automatic pipeline cycles (download/upload); `Manual` and `OnArrival` there suppress those cycles and nothing else. A job must never sit behind an early return belonging to a different job's configuration.
- **F-M210a:** **A service with no manual start button offers "Never"/"off", never "Manual".** `Manual` means "triggered by the dashboard button"; where no such control exists for the job, the disabling option is `Never`. (Prune: `PruneMode.Never`; OSHash: `OshashRefreshMode.Never` — a trust window, not a cadence; postprocessing: `Never`.)
- **F-M211:** **The shared database context is created under a lock.** Concurrent first access by two jobs firing in the same tick must yield exactly one context; constructing two over the same data file races LiteDB's non-thread-safe `BsonMapper` and kills one task.
- **F-M212:** **No fire may be consumed before its task is registered.** `ITaskManager.QueueScheduledTask` silently drops the fire — logging `Unable to find scheduled task of type "X" in QueueScheduledTask` at error level — when the target task is not yet registered, which is the normal state during early startup. Every fire path must therefore test `IsTaskRegistered<T>` **before** it consumes its slot (no marker set, no reschedule counter reset), so the next 30-s tick retries and the work is not lost for the day. This applies to **all six** paths: database refresh, OSHash refresh, postprocessing, the refetch cycle, the F-M156 catch-up and the F-M65 recovery fires. A guard placed after the marker is consumed is a silent data-loss bug, not a harmless check. **Test: T31.**

- **F-M248:** **The scheduler's whole due-state is persisted, and a missed anchor slot is caught up instead of waiting for the next window.**
 - **Rule:** every dedup marker, the catch-up flag and the lock-busy deferrals survive a Jellyfin restart. A slot that already fired today stays consumed; a slot whose window was missed fires on the first tick where it is past-due and unconsumed. No fire carries a time window.
 - **Why the state must be on disk:** every due-test in the coordinator is answered against a RAM field (`_lastXMarker != marker`, `!_catchUpFired`). After a restart those fields are null, so `null != today` re-claims a slot that has already run — the due-test must read a persisted marker, or a restart re-fires the task. The database refresh carries the same shape on its own anchor day.
 - **The same defect on the refetch slot:** `_catchUpFired` and `_lastFiredMarker` are RAM-only too, so F-M156's one-shot catch-up replayed after every restart.
 - **And on postprocessing:** its marker is minute-granular (`yyyyMMddHHmm`), so it re-claims far more often than the day-granular ones.**
 - **What is persisted:** one file `scheduler-state.json` in the configuration directory, holding the four markers (`refresh`, `oshash`, `postprocess`, `fired`), the `catchup` flag and the three deferral instants (`refreshDefer`, `oshashDefer`, `postprocessDefer`, round-trip `O` format, `DateTime.MinValue` when none is pending). Written at most once per tick and only when a field actually changed.
 - **The marker counts the CLAIM, not the outcome.** A run that fails after being queued stays consumed for the day — persistence must not turn a failure into an infinite retry.
 - **No fire window.** The refetch slot carried `if (now > fire.Effective.AddSeconds(2 * TickSeconds)) continue;` — a 60-s window that made a missed anchor wait for the NEXT regular window instead of being caught up, contradicting F-M156 and the treatment of the three own-cadence jobs (refresh, OSHash, postprocessing carry no window). The window is removed: a past-due, unconsumed slot fires on the next tick. Stacking is prevented by the persisted marker, not by a window.
 - **Deliberately unchanged:** the deferrals keep their existing semantics (lock-busy → back off `JobSpacingMinutes`, slot stays claimable), the reschedule budget stays per-day in RAM (it is a safety valve, not a due-state), and recovery fires keep their own file (F-M116) because they are consumed on fire rather than keyed by day.
 - **Tests: T66, T67.**

### 3.14 Run Behaviour, Limits & Lifecycle
- **F-M54:** **Reaction matrix per server response:** 403 auth → immediate stop; 429 → classified by variant (F-M238) and decided against the live counters: a spent allowance follows F-M49/F-M182 (wait-until-reset or clean stop per the direction's `Continue after daily limit`), a short-term `service_busy`/`rate_limit` trip is respaced by `JobSpacingMinutes`; 5xx → retry with backoff; 200 + `status:false` → warn, fail-open for searches. **Correction:** the earlier wording routed every 429 straight to "daily limit or transient" from the status code and body alone — the code has decided against the counters since F-M238, because the same status code covers both cases.
- **F-M58:** **Transient-overload 429 classification:** `service_busy` 429 with `retryAfterSeconds` → retry loop (max 3×), run continues; login hardening for non-JSON 429 responses.
- **F-M62:** **429 classification fix:** a 429 that carries no rate headers and names neither `service_busy` nor `rate_limit` is treated as the conservative fallback (server-level 429, next-midnight anchor), not as the daily allowance — a 429 whose kind cannot be named must never be guessed in the direction that discards a day of work. The real daily allowance carries a reset signal. **Correction:** the earlier wording said every 429 without a reset signal is "transient with a 30-s window"; that holds for the two named bodies (`service_busy`, `rate_limit`) since F-M238, while an unnamed 429 goes to the fallback anchor.
- **F-M59:** **LIFO queue order:** both pipelines process items by `DateCreated` descending — newest first. The id-order partition keeps id-resolvable items before the id-less backlog.
- **F-M60:** **File-missing retries before permanent skip:** persistent counter per item (shared by both pipelines). Each failed file access bumps it; success resets it. At the configurable threshold (default 3, 0 = never) the item is skipped as "file-missing (retries exhausted)".
- **F-M64:** **Target-language change needs no reset pass:** each file stores the language list it was last searched under plus the timestamp (`MediaEntity.LastSearchLanguages`). `IsDue` compares that stored list against the current configuration, so a changed list simply makes affected files due again — no global reset run and no second bookkeeping row. Items already holding all new languages still skip without API calls.
- **F-M111:** **Queue-driven operation:** both pipelines run only over items the seeder placed in the in-memory queue. Runs are atomic per direction and serialized by a global run lock.
- **F-M131:** **Manual stop via marker files:** the Stop button creates `.stop-upload` and/or `.stop-download` in the plugin data directory. Each pipeline checks its marker before processing the next item (and, for uploads, also between streams of the same item), cancels the direction, deletes the marker and reports `StopRequested`. The dispatcher ends the cycle without starting further directions. Stop markers do **not** affect the delayed upload postprocessing task. The canonical endpoint for programmatic stops is `POST /Plugins/SubdlSync/Stop?direction=upload|download|all`; `DELETE /ScheduledTasks/Running/{id}` cancels the Jellyfin task wrapper but a currently-running pipeline item may finish first.
- **F-M177:** **Conditional follow-up reseed:** after the first seed/download/upload round of a cycle, a follow-up reseed runs exactly once — and only if new library arrivals were collected while a seed, download or upload was already running. Gated by `FollowUpRoundsDownload` and `FollowUpRoundsUpload`; if both are off no reseed runs, otherwise the forced scan seeds the pending arrivals and, if it adds new work, download runs before upload.

### 3.15 Upload Postprocessing
- **F-M17y:** **Delayed upload postprocessing:** after an upload run (normal finish or stop), on the postprocessing schedule (F-M176; not tied to the run and not to a fixed delay — SubDL review latency varies), the plugin queries `/user/mySubtitles` and resolves every locally pending-review entry into its final verdict: `accepted` → approved; `rejected` with "Duplicate upload" → deleted on SubDL + marked duplicate-remote; other rejects → marked upload-rejected. All steps logged at Debug. The task is scheduled by the dispatcher so it also runs after a stopped upload.
- **F-M176:** **Postprocessing reschedule spacing:** if postprocessing cannot start because the global run lock is busy (F-M94h: immediate `false`, no waiting) or it hits the hourly rate limit, it schedules a one-shot re-fire in `JobSpacingMinutes` (configurable 5–120 min, default from general job spacing). The re-fire still respects the diced schedule anchor and does not move the next regular postprocessing run. A busy lock is first checked for staleness; only a genuinely living previous run causes a deferral.
- **F-M193 [B1]:** **`/user/mySubtitles` is NOT paginated — the postprocessing counters must count DISTINCT upload ids.** The endpoint ignores `page`, `per_page`, `offset`, `limit` and `start`: every value returns the byte-identical complete list. `ListMySubtitlesAsync` must therefore deduplicate by `UploadId` and break on the first page that adds no new id (which also covers an ordinary short last page), while rows with `UploadId <= 0` are kept unconditionally so a parser regression cannot silently drop data. `CountMySubtitles` counts distinct ids and additionally reports `distinctUploadIds` and `paginationUnsupported`; the status line must not claim "in N pages".

### 3.16 Shared State, Locks & Maintenance
- **F-M94h:** **ONE global run lock for all six state-mutating components** (seeder, downloader, uploader, postprocessing, database refresh, OSHash refresh) — they all touch the same LiteDB state, so a single mutual exclusion is what the design needs. The lock is a block file holding `PID|UTC`; **overlap is never waited out.** A caller that cannot acquire gets `false` immediately (only a 20-s in-process hand-off grace) and **reschedules itself by `JobSpacingMinutes`** via the coordinator's `Schedule*Fire` / `ScheduleRecoveryFireAt` — all six do this. No poll loop.
 - **Stale detection:** (1) dead holder PID → take over immediately; (2) holder alive but stamp older than the 6-h run ceiling → wedged run, take over; (3) file older than 24 h → take over. `ClearOnStartup` deletes a leftover block file at plugin start. Fail-open: a malformed block file never wedges the plugin.
 - **Why one lock:** the redundant in-process semaphores (`_uploadWorkLock`, `_postprocessingLock` with its own duplicate stale logic) and the dispatcher's `_seedLock` guarded nothing the global lock did not cover, and `_uploadWorkLock.WaitAsync` sat outside its `try`, so a cancellation between the two acquires leaked the run lock.
- **F-M204:** **A running cycle is never widened and a trigger is never merged into it.** Any overlap between scheduled upload and download is answered by a **reschedule**: `ScheduleRecoveryFireAt(direction, now + JobSpacingMinutes)` for the direction not covered by the running cycle; the dispatcher logs `rescheduled +N min — cycle already running (dir Running, requested Requested)` and returns `false`. When the fire comes due, the coordinator's tick re-checks `PipelineRunLock.IsFree` and defers again if still busy. The per-direction latch exists for the fresh-cycle case only.
 - **Why:** the old merge returned "merged into running cycle", so the other direction's run never happened, and because the merge sat above the global run lock the lock's busy path was never reached. **Test: T23.**
- **F-M205:** **Every reschedule is counted; after 16 the rescheduling stops.** `TryCountReschedule(slot, reason)` keeps one counter per slot (`upload`, `download`, `postprocess`, `dbrefresh`, `oshash`, `refetch`) and returns `false` once the slot has been rescheduled `MaxRescheduleAttempts` times. **The limit is 16** — a single constant; every log line renders `{Limit}` from it, so raising it touches no message text.
 - The count happens in the **public entry points** — `ScheduleRecoveryFireAt` (lock-busy, hourly-cap roll-over, rate-limit respacing), `ScheduleOverloadFire` (service_busy), `SchedulePostprocessFire`, `ScheduleRefreshFire`, `ScheduleOshashFire`, plus the coordinator's own anchor defers for the refresh, oshash and refetch — **before** the F-M65 duplicate check, so repeated triggers for the same slot consume budget rather than being silently swallowed.
 - On refusal the slot's pending fire is dropped (recovery fires) or the defer is skipped (anchor fires) and the slot falls back to its next **regular** anchor; `DeferFire` additionally clears the pending recovery fire.
 - Giving up logs a **warning**, exactly once (`attempt == MaxRescheduleAttempts + 1`); further refusals log at debug so a repeatedly-triggered slot cannot flood the log.
 - The counter is cleared by `ResetReschedule(slot)` on a real fire and by the per-day budget reset (F-M208). It lives in RAM only — a restart resets it, which is the intended fail-open.
 - **Not counted:** daily-limit quota-reset fires (`ScheduleRecoveryFire`) — they are driven by the reset, and dropping them would skip the direction outright. **Test: T24.**
- **F-M206:** **A respacing log line must not claim a quota reset.** A fire carrying an exact, caller-computed time (lock-busy, hourly-cap, rate-limit respacing) applies **no jitter** and must log `respaced by JobSpacingMinutes after lock-busy or rate-limit (no jitter)`. The quota-reset wording (reset anchor + 30–300 min jitter) is confined to the branch that actually dices it. **Test: T25.**
- **F-M94:** **Database refresh as scheduler task:** a dedicated task reconciles the stored state with reality — it removes tracker state for Jellyfin items that no longer exist and verifies the file side of stored verdicts (F-M234). The task, its dashboard name and its log prefix all read "database refresh" (`SubdlDatabaseRefreshTask`, `[SubDL-Refresh]`); the config field `PruneMode` keeps its name because it is serialized. It uses the global run lock and operates on the shared **LiteDB** database (`SharedDbContext`).
- **F-M214:** **A database refresh compacts the database in the same run.** Deleting rows in LiteDB releases pages inside the file but never returns them to the filesystem, and every delete also sits in the rollback journal (`subdl-sync-log.db`) until a checkpoint — so a prune on its own leaves the store physically as large as before it ran. The prune is therefore followed, inside the same run and while it still holds the global run lock, by `SubdlDbContext.Compact`: fold the journal in (`Checkpoint`), then rebuild the file (`Rebuild`) to release the free pages.
 - **Compaction is measured as the whole footprint** — data file plus journal, before and after. Reporting the main file alone understates the starting size (the freed bytes are in the journal at that moment) and can render a real reduction as growth.
 - **It must never fail the task:** an exception is logged as a warning and swallowed. It is housekeeping, and the refresh's own work has already succeeded by then.
 - **No separate setting:** the compaction follows the refresh cadence (`PruneMode`) and runs whenever the refresh runs, including a manual trigger. `PruneMode.Never` therefore means neither prune nor compaction. On an already dense file `Rebuild` reports 0 collections rewritten and changes nothing, so the cost on every run is negligible.
 - **Why not a file-level copy-and-rebuild:** the database is open and other components hold references to it, so swapping the file under them would race with their writers. The rebuild runs in-process on the open store. **Test: T33.**
- **F-M119:** **OSHash refresh as scheduler task:** a dedicated task recomputes expired or fingerprint-changed OSHash cache entries on **its own diced WEEKLY anchor** (`RandomOshashTime`, "D HH:mm", drawn once at install and never re-rolled). It fires **every week** — unlike the database refresh there is no `IsoWeek` gating. It holds the global run lock while mutating the shared cache. `OshashRefresh` is **not** a cadence: it bounds how long a cached fingerprint is trusted (`Never` = fingerprint mismatch only, zero media reads in the steady state), while the fire date comes from the anchor alone. Setting it to `Never` therefore does **not** disable the job.
- **F-M193a:** **No construct LiteDB cannot translate may cross into a query.** A `StringComparison` overload, a helper-method call or any predicate without a `BsonExpression` must be applied **outside** the query lambda. Keep the indexed equality inside and move the rest to LINQ-to-objects afterwards:
 ```
 // wrong — the ItemId index stays unused and the query fails at execution.Find(x => x.ItemId == itemId && string.Equals(x.Language, language, StringComparison.OrdinalIgnoreCase))
 // right.Find(x => x.ItemId == itemId).Where(x => string.Equals(x.Language, language, StringComparison.OrdinalIgnoreCase))
 ```
 - **Why this is a rule and not a style note:** such a predicate does not fail at build time and does not fail helpfully at runtime. LiteDB emits a syntactically valid-looking expression with a **missing operand**, and the exception leaves `RunAsync` — so the failure presents as a **dead pipeline**, not as a compile error, a startup error or a network problem. A pipeline that dies *after* its API calls have succeeded points at this class of defect. **Test: T29.**
- **F-M192 [B1]:** **The partial reset scopes (`scope=upload`, `scope=download`) must WRITE BACK the rows they mutate.** Clearing a file-complete marker mutates the entities returned by `FindAll`, so the persist step must receive **those same objects** — passing a second, freshly deserialized `Update(db.Media.FindAll)` makes both scopes silent no-ops that answer `200 {ok:true}` while the database is untouched. Collect the touched entities and call `Update(list)`. The scope logs the number of cleared markers so a no-op is visible instead of looking like success. **The `all` scope was never affected** — it deletes the whole file, which is why a full reset appeared to work while the partial scopes did not.
- **F-M191 [B1]:** **A SERIES item must carry SHOW-level ids** — TMDB and SubDL expect the tvshow id together with season and episode, **never an episode id**. Jellyfin's provider ids for a mis-typed episode are EPISODE ids in **both** fields.
 - **Episode → show resolution:** `GET /find/{imdbId}?external_source=imdb_id` → `tv_episode_results[0].show_id` IS the series TMDB id; `tv_results[0].id` is the series itself when the id was already show-level. The series IMDb then comes from `/tv/{showId}/external_ids`.
 - **An episode TMDB id cannot be walked up directly:** `/find/{episodeId}?external_source=tmdb_id` returns EMPTY and `/tv/{episodeId}` is 404. Without a usable IMDb id such a value is **dropped** (one `IsShowIdAsync` probe instead of two guaranteed 404s); the caller's type-free title search resolves the show by name.
 - **Placement:** `NormalizeSeriesLevelIdsAsync` runs for series items **after** the file-name type detection (so name-detected series are covered) and **before** the quality gate. Every correction is reported at Normal level: `Episode-level ids for "<title>": Jellyfin says imdb=…, tmdb=… — using the series-level ids imdb=…, tmdb=… (TMDB wins).`
- **F-M191b — Unresolvable IMDb id ⇒ DROP it, never keep it.** When `/find` returns every result array empty, TMDB does not index that IMDb id at all — for a series item it is an episode id TMDB has no record of. Keeping it "as the best available" uploads an episode IMDb id in the SERIES slot, exactly what this rule forbids. Both ids are dropped so the caller's type-free title search resolves the show by name.
- **F-M90:** **Database maintenance UI:** the config page exposes only **Reset** and **Restore** for `subdl-sync.db`. **Reset** creates a timestamped backup, then removes the database so the plugin starts with a fresh registry. **Restore** restores the most recent backup after a single confirmation. No separate "Initialize database" button: the plugin creates an empty database on first start and always opens an existing one.
- **F-M181:** **Single backup retention:** after a database reset all older `subdl-sync.db.bak-*` files are deleted; only the backup created by that reset remains.

### 3.18 Persistent State — Data Model and Compatibility

The plugin keeps its state in **one LiteDB file** (`subdl-sync.db`, next to the DLL, in the plugin data directory), grouped into **five clearly separated areas**, each keyed by the thing it actually describes. "One file, five areas" is deliberate: the areas share a lifetime and are written by the same lock, but they must not be mixed, because a verdict about a video file, a stream position and a piece of subtitle text has three different identities.

#### 3.18.0 Area 0 — Compatibility record (`meta`)

- **F-M195:** exactly **one** row (`_id = "db"`) describing the file itself: `SchemaVersion` (integer, raised by hand whenever the stored shape changes), the plugin version that wrote it last, the Jellyfin version, and a timestamp.
 - Read at startup to answer "may I safely write here?". A `SchemaVersion` **higher** than the running build understands → writing is disabled for the session and an Error is logged naming both versions. Rationale: a newer build may store fields this one would silently drop when it rewrites a row; without the check an older DLL opening newer data destroys it quietly.
 - A **lower** version logs a warning and raises the marker. No migration (F-M195b).
 - The row is written **once per context creation**, never per run: an audit record that rewrites itself every cycle is a write amplifier and tells nobody anything.
 - The Jellyfin version is read from the loaded server assembly and stays **null when unavailable** rather than being invented. The assembly is named `jellyfin` (lower case, from `jellyfin.dll`); `Jellyfin.Server` is only a namespace inside it. The probe must try `jellyfin`, `Jellyfin.Server` and `Jellyfin.Server.Implementations` **case-insensitively** and fall back to the entry assembly.

#### 3.18.1 Area 1 — Media hash cache (`oshashes`)

- **F-M61b:** keyed by **file path** → `Hash`, `Size`, `MtimeUnix`, `Updated`. Pure cache: losing it costs one recomputation and nothing else, which is why it is the one area keyed by a path while every other area is keyed by a hash. A lookup validates size **and** mtime and treats a mismatch as a miss, so a replaced file is re-hashed automatically.

#### 3.18.2 Area 2 — Video files and their embedded tracks (`media`, `embeds`)

- **F-M196:** one record per **video file**, `_id` = the stable OSHash (16 hex characters, F-M61). Carries `Path`, `JellyfinItemId`, `ImdbId`, `TmdbId`, `SdId`, `IsSeries`, `Season`, `Episode`, `LastSeen`. For a series episode the ids are the **SHOW** ids, never episode or season ids (F-M191).
 - Derived, written automatically whenever an embedded track is stored so they cannot drift: `LanguagesAvailable` (sorted, comma separated) and `HearingImpairedAvailable`.
 - Completion marks: `SubtitlesUploadedAt` / `SubtitlesDownloadedAt` + `SubtitlesDownloadedLanguages` (F-M88c, F-M151a).
 - Search bookkeeping: `LastSearchUtc` + `LastSearchLanguages` (F-M64).
- **F-M197:** one record per **embedded subtitle stream** in `embeds`, `_id` = `"<media hash>|<stream position>"`.
 - The key is media hash **plus position** because that is the identity of an embedded track: it has no name and no existence of its own. Two streams of one file can share a language (a normal and an SDH variant, or two differently timed releases), so the language alone must never identify the row.
 - Fields: `Language`, `HearingImpaired`, `ContentHash`, `Status`, `Reason`, `StatusAt`, `SubdlId` (F-M198).
 - **Why position-grain matters:** recording a rejection per (file, language, HI) while recording terminality per position allows the two to contradict each other — one rejected stream blocks the whole language, so a pair with a rejected *and* an uploaded stream is skipped entirely. With the key on the position the two verdicts cannot contradict each other. **Test: T17.**

#### 3.18.3 Area 3 — Sidecar files (`sidecars`)

- **F-M199:** one record per loose `.srt` file, `_id` = the **normalized content hash** (F-M186).
 - Content is the identity because that is what makes a sidecar an independent thing: the same subtitle stays known after the file is renamed or moved, and two sidecars sharing a language but differing in text stay two rows. The file name is stored for diagnosis only and plays **no part** in the key.
 - Fields: the shared subtitle state (F-M198), plus `FileName`, `Path`, `MediaHash` and a copy of the parent metadata (`ImdbId`, `TmdbId`, `IsSeries`, `Season`, `Episode`) so a sidecar can be judged without loading the file record.
 - Downloaded subtitles are stored here too: once fetched, the file on disk **is** a sidecar, so it belongs in the same area rather than a parallel one.
 - Sidecars deliberately carry **no stream position**: they have none. Terminality is therefore the outcome itself (uploaded, rejected, downloaded) — there is no second "settled" marker to write. **Test: T19.**

#### 3.18.4 Area 4 — Burned download candidates (`rejected_candidates`)

- **F-M200:** one record per fetched-and-discarded download candidate, `_id` = `"<item id>|<language>|<SubDL id>"`.
 - Its grain is neither a stream nor a piece of content but "this remote release was burned for this file and language", and SubDL's own id is the only identifier such a verdict has.
 - Fields: `Reason`, `Updated`. Capped at the newest 50 per file and language so a pathological candidate sequence cannot grow the store without bound. Cleared for a file and language when a download finally succeeds (a real save proves the file was not the problem).

#### 3.18.5 The four subtitle states (F-M198)

A subtitle in area 2 or 3 is in exactly one of four states:

- **uploaded** — sent to SubDL and accepted.
- **rejected** — not accepted. The **reason** lives in its own field (`Reason`), never in the state name: `duplicate-remote`, `duplicate-content`, `too-small`, `too-few-cues`, `lang-mismatch`, `bad-structure`, `runtime-mismatch`, `und-off`, `und-too-small`, `und-detection-failed`, `unmapped-language`, `duplicate-self-echo` (we had already uploaded this pair in this run), `candidate-rejected`.
- **downloaded** — fetched from SubDL.
- **pending** — nothing recorded yet. This is **never stored**: it is the absence of a row.

There is deliberately **no "settled"/"done" state.** The previous model kept a separate settled row beside the outcome row, which duplicated every verdict and forced every reader to know both layers and keep them consistent. "Is this position finished?" is answered by asking whether any of the three stored outcomes is present.

#### 3.18.6 Key discipline (all areas)

- **F-M194b:** every area is keyed by a **computed business key stored in the record's own `_id`**, never by a database-assigned auto id. This is the structural correction of **F-M194** (the earlier auto-id keying): with an auto id an upsert of a "new" row can never find the row it means to update, and the write silently inserts instead — so one logical fact came to exist many times over. With a computed key the failure is impossible by construction. **Test: T16.**
- Composite keys are built in exactly one place per area (`SubdlDbContext.EmbedKey`, `SubdlDbContext.CandidateKey`) so writers and readers cannot drift apart on the key shape.
- Every area has an index on its key; the query paths used by the pipelines are indexed as well (media hash, content hash, status, language).

#### 3.18.7 Consequences for readers and writers

- `IsUploaded(mediaHash, language, hearingImpaired)` stays pair-level by design: it answers "do I still need to upload this language for this file", which is what the self-echo guard and the collector ask.
- Per-position questions use `GetEmbed` / `EmbedRejectedReason` / `ArePositionsTerminal` — never a pair-level query.
- A stream skipped **because its language is already uploaded** is recorded as **rejected with `duplicate-self-echo`**, not as "uploaded". It was not uploaded; claiming so would inflate the upload statistics.
- Derived file aggregates (`LanguagesAvailable`, `HearingImpairedAvailable`) are recomputed whenever a track is written, in one place, so no caller can leave them stale.

- **F-M201:** **The plugin persists its OWN configuration fields by patching them into the file on disk**, not by writing its in-memory object over it. The file is read, only those fields are replaced, the rest of the document is preserved byte for byte, and the result is written as a temp file that then replaces the original.
 - **Fields:** the seven scheduler anchors plus the statistics counters and their start stamp (the counters moved to the database in F-M207; the flag `StatusCountersMigratedToDb` remains a config field).
 - **Why:** Jellyfin has no partial write — `SaveConfiguration(config)` always serialises the **whole** object, so any consumer that saves must be able to reproduce every field. Two code paths in this plugin save automatically (the constructor and the event dispatcher) and neither is a user action.
 - **Consequence:** with the fields taken from the file, an empty or damaged in-memory state can no longer erase user settings — the failure is impossible by construction rather than merely guarded against. The temp-file-and-rename write additionally ensures an interrupted save cannot replace a valid file with a truncated one.
 - A `null` field value is **skipped**, never written as empty: "unknown" must not become "delete".
 - When no file exists yet, only the plugin's own fields are written; the document is deliberately **not** seeded from the in-memory object, since that would be the very overwrite this rule exists to prevent.
 - User-facing saves are unaffected: the config page writes through Jellyfin's own `updatePluginConfiguration`, which legitimately sends the complete object. **Test: T20.**

#### 3.18.8 Migration policy

- **F-M195b:** structural changes are **not migrated**. The schema marker in area 0 makes the change visible and the database reset (F-M90) is the intended path; records from an unrecognised schema version are ignored rather than rewritten. Rationale: the stored state is reconstructible from the media files, and a half-migrated store is worse than an empty one.

## 4. Non-Goals
- N-1: Standalone downloader app or separate downloader plugin — integrated in SubDL Scribe.
- N-3: Transcoding/opening bitmap subtitles
- N-5: Changes to Jellyfin core

## 5. Non-Functional Requirements
- **NF-1:** Platform independence: pure IL DLL (net10.0), no native binding, no P/Invoke, no platform-specific dependencies.
- **NF-2:** GPLv3
- **NF-3:** Performance: no blocking of library scans; uploads asynchronous (background queue, IHostedService), extraction sequential per file
- **NF-4:** Robustness: queue survives Jellyfin restart (persistent state files); no infinite retries
- **NF-5:** No telemetry/external calls except api.subdl.com (+ dl.subdl.com for downloads, + api.themoviedb.org when a TMDB key is configured)
- **NF-6:** Testability: test JF instance with a small test library
- **NF-7:** Cross-platform discipline in code: no hardcoded path separators, no P/Invoke, no case-sensitive file operations without normalization
- **NF-8:** **Manual stop button** ("■ Stop all uploads & downloads", General tab): one click sends `DELETE /ScheduledTasks/Running/{taskId}` for BOTH directions.

## 6. Acceptance Criteria
- **A-1:** New episode with embedded subs appears in JF → all text subs automatically extracted, QA-checked, uploaded, without manual intervention
- **A-2:** Dry run on test library produces a complete status report without API calls
- **A-3:** Corrupted/garbled subtitle stream is detected by QA and skipped
- **A-4:** Wrong-language test case → detected per config
- **A-5:** Upload error (simulated 5xx) → retry + "failed" status, no crash
- **A-6:** State survives JF restart: already uploaded files are not processed again
- **A-7:** Library scan is not blocked by running uploads (<1s in-scan overhead)
